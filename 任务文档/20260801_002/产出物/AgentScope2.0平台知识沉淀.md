# AgentScope 2.0 多 Agent 协作平台 — 实战知识沉淀

> 积累时间：2026-08-01 ~ 2026-08-03
> 触发项目：供应链治理智能体团队（agent-team）
> 适用场景：任何需要在 AgentScope 2.0 上构建多 Agent 协作系统的项目

---

## 一、AgentScope 2.0 核心机制与硬限制

### 1.1 ReAct 循环：串行工具调用

AgentScope 2.0 的 Leader Agent 基于 **ReAct 循环**（Reasoning + Acting）工作：

```
思考 → 调用工具 → 等待返回 → 思考 → 调用下一个工具 → ...
```

这个循环的本质约束是：**每次只能调用一个工具，必须等返回后才能调用下一个**。这意味着：

- `AgentCreate` 只能逐个调用，不能批量并行
- 任何依赖"同时创建多个 Agent"的设计都会失败

### 1.2 Worker 的独立 Session：创建串行，执行并发

虽然 AgentCreate 是串行调用的，但每个 Worker 被创建后立即在**独立 Session** 中启动执行。因此：

| 阶段 | 实际模式 | 说明 |
|------|---------|------|
| AgentCreate × N | 串行创建 | ReAct 一次一个，逐个调用 |
| Worker 执行 | 并发运行 | 每个 Worker 创建后立即在独立 Session 中工作 |
| 结果收集 | 平台同步 | 通过 TeamWait 阻塞等待所有 Worker 完成 |

这个"串行创建 + 并发执行"模式是 AgentScope 2.0 多 Agent 系统的基础。

### 1.3 Agent 嵌套创建硬伤

AgentScope 2.0 底层对 Agent 嵌套创建存在硬伤：

- 当已有 4 个执行专家在运行时，再创建第 5 个 Agent（如监理 Agent）容易触发 **token 耗尽**或 **teamwait 状态异常**
- 这是系统底层限制，不是代码逻辑问题

**应对策略**：将额外的 Agent 职责（如质量审查）合并到 Leader Agent 自身，通过"团长亲自审查"替代"创建监理 Agent"。

### 1.4 TeamWait：平台级同步原语

`TeamWait` 是 AgentScope 2.0 提供的核心同步机制：

- 调用后**阻塞等待**，直到所有活跃 Worker 通过 `TeamSay(kind='final', artifacts=[...])` 提交结果
- 返回后说明所有 Worker 已完成
- 不可在 TeamWait 期间向 Worker 发送 TeamSay 分配任务——任务必须在 AgentCreate 时嵌入提示词

## 二、团队模式 API 全景

AgentScope 2.0 提供以下团队管理工具：

| 工具 | 用途 | 调用时机 | 调用次数 |
|------|------|---------|---------|
| `TeamCreate` | 创建团队，返回 team_id，调用者成为 leader | 判断需要团队协作时，第一步 | 全程 1 次 |
| `AgentCreate` | 创建子 Agent，传入角色名称和完整提示词（含任务） | 创建团队后，按需逐个调用 | 每个角色 1 次 |
| `TeamWait` | 阻塞等待所有 Worker 提交 final | 每批 AgentCreate 之后 | 每批 1 次 |
| `TeamSay` | 向子 Agent 发送补充指令 | Worker 完成后的补查阶段 | 按需 |
| `TeamFinish` | 结束团队任务，不可恢复 | 最终交付后 | 全程 1 次 |

**关键约束**：

- `TeamSay` 仅用于补查和反馈，不能用于初始任务分配（任务在 AgentCreate 时嵌入提示词）
- `TeamSay` 发送给多个 Worker 时必须逐个发送，每个发送后等待响应
- `TeamFinish` 调用后不可恢复

## 三、AgentCreate 提示词策略

### 3.1 核心原则：完整提示词 + 任务嵌入

AgentCreate 时必须传入**完整的角色提示词**（含任务描述），而不是只传 first_task。

**错误做法**（导致 Worker 缺少技能定义）：

```
AgentCreate(name="依赖审计Agent", first_task="请分析项目依赖")
```

**正确做法**（Worker 创建后即可独立执行）：

```
AgentCreate(name="依赖审计Agent", prompt="你是软件供应链依赖审计专家。你的任务是...
（完整的角色定义、分析维度、输出格式、注意事项、当前任务）")
```

### 3.2 提示词结构模板

每个角色的 AgentCreate 提示词应包含以下部分：

```
你是 [角色名称]。你的任务是 [一句话职责描述]。

## 分析维度
（详细的检查维度、判断标准、风险等级定义）

## 分析方法
（具体执行步骤）

## 输出格式
（明确的结构化输出模板，作为格式约束）

## 注意事项
（边界情况说明、容易误判的场景）

## 当前任务
- 项目名称：[项目名]
- 项目路径：[目标软件路径]
- 治理要求：[具体治理条目]

完成后，通过 TeamSay 提交结果：
TeamSay(kind='final', artifacts=['[项目名]XX报告.md'])
```

### 3.3 完整提示词存放位置

**所有角色的完整提示词嵌入 AGENTS.md 的"角色库"章节。** AgentCreate 时从角色库中提取对应角色的提示词，填入 [项目名]、[目标软件路径]、[治理要求] 等变量后传入。

SKILL.md 文件作为"参考文档"和"平台上传用技能包"保留，实际运行时 Agent 的提示词来自 AGENTS.md 中的角色库。

## 四、工作流标准模式

### 4.1 推荐流程（13 步）

```
阶段一：创建执行专家
  Step 1: TeamCreate（创建团队，全程 1 次）
  Step 2: AgentCreate × N（逐个创建，串行调用，提示词含任务）
  Step 3: TeamWait（阻塞等待所有 Worker 完成）

阶段二：团长审查
  Step 4: Read 各 Worker 输出报告
  Step 5: 逐份审查（覆盖完整性、分析深度、证据充分性、一致性）
  Step 6: 判定——全部合格 → 阶段四 / 有问题 → 阶段三

阶段三：补查循环（最多 2 轮）
  Step 7: TeamSay 逐个发送退回意见
  Step 8: TeamWait 等待补查完成
  Step 9: 复核，判断是否需再次补查

阶段四：汇总与交付
  Step 10: 交叉验证（不同专家结论对照）
  Step 11: 汇总综合治理报告
  Step 12: 交付
  Step 13: TeamFinish
```

### 4.2 退回补查规范

退回意见必须包含三个要素：

- **具体问题**：遗漏了什么
- **具体位置**：在哪里
- **具体要求**：需要补充什么

好的退回意见：

> "代码分析专家只分析了 howdoi.py 主文件，遗漏了 setup.py 中的 distutils 废弃 API 调用（第 14 行）和 subprocess.check_call（第 63 行），以及 fastentrypoints.py 中的猴子补丁模式。请补充分析这三个位置。"

坏的退回意见：

> "代码分析不够全面，请重新分析。"

## 五、质量审查维度

团长亲自审查时，按以下四个维度逐份评估：

### 覆盖完整性
- 治理清单的每条要求是否都有对应的专家覆盖？
- 专家是否只检查了部分文件？
- 专家是否只分析了部分代码路径？

### 分析深度

| 深度等级 | 特征 | 判定 |
|---------|------|------|
| 表面 | 只说"发现 X 个问题"，无具体位置、无代码片段 | 不合格，退回 |
| 中等 | 有问题位置和代码片段，但未分析上下文和影响 | 需补充 |
| 深入 | 有位置、代码、上下文分析、影响评估、修复建议 | 合格 |

### 证据充分性
- 声称"存在高风险" → 必须有具体的代码或配置证据
- 声称"版本过时" → 必须说明当前版本和最新版本的差距
- 声称"无问题" → 必须说明检查了哪些内容、为什么判断无问题

### 一致性检查
- 不同专家的结论是否存在矛盾？
- 许可证专家说"MIT"→ 代码分析专家是否发现了其他许可证声明？
- 依赖审计专家说"版本安全"→ 完整性校验专家是否发现来源不可信？

## 六、技能（Skill）设计规范

### 6.1 SKILL.md 格式要求

每个 SKILL.md 开头必须包含 YAML frontmatter，含 `name` 和 `description` 字段：

```yaml
---
name: skill-identifier
description: 一句话描述技能用途、范围和输出
---
```

缺少这两个字段，技能无法上传到平台。

### 6.2 SKILL.zip 打包规范

- 每个技能文件夹内包含 `SKILL.md` 和 `SKILL.zip`
- `SKILL.zip` 中**仅包含 SKILL.md**，无父级文件夹
- zip 放置位置：与 SKILL.md 同级目录

### 6.3 技能与 AGENTS.md 的关系

| 文件 | 角色 | 用途 |
|------|------|------|
| AGENTS.md | 唯一必需文件 | 包含角色库，AgentCreate 时直接提取完整提示词 |
| skills/*/SKILL.md | 参考文档 | 独立技能定义，可上传平台供其他场景复用 |
| skills/*/SKILL.zip | 上传包 | 平台技能库上传用 |

实际运行时，Agent 的提示词来自 AGENTS.md 的角色库，不依赖 SKILL.md 文件。

## 七、常见坑点与解决方案

### 坑点 1：TeamSay 并行 + 提前解除 teamwait → 卡死

**现象**：主 Agent 收到 2 个专家回复后解除 teamwait 状态，后续专家的 TeamSay 消息无法送达，系统卡死。

**根因**：AgentCreate 后使用 TeamSay 分配任务，且并行发送多条 TeamSay 后立即"等待所有回复"，但实际只收到部分回复就提前退出等待状态。

**解决**：任务在 AgentCreate 时嵌入提示词，Worker 创建后自动执行。Leader 通过 TeamWait 等待所有 Worker 完成。TeamSay 仅用于退回补查，且逐个发送、逐个等待。

### 坑点 2：AgentCreate 只传 first_task → Worker 缺少技能

**现象**：Worker 创建后不知道自己的角色定义、分析维度、输出格式，无法正常工作。

**根因**：AgentCreate 时只传了简短的 first_task，没有传完整角色提示词。

**解决**：AgentCreate 时传入角色库中的完整提示词（含角色定义、分析维度、输出格式、当前任务）。

### 坑点 3：主 Agent 自己分析而非创建专家

**现象**：主 Agent 收到治理请求后，自己执行了所有分析工作，没有创建任何专家 Agent。

**根因**：AGENTS.md 中使用了模糊的"调用技能"表述，主 Agent 理解为"自己调用技能执行"，而非"创建专家 Agent"。

**解决**：AGENTS.md 中明确使用 `AgentCreate` 工具名称，工作流中明确列出每个步骤需要创建哪个 Agent，提供完整的角色提示词。

### 坑点 4：Token 耗尽

**现象**：创建到第 4~5 个 Agent 时，token 消耗已达 114.9k，后续 AgentCreate 失败。

**根因**：主 Agent 在创建 Agent 前做了过多前置分析，消耗了大量 token。

**解决**：
- 主 Agent 只做编排，不做分析
- AgentCreate 时使用角色库中的预设提示词，不额外生成
- 审查和汇总阶段合理控制 token 使用

### 坑点 5：监理 Agent 创建失败

**现象**：4 个执行专家创建完成后，第 5 个监理 Agent 无法创建（token 耗尽或 teamwait 异常）。

**根因**：AgentScope 2.0 底层对 Agent 嵌套创建存在硬伤。

**解决**：取消监理 Agent，改为团长亲自审查。审查维度和标准不变，只是执行者不同。

## 八、输出模式演进

| 版本 | 输出形式 | 核心逻辑 | 问题 |
|------|---------|---------|------|
| v2.x | 7 份独立报告套件 | 团长只写总览，不合并 | 用户收到 7 个文件，阅读体验差 |
| v3.5.0 | 1 份综合治理报告 | 团长汇总所有专家结果 | 一份文件，结构完整，可直接阅读 |

**综合治理报告结构**：

```
[项目名]综合治理报告.md
├── 封面与基本信息
├── 第一章：治理总览与判定（团长编写）
├── 第二章 ～ 第七章：各维度专家报告（原文嵌入）
├── 第八章：交叉验证与综合判定（团长编写，含加权评分）
└── 附录：原始报告目录（独立文件保留）
```

## 九、版本演进路线图

整个 agent-team 项目从 v2.0.0 到 v3.5.0 的演进路径：

| 版本 | 关键变更 | 解决的问题 |
|------|---------|-----------|
| v2.0.0 | 初始设计：4 专家 + 1 监理 | — |
| v2.1.0 | TeamSay 逐个发送 | TeamSay 并行卡死 |
| v2.2.0 | AgentCreate 时嵌入任务 | Worker 无技能定义 |
| v2.3.0 | 主 Agent 角色库 + 完整提示词 | Token 耗尽 |
| v2.4.0 | 取消监理 Agent，团长亲自审查 | 监理 Agent 创建失败 |
| v3.0.0 | 新增 SBOM + 投毒分析，6 维度 | 治理覆盖不完整 |
| v3.5.0 | 输出改为 1 份综合治理报告 | 报告碎片化 |

**每次迭代的核心教训**：在 AgentScope 2.0 上做多 Agent 系统，必须深度理解平台约束（ReAct 串行、TeamWait 同步、嵌套创建硬伤），而不是按照理想架构强行设计。

## 十、给后续项目的建议

1. **先理解平台约束，再设计架构**。AgentScope 2.0 的 ReAct 循环、TeamWait 同步、嵌套创建限制是硬约束，不是可以绕过的。

2. **完整提示词是 Agent 的灵魂**。AgentCreate 时传入的提示词决定了 Worker 的能力边界。提示词必须包含角色定义、分析维度、输出格式、注意事项、当前任务。

3. **AGENTS.md 的角色库是唯一真相来源**。所有角色提示词集中管理，AgentCreate 时直接提取。SKILL.md 作为参考和上传包保留。

4. **TeamWait 是同步核心，不要绕过它**。任务在 AgentCreate 时嵌入，Leader 通过 TeamWait 等待。TeamSay 只用于补查。

5. **能合并到 Leader 的职责就不要创建新 Agent**。每多一个 Agent 就多一份 token 消耗和创建失败风险。质量审查、汇总报告等都可以由 Leader 亲自完成。

6. **输出一份报告比输出一堆文件好**。用户最终需要的是一个完整的结论，不是一堆需要自己拼凑的碎片。

7. **退回意见必须具体**。模糊的反馈只会导致反复补查，浪费 token 和时间。具体问题 + 具体位置 + 具体要求，缺一不可。
