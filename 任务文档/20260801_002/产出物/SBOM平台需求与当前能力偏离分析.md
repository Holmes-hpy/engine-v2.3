# SBOM 分析平台需求与当前治理团队能力偏离分析

> 分析日期：2026-08-03
> 参考文档：《SBOM分析平台多智能体协作体系规范文档》
> 对比对象：供应链治理智能体团队（agent-team v3.5.0）
> 分析结论：**两套体系高度正交，6/7 Agent 能力完全缺失，1/7 部分覆盖**

---

## 一、偏离度总览

| 文档定义的 Agent | 当前对应能力 | 覆盖度 | 偏离说明 |
|:--|:--|:--:|:--|
| 1. 输入解析与验证Agent | 无 | 0% | 解析Excel→生成CycloneDX SBOM→安全清洗→哈希审计 |
| 2. 工具策略Agent | 无 | 0% | Snyk/Trivy/Grype/OSV 多工具并行漏洞扫描 |
| 3. 漏洞分析Agent | 无 | 0% | CVE归并去重、CVSS分级、EPSS+KEV关联研判 |
| 4. VEX生成Agent | 无 | 0% | 可达性分析、CycloneDX VEX文档生成 |
| 5. 优先级排序与风险评估Agent | 无 | 0% | 五维度加权风险评分、修复优先级排序 |
| 6. 修复建议Agent | 无 | 0% | 官方方案检索、兼容性评估、替代方案输出 |
| 7. 报告与集成Agent | 部分 | ~30% | 仅Markdown报告，缺失：多格式/系统集成/审计日志/VEX签发 |

## 二、逐 Agent 详细偏离分析

### 2.1 输入解析与验证Agent —— 完全缺失

**文档要求：**

| 能力项 | 说明 |
|:--|:--|
| 文件解析 | 支持 `.xlsx/.xls` 格式，提取组件名、版本号 |
| 数据校验 | 语义化版本校验、组件名非空检查 |
| 安全清洗 | 过滤特殊字符、系统命令、注入载荷，防 Prompt Injection |
| 格式转换 | 转换为 CycloneDX 1.4~1.6 标准 SBOM JSON |
| 审计溯源 | 计算输入文件 SHA-256 哈希，全流程追踪 |
| 严格边界 | 校验失败直接终止，不擅自猜测、修正、补全数据 |

**当前最近能力：SBOM分析Agent**

SBOM分析Agent 只分析**已有 SBOM 的质量**（NTIA 最小要素检查、覆盖完整性、数据准确性），不负责解析 Excel 和生成 SBOM。一个是 SBOM 的"生产端"，一个是 SBOM 的"消费端"，职责正交。

**缺口：** 6 项能力全部缺失。

---

### 2.2 工具策略Agent —— 完全缺失

**文档要求：**

| 能力项 | 说明 |
|:--|:--|
| 生态识别 | 识别组件技术生态（Maven、npm、PyPI、Go 等） |
| 工具调度 | 按需匹配 Snyk、Trivy、Grype、OSV 等扫描工具 |
| 并行扫描 | 支持多工具并行/串行扫描，单工具失败不中断整体 |
| 结果去重 | 多工具对同一组件的重复报告合并去重 |
| 结构化输出 | 按组件维度整合 CVE 编号、CVSS 评分、描述、影响版本、修复版本 |

**当前最近能力：无**

我们没有任何调用外部漏洞扫描工具的能力。当前的安全检测是**静态代码分析**（危险函数调用、硬编码凭证、网络通信安全），而不是基于 CVE 数据库的漏洞匹配扫描。这是两个完全不同的安全检测维度。

**缺口：** 5 项能力全部缺失。

---

### 2.3 漏洞分析Agent —— 完全缺失

**文档要求：**

| 能力项 | 说明 |
|:--|:--|
| 数据归并 | 同一 CVE 被多工具报告时合并去重，整合完整信息 |
| CVSS 分级 | 基于 CVSS 评分划分 Critical/High/Medium/Low 四级 |
| EPSS 关联 | 关联 EPSS 利用概率评分，判定漏洞被利用的可能性 |
| CISA KEV 关联 | 关联 CISA 已知被利用漏洞目录，标记实战高风险 |
| 优先级计算 | 综合多维度数据生成漏洞优先级评分与排名 |
| 统计报告 | 按组件维度输出漏洞统计摘要与明细 |

**当前最近能力：无**

我们没有任何 CVE 分析、CVSS 评分、EPSS/KEV 关联的能力。这个 Agent 是 SBOM 漏洞管理平台的核心决策枢纽，根据行业标准漏洞数据库做量化分析，在我们的治理体系中完全不存在对应能力。

**缺口：** 6 项能力全部缺失。

---

### 2.4 VEX生成Agent —— 完全缺失

**文档要求：**

| 能力项 | 说明 |
|:--|:--|
| 上下文匹配 | 获取目标系统部署环境、组件使用方式、运行配置 |
| 可达性分析 | 逐漏洞判定在实际业务环境中是否可触发、可利用 |
| 状态分配 | 分配标准 VEX 状态：not_affected / affected / fixed / under_investigation |
| 依据撰写 | 为所有 VEX 断言提供可审计、可追溯的技术推理依据 |
| VEX 文档生成 | 输出符合 CycloneDX 1.6 规范的标准 VEX 文档 |
| 人工兜底 | 无法判定时标记 under_investigation，转人工处理 |

**当前最近能力：无**

VEX（Vulnerability Exploitability eXchange）是漏洞管理的高级能力，需要理解业务系统的运行时上下文（部署架构、调用链、配置参数），远超我们当前治理体系的范围。我们完全没有涉及可达性分析、VEX 状态判定、CycloneDX VEX 文档生成等能力。

**缺口：** 6 项能力全部缺失。

---

### 2.5 优先级排序与风险评估Agent —— 完全缺失

**文档要求：**

| 能力项 | 说明 |
|:--|:--|
| 多维度聚合 | 综合 CVSS + EPSS + CISA KEV + VEX状态 + 业务影响 五大维度 |
| 加权评分 | 五维度加权计算综合风险评分，算法透明可解释 |
| 全局排序 | 按综合风险分数降序排列所有漏洞 |
| 高危组合识别 | 识别多漏洞集中同一组件、同一调用链的高危风险组合 |
| VEX 适配 | 自动降低 not_affected 类漏洞优先级，保留记录不遗漏 |

**当前最近能力：无**

我们每个专家有独立的评分体系（依赖审计评分、代码安全评分、许可证合规评分等），但这是**单个维度独立评分**，不是跨维度加权综合。文档要求的是把多个维度的风险数据（CVSS、EPSS、KEV、VEX、业务影响）聚合后重新计算综合风险，这是完全不同的评分逻辑。

**缺口：** 5 项能力全部缺失。

---

### 2.6 修复建议Agent —— 完全缺失

**文档要求：**

| 能力项 | 说明 |
|:--|:--|
| 方案检索 | 查询官方安全公告、CVE 数据库，获取权威修复方案 |
| 兼容性评估 | 研判版本升级对 API 兼容性、依赖冲突的影响 |
| 方案区分 | 直接升级可行时输出升级方案，不可行时提供临时缓解替代方案 |
| 溯源标注 | 所有修复方案标注官方来源，保证可审计 |
| 风险提示 | 高兼容性风险方案强制标注，提示人工复核 |

**当前最近能力：无**

我们的专家会给出治理层面的建议（如"锁定版本号"、"升级到最新版本"），但这是**治理建议**，不是文档要求的"查询 CVE 数据库→评估版本升级兼容性→输出具体升级版本号或替代方案"这种**可操作的漏洞修复方案**。文档要求的是工程级别的修复指导，我们的是合规级别的治理建议。

**缺口：** 5 项能力全部缺失。

---

### 2.7 报告与集成Agent —— 部分覆盖（~30%）

**文档要求：**

| 能力项 | 当前覆盖 | 说明 |
|:--|:--:|:--|
| Markdown 报告 | 有 | 综合治理报告.md |
| JSON 结构化报告 | 无 | 缺失，无结构化数据输出 |
| PDF 正式归档 | 无 | 缺失，无 PDF 生成能力 |
| Jira 工单创建 | 无 | 缺失，无外部系统集成 |
| Slack 消息推送 | 无 | 缺失，无消息推送能力 |
| Dependency-Track 同步 | 无 | 缺失，无 SBOM 平台对接 |
| 全流程审计日志 | 无 | 缺失，无决策链记录 |
| VEX 正式签发 | 无 | 缺失，无 VEX 签发流程 |
| 外部 API 容错回退 | 无 | 缺失，无集成容错机制 |

**当前能力：** 我们仅能生成一份 Markdown 格式的综合治理报告（含封面、总览、6维度分析、交叉验证、综合判定），原始专家报告作为附件保留。无任何外部系统集成能力。

**缺口：** 9 项能力中 8 项缺失。

## 三、本质差异总结

两套体系解决的是**不同的问题**：

| 维度 | SBOM 漏洞管理平台 | 当前供应链治理体系 |
|:--|:--|:--|
| **核心目标** | 基于 SBOM 的漏洞发现→分析→修复闭环 | 软件供应链安全合规性审查 |
| **输入** | Excel 组件清单 | GitHub 仓库 / 本地项目 |
| **核心能力** | CVE 漏洞扫描、VEX 判定、修复方案 | 依赖审计、许可证合规、代码安全、投毒检测 |
| **输出** | 漏洞优先级清单 + 修复方案 + 多格式报告 | 综合治理报告（6 维度合规审查） |
| **技术依赖** | Snyk/Trivy/Grype/OSV 等扫描工具 | 静态代码分析、依赖声明解析 |
| **标准对齐** | CycloneDX 1.4~1.6、CVSS、EPSS、CISA KEV | SPDX、NTIA 最小要素 |
| **集成能力** | Jira / Slack / Dependency-Track | 无外部系统集成 |
| **工作流模式** | 管道式串行（7 Agent 流水线） | 串行创建 + 并发执行 + 团长审查 |
| **容错策略** | 单工具失败不中断、数据残缺标记人工审核 | 退回补查（最多 2 轮）、争议项人工复核 |

## 四、能力重合点

两套体系仅有以下微弱交集：

| 交集点 | 文档能力 | 当前能力 | 重合度 |
|:--|:--|:--|:--|
| SBOM 分析 | 生成 CycloneDX SBOM | 分析 SBOM 质量（NTIA 要素） | 方向不同，一个生产一个消费 |
| 报告输出 | 多格式报告 + 系统集成 | Markdown 综合治理报告 | 仅格式层面有交集 |
| 修复建议 | 工程级修复方案 | 治理级修复建议 | 深度不同，不可替代 |

**结论：两套体系在能力上高度正交，几乎没有可复用的能力模块。**

## 五、如果要补齐，需要做什么

若要将当前治理团队扩展为兼容 SBOM 漏洞管理平台的能力，需要新增以下工作：

### 5.1 新增 6 个 Agent

| 新增 Agent | 核心能力 | 复杂度 | 预估提示词规模 |
|:--|:--|:--:|:--:|
| 输入解析与验证Agent | Excel解析、数据清洗、CycloneDX SBOM生成 | 中 | ~200 行 |
| 工具策略Agent | 漏洞扫描工具调度、结果去重 | 高 | ~300 行 |
| 漏洞分析Agent | CVE归并、CVSS/EPSS/KEV 关联分析 | 高 | ~350 行 |
| VEX生成Agent | 可达性分析、VEX 文档生成 | 极高 | ~400 行 |
| 优先级排序与风险评估Agent | 五维度加权评分、高危组合识别 | 中 | ~250 行 |
| 修复建议Agent | 官方方案检索、兼容性评估 | 中 | ~250 行 |

### 5.2 升级 1 个 Agent

| 升级 Agent | 新增能力 | 复杂度 |
|:--|:--|:--:|
| 报告与集成Agent（当前为团长汇总） | JSON/PDF 输出、Jira/Slack 集成、审计日志、VEX 签发 | 高 |

### 5.3 架构调整

当前架构是"6 专家并发 + 团长审查"，文档要求的是"7 Agent 管道式串行流水线"。如果完全对齐文档，需要重新设计整个工作流：

```
当前：AgentCreate × 6 → TeamWait → 团长审查 → 汇总报告
文档：Excel上传 → 解析 → 扫描 → 分析 → VEX → 排序 → 修复 → 报告
```

两种模式在 AgentScope 2.0 上的可行性分析：

- **管道式串行**在 AgentScope 2.0 上更可行——因为 ReAct 本身就是串行的，管道式天然匹配
- 但当前 6 Agent 并发模式的优势（并行执行、TeamWait 同步）在管道式中无法利用
- 如果全部改为管道式，**总执行时间会显著增加**（7 个 Agent 依次执行，每个依赖前一个的输出）

### 5.4 预估工作量

| 工作项 | 预估工作量 | 说明 |
|:--|:--|:--|
| 新增 6 个 Agent 角色提示词 | 3-4 天 | 含分析维度、输出格式、注意事项、任务模板 |
| 升级 1 个 Agent | 1 天 | 报告与集成能力扩展 |
| 重写 AGENTS.md 工作流 | 1 天 | 从并发模式改为管道式串行 |
| 新增 SKILL.md + SKILL.zip | 0.5 天 | 6 个新技能的打包上传 |
| 联调测试 | 2-3 天 | 管道式数据流验证、容错测试 |
| **合计** | **8-10 天** | 不含外部工具（Snyk/Trivy等）的接入开发 |

## 六、建议

1. **不建议直接合并两套体系**。SBOM 漏洞管理平台和供应链治理体系解决的是不同层次的问题，强行合并会导致角色职责混乱、提示词膨胀、token 消耗激增。

2. **建议独立建设 SBOM 漏洞管理 Agent 团队**。参照文档的 7 Agent 管道式架构，新建一个独立的 `sbom-vuln-team/` 项目，与现有 `agent-team/` 并行存在。

3. **可复用的经验**：当前治理团队的架构设计经验（完整提示词策略、TeamWait 同步、退回补查机制、质量审查维度）可直接迁移到新模式中，但角色定义和提示词需要从头编写。

4. **注意 AgentScope 2.0 的约束**：7 Agent 管道式串行意味着需要 7 次 AgentCreate，这可能触发 token 耗尽的硬伤。建议考虑将某些轻量 Agent（如输入解析、优先级排序）合并，控制在 5 个以内。
