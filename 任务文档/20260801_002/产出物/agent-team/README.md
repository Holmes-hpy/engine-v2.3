## 二、核心设计理念：AgentCreate + TeamWait（对齐可研报告 v1.7.7 模式）

### 关键概念：任务嵌入提示词，TeamWait 做同步，Worker 自主执行

```
┌──────────────────────────────────────────────────────────┐
│  主Agent（编排者）— AGENTS.md                              │
│  ┌─────────────────────────────────────────────────┐    │
│  │ TeamCreate → AgentCreate(提示词+任务) → TeamWait → 收结果│    │
│  │ → 监理AgentCreate → TeamWait → 补查 → 判定 → TeamFinish│    │
│  └─────────────────────────────────────────────────┘    │
│     │ AgentCreate(角色1提示词+任务)  ← Worker启动即执行      │
│     │ AgentCreate(角色2提示词+任务)                         │
│     │ AgentCreate(角色3提示词+任务)                         │
│     │ AgentCreate(角色4提示词+任务)                         │
│     │ TeamWait() ← 阻塞等待全部 Worker 提交 final           │
│     │ AgentCreate(角色5提示词+审查材料)  ← 质量监理         │
│     │ TeamWait() ← 阻塞等待监理提交 final                  │
│     ▼                                                      │
│  ┌──────────────────────────────────────────────────┐    │
│  │ Worker 完成后通过 TeamSay(kind='final') 提交结果    │    │
│  │ 依赖审计 │ 代码安全 │ 许可证合规 │ 完整性校验 │ 质量监理 │    │
│  └──────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────┘
```

**核心原则：任务在 AgentCreate 时嵌入提示词。** Worker 创建后自动执行，不需要 Leader 再发 TeamSay 分配任务。Leader 通过 TeamWait 等待所有 Worker 完成。这借鉴了可研报告 v1.7.7 的成功模式——AgentCreate(完整提示词) → TeamWait → 收结果。

**与之前版本的根本区别：**

| 版本 | 任务分配方式 | 同步方式 | 问题 |
|------|------------|---------|------|
| v2.0.0 | AgentCreate 后 TeamSay 发任务 | 手动"等回复" | TeamSay 并行+提前解除 teamwait → 卡死 |
| v2.1.0 | AgentCreate 后 TeamSay 逐个发 | 逐个等待回复 | 仍然依赖 TeamSay 通信，逻辑复杂 |
| **v2.2.0** | **AgentCreate 时嵌入任务** | **TeamWait 平台同步** | ✅ 正确 |

**SKILL.md 的角色：** skills/ 目录下的 SKILL.md 文件作为"参考文档"和"平台上传用技能包"保留，实际运行时 Agent 的提示词来自 AGENTS.md 中的角色库。

### 双层架构

```
┌─────────────────────────────────────────────────────┐
│                    执行层（4 个专家Agent）              │
│  依赖审计 │ 代码安全分析 │ 许可证合规 │ 完整性校验      │
│   ↓ 产出   ↓ 产出        ↓ 产出      ↓ 产出          │
├─────────────────────────────────────────────────────┤
│                    质量监理层（1 个监理Agent）          │
│  完整性审查 │ 深度审查 │ 证据审查 │ 一致性审查 │ 交叉验证 │
│   ↓ 发现问题 → 退回专家 → 补查 → 复核 → 放行          │
├─────────────────────────────────────────────────────┤
│                    主 Agent（编排 — 不执行检测）       │
│  解析清单 → 创建Agent → 分配任务 → 接收结果 → 汇总报告  │
└─────────────────────────────────────────────────────┘
```

**质量监理是灵魂，不是附庸。** 没有质量监理，这只是一个"4 个脚本并行跑"的工作流引擎。有了质量监理，它才是一个"能自我纠错的智能体系统"。

## 三、为什么质量监理是核心？

### 客户要的不是"自动检测"，是"自动确保检测质量"

传统方式：人写脚本 → 脚本跑检测 → 人看结果 → 人判断够不够 → 人决定要不要补查

智能体方式：智能体调度专家 → 专家跑检测 → **质量监理审查** → 监理发现遗漏 → 退回补查 → 复核通过 → 出报告

**关键跳跃：传统方式里"人判断够不够"这一步，被质量监理替换了。** 这才是 AI 的价值——不是替代执行，是替代判断。

### 演示中的叙事张力

| 时刻 | 发生了什么 | 观众感受 |
|------|----------|---------|
| 4 个专家跑完 | 汇总出 8 个问题 | "哦，自动化脚本" |
| 质量监理介入 | 监理说"代码分析专家漏了 setup.py 和 fastentrypoints.py" | "等等，它竟然会检查自己人？" |
| 专家退回补查 | 代码分析专家补充分析，又发现 3 个问题 | "它真的回去补了！" |
| 监理复核 | 监理确认"补充完整，放行" | "这个系统有质量意识" |

**同样的 11 个问题，加上质量监理的叙事，说服力翻 10 倍。**

**对完整性校验专家的退回意见：**

> "完整性校验专家只检查了'无 SHA256/GPG 签名'，但未检查：

| 初始检测 | 8 个 |

**演示时主 Agent 可以这样说：** "初始检测发现 8 个问题，质量监理审查后认为代码分析覆盖不完整，退回补查。补查后新增 3 个发现，最终确认 11 个问题。监理复核通过，进入报告生成。"

## 五、演示流程（6 幕，新增质量监理环节）

### 第 1 幕：上传治理清单（1 分钟）
- 展示 10 条治理要求
- 主 Agent 解析并生成任务 DAG

### 第 2 幕：主Agent创建专家，TeamWait 等待（3 分钟）
- 主Agent **逐个调用 AgentCreate**，每次传入完整提示词（含任务描述）
- 四个 AgentCreate 完成后，调用 **TeamWait** 阻塞等待
- 四个 Worker 在各自 Session 中并发执行，完成后通过 `TeamSay(kind='final')` 提交结果
- TeamWait 返回后，输出"✅ 四个执行专家全部完成检测"

### 第 3 幕：质量监理审查（3 分钟）★ 核心
- 监理接收所有专家输出
- 逐专家审查：完整性、深度、证据、一致性
- 发现代码分析专家和完整性校验专家存在遗漏
- **退回两个专家，要求补查**

### 第 4 幕：专家补查（2 分钟）
- 代码分析专家补充分析 setup.py、fastentrypoints.py、workflow
- 完整性校验专家补充分析 pip 安装安全性、修正结论
- 新增 3 个发现

### 第 5 幕：监理复核与放行（1 分钟）
- 监理复核补查结果
- 确认全部合格，签发放行

### 第 6 幕：报告生成（1 分钟）
- 汇总 11 个问题
- 输出包含质量监理报告的完整治理报告

## 六、执行模式说明

### AgentScope 2.0 的 ReAct 约束

AgentScope 2.0 的 Leader Agent 基于 ReAct 循环工作：每次只能调用一个工具，等待返回后再调用下一个。这意味着 **AgentCreate 只能逐个调用，不能并行**。

但 Worker 被创建后立即在独立 Session 中开始执行——创建是串行的，执行是并发的。四个 Worker 创建完毕后，它们已经在各自 Session 中并发工作了。

### 串行与并行的实际划分

| 阶段 | 执行模式 | 原因 |
|------|---------|------|
| AgentCreate × 4 | **串行创建，并发执行** | ReAct 每次只能调一个工具；Worker 创建后立即独立运行 |
| TeamWait | **平台级阻塞同步** | 等待所有 Worker 通过 `TeamSay(kind='final')` 提交结果 |
| 质量监理 | **AgentCreate + TeamWait** | 等执行专家全部完成后，创建监理Agent，TeamWait 等待 |
| 退回补查 | **TeamSay 逐个发送 + TeamWait** | 补查指令发送完毕后，TeamWait 等待补查完成 |

## 七、导入智能体平台

### 核心文件：AGENTS.md（唯一必需）

**AGENTS.md 已包含五个角色的完整提示词**，AgentCreate 时直接传入。因此只需导入 AGENTS.md 作为主 Agent 提示词即可运行。

### 可选：上传技能包（SKILL.zip）

skills/ 目录下的 SKILL.md 可作为独立技能上传到平台，供其他场景复用。每个技能文件夹内已备好 `SKILL.zip`：

| 技能文件夹 | zip 包 | 用途 |
|-----------|--------|------|
| `skills/dependency-auditor/` | `SKILL.zip` | 独立上传，其他项目可复用 |
| `skills/code-analyzer/` | `SKILL.zip` | 独立上传，其他项目可复用 |
| `skills/license-compliance/` | `SKILL.zip` | 独立上传，其他项目可复用 |
| `skills/integrity-checker/` | `SKILL.zip` | 独立上传，其他项目可复用 |
| `skills/quality-inspector/` | `SKILL.zip` | 独立上传，其他项目可复用 |

### 导入顺序

1. **导入 AGENTS.md** → 作为主 Agent 系统提示词（唯一必需步骤）
   - AGENTS.md 的"角色库"章节包含五个角色的完整提示词
   - 主Agent 通过 AgentCreate 将对应提示词直接传给子Agent
   - 子Agent 不需要额外绑定技能即可运行
2. （可选）上传 5 个 SKILL.zip 到平台技能库
   - 这些技能是独立的"岗位说明书"，可供其他治理项目复用
   - 本项目的 Agent 运行时**不依赖**这些技能文件

## 八、注意事项

- **TeamWait 是核心同步机制**：v3.2.0 最重要的架构变更。任务在 AgentCreate 时嵌入提示词，Worker 自主执行，Leader 通过 TeamWait 等待。禁止在 TeamWait 期间发 TeamSay 分配任务——那会扰乱 Worker 的 Session 状态。
- 质量监理的退回必须是真的——不能是"先故意漏掉几个问题再让监理发现"这种表演，要真实
- 如果客户问"监理会不会太严格导致效率低"，回答："质量监理的退回有次数上限（2 次），在质量和效率之间取得平衡。实际上，监理的审查成本远低于人工审查，但效果接近。"
- 如果客户问"为什么不是并行执行"，直接回答："AgentCreate 受 ReAct 循环限制只能串行调用，但 Worker 创建后各自在独立 Session 中并发运行。TeamWait 是平台级同步原语，确保所有 Worker 完成后再进入下一阶段，这是可研报告 v1.7.7 验证过的可靠模式。"
