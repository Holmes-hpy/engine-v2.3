# 多格式报告生成技能

## 功能

整合全链路分析数据，生成多格式标准化报告，包括 Markdown（人类可读）、JSON（结构化数据）、PDF（正式归档），并生成审计日志。

> **说明**：本技能生成的 Markdown 和 JSON 报告可直接输出。PDF 报告在无 PDF 生成工具的环境中以"可导出的 Markdown + 样式说明"形式提供，或由平台转换生成。

## 适用场景

当所有分析阶段完成，需要生成最终交付报告时，调用本技能。

## 输入

- SBOM 数据
- 扫描结果摘要
- 漏洞分析结果
- VEX 评估结果
- 风险优先级清单
- 修复方案
- 审计日志（各阶段关键事件）

## 报告格式说明

### 格式1：Markdown 报告（人类可读）

面向安全分析师、开发人员、管理层阅读，结构清晰，带表格和分级展示。

**报告结构**：

```
# [项目名] SBOM漏洞分析报告

## 一、报告概览
- 报告编号、生成时间、分析范围
- 核心数据摘要（组件数、漏洞数、高危数、P0数）
- 整体风险评级

## 二、SBOM概览
- 组件总数
- 生态分布（Maven/npm/PyPI...）
- Top 10 组件（按漏洞数排序）

## 三、漏洞统计
- 按严重等级分布
- 按组件分布
- KEV漏洞清单
- 新增漏洞趋势（如果有历史数据）

## 四、VEX评估摘要
- 各状态数量（affected/not_affected/fixed/under_investigation）
- not_affected 典型案例及理由
- 待人工审核清单

## 五、修复优先级TOP 10
- 排名、CVE、组件、风险分、建议行动、预计修复时间

## 六、高危漏洞详情
- 每个P0/P1漏洞的详细信息
- 漏洞描述、影响、修复方案

## 七、修复方案总览
- 按优先级分组的修复建议
- 兼容性风险分布
- 总预估工作量

## 八、高危组合风险
- 识别到的高危风险组合及说明

## 九、审计日志
- 全流程关键节点记录
- 各阶段耗时、执行结果

## 附录
- 完整漏洞清单（表格）
- 完整修复方案清单
- 术语表
```

### 格式2：JSON 报告（结构化数据）

面向系统集成、自动化消费，字段完整、机器可读。

包含完整的结构化数据：
- 报告元数据（ID、时间、版本）
- SBOM 完整数据
- 漏洞完整列表（含所有维度评分）
- VEX 断言列表
- 优先级清单
- 修复方案列表
- 审计日志

### 格式3：PDF 报告（正式归档）

面向正式归档、合规审计、对外发布，带封面、目录、页眉页脚、水印。

> Demo 环境中，PDF 报告以"格式化 Markdown + PDF 导出说明"形式提供，或由平台工具转换生成。

## 报告质量标准

1. **数据一致性**：所有数字要对得上（总数=各部分之和）
2. **来源可追溯**：每个结论都要有依据和来源
3. **分级清晰**：用颜色、图标、标签等方式直观区分风险等级
4. **行动导向**：不仅告诉用户"有什么问题"，还要告诉"该怎么修、先修哪个"
5. **专业规范**：术语准确、格式统一、无错别字

## 处理步骤

### 第1步：数据聚合

收集所有阶段的输出数据，整理成统一的内部结构。

### 第2步：数据校验

检查数据一致性：
- 漏洞总数 = 各等级之和？
- VEX 状态数之和 = 漏洞总数？
- 优先级清单的漏洞是否都在漏洞列表中？
- 修复方案是否覆盖了所有漏洞？

发现不一致的地方，标记并尽量修正，无法修正的标注"数据待确认"。

### 第3步：生成 Markdown 报告

按报告结构生成 Markdown 格式报告：
- 用表格展示统计数据
- 用分级标题组织内容
- 用 emoji/颜色标记风险等级
- 关键信息加粗高亮

### 第4步：生成 JSON 报告

输出完整的结构化 JSON 数据，包含所有字段，供系统消费。

### 第5步：生成 PDF 报告（可选）

如果有 PDF 生成工具，将 Markdown 转换为带样式的 PDF：
- 添加封面（项目名、报告编号、日期、保密等级）
- 添加目录
- 添加页眉页脚（公司名、页码、报告编号）
- 添加水印（如"CONFIDENTIAL"）

### 第6步：生成审计日志摘要

整理全流程关键事件，形成审计日志：
- 各阶段开始/结束时间
- 关键决策和判定
- 异常事件（工具失败、数据异常等）
- 人工介入点

## 注意事项

- 报告是给**人看的**——要站在读者角度想："我看这份报告，最关心什么？" 别光堆数据，要有结论、有建议
- **数字要对账**——概览里说 23 个漏洞，后面加起来也要是 23。数字对不上是报告的硬伤，会让客户怀疑整个分析的可信度
- **优先级TOP 10是重点**——大部分人只看前10个，这部分要写得最清楚、最有行动指导性
- 修复方案要**可落地**——不能只说"升级到最新版"，要告诉升到哪个版本、有什么风险、预计多久
- 审计日志要**可追溯**——谁在什么时候做了什么决策、依据是什么，都要能查得到
- PDF 报告如果暂时生成不了，要诚实说明，别拿假的糊弄——可以提供"可打印的 Markdown + 导出指南"
- 报告里的术语要统一——不能一会儿说"严重"一会儿说"Critical"，要统一定义
