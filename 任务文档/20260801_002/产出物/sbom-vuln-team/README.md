# SBOM漏洞分析智能体团队

> 基于 AgentScope 2.0 架构 | 专家+Skill 混合模式
> 版本：v1.0.0
> 对齐文档：《SBOM分析平台多智能体协作体系规范文档》

---

## 一、这是什么？

这是一个 **SBOM 漏洞分析的多智能体团队**，采用「专家+Skill」混合模式：

- **5 位专家 Agent**——负责判断、分析、决策
- **8 个可复用 Skill**——负责标准化、流程化的操作
- **1 位编排主任**——负责统筹调度、质量审查、最终交付

打个比方——就像医院看病：
- 专家 Agent = 专科医生（心内科、神经内科、皮肤科…）
- Skill = 化验室/检查设备（抽血、X光、心电图…）
- 编排主任 = 门诊部主任（分诊、安排检查、汇总诊断、出报告）

## 五、工作流（五阶段管道式）

```
阶段1：SBOM解析
  ↓  创建 SBOM解析专家
  ↓  调用 excel-parser + sbom-generator
  ↓  主任审查 → 通过/退回补查（最多2轮）
阶段2：漏洞扫描
  ↓  创建 漏洞扫描专家
  ↓  调用 vuln-scanner（内部多工具并行）
  ↓  主任审查 → 通过/退回补查
阶段3：漏洞分析
  ↓  创建 漏洞分析专家
  ↓  调用 cve-analyzer
  ↓  主任审查 → 通过/退回补查
阶段4：风险评估
  ↓  创建 风险评估专家
  ↓  调用 vex-assessor + risk-calculator
  ↓  主任审查 → 通过/退回补查
阶段5：修复与报告
  ↓  创建 修复与报告专家
  ↓  调用 remediation-finder + report-builder
  ↓  主任审查 → 通过/退回补查
  ↓  最终交付
```

**特点**：
- **大管道、小并发**——整体是管道式串行，但扫描阶段内部是多工具并行
- **每阶段必审**——主任亲自把关，不合格退回重做
- **全流程可追溯**——每个阶段的输入输出都有记录

## 六、五维度风险评分算法

```
综合风险分 = 
  CVSS × 0.30 +      # 漏洞严重程度
  EPSS × 0.20 +      # 利用难易程度
  KEV × 0.20 +       # 是否已知在野利用
  VEX × 0.15 +       # 实际可达性
  业务影响 × 0.15    # 业务重要性
```

| 综合分 | 优先级 | 建议行动 |
|-------|--------|---------|
| ≥ 80 | P0 - 紧急 | 立即修复，24小时内 |
| 60 - 79 | P1 - 高 | 本周内修复 |
| 40 - 59 | P2 - 中 | 本迭代内修复 |
| 20 - 39 | P3 - 低 | 下个迭代修复 |
| < 20 | P4 - 可忽略 | 定期跟踪 |

## 八、关于模拟模式的说明

> ⚠️ 重要提示

本项目中的漏洞扫描、EPSS/KEV 关联、修复方案检索等能力为**知识驱动的模拟模式**，基于公开 CVE 知识库进行推理匹配。

**与真实生产环境的区别**：

| 能力 | Demo 模拟模式 | 真实生产环境 |
|:--|:--|:--|
| 漏洞扫描 | 基于知识库推理匹配 | 调用 Snyk/Trivy/OSV 等真实 API |
| EPSS 评分 | 典型值/推理值 | 实时查询 FIRST EPSS API |
| CISA KEV | 知识库中的已知条目 | 实时下载最新 KEV 目录 |
| 修复方案 | 基于公开安全公告推理 | 实时查询厂商安全公告 API |
| 系统集成 | 模拟调用/跳过 | 真实 Jira/Slack/Dependency-Track API |

**Demo 的核心价值**：
展示的是**多专家协作流程、工作流编排、质量审查机制、Skill 复用模式**，而不是扫描工具的准确性。
就像售楼处的样板间——展示的是户型设计、装修风格、空间布局，不是让你真的住进去。

## 九、导入智能体平台

### 核心文件：AGENTS.md（唯一必需）

**AGENTS.md 已包含五个角色的完整提示词**，AgentCreate 时直接传入。因此只需导入 AGENTS.md 作为主 Agent 提示词即可运行。

### 可选：上传 Skill 技能包

skills/ 目录下的 8 个 SKILL.md 可作为独立技能上传到平台，供其他场景复用。每个技能文件夹可打包为 SKILL.zip 上传。

### 导入顺序

1. **导入 AGENTS.md** → 作为主 Agent 系统提示词（唯一必需步骤）
   - AGENTS.md 的"角色库"章节包含五个角色的完整提示词
   - 主 Agent 通过 AgentCreate 将对应提示词直接传给子 Agent
   - 子 Agent 不需要额外绑定技能即可运行（Skill 逻辑写在专家提示词中）

2. （可选）上传 8 个 SKILL.zip 到平台技能库
   - 这些技能是独立的"标准作业程序"，可供其他安全项目复用
   - 本项目的 Agent 运行时**不依赖**这些技能文件

## 十一、与原 7 Agent 方案的对比

| 维度 | 原 7 Agent 管道式 | 专家+Skill 模式（本方案） |
|:--|:--|:--|
| 专家数量 | 7 个（全是Agent） | 5 个专家 Agent |
| Skill 数量 | 0（能力都写在Agent里） | 8 个可复用 Skill |
| 工作流 | 严格串行流水线 | 管道+并发混合 |

| 演示效果 | 流水线感强，节奏慢 | 有张有弛，专家会诊感强 |

## 十二、注意事项

- **TeamWait 是核心同步机制**：任务在 AgentCreate 时嵌入提示词，Worker 自主执行，Leader 通过 TeamWait 等待。禁止在 TeamWait 期间发 TeamSay 分配任务——那会扰乱 Worker 的 Session 状态。
- **主任审查是质量保障**：每个阶段主任都要亲自审查，不能偷懒跳过。审查维度：格式合规性、数据完整性、逻辑一致性、依据充分性、异常处理。
- **退回意见必须具体**：不能只说"不够全面"，必须包含具体问题（遗漏了什么）、具体位置（在哪里）、具体要求（需要补充什么）。
- **每阶段最多退回 2 轮**：超过 2 轮还不合格，说明问题比较复杂，需要人工介入了。
- **VEX 的 not_affected 要慎之又慎**：漏掉一个真实受影响的高危漏洞，后果很严重。拿不准的就标 under_investigation。
- **Skill 是工具不是 Agent**：不要为每个 Skill 创建单独的 Agent，那是浪费 token。Skill 是专家调用的工具，共享专家的上下文。
- 如果客户问"为什么是5个专家不是7个"，回答："原规范中的VEX生成和优先级排序都是风险评估范畴，放同一个专家更符合业务逻辑；修复建议和报告集成都属于交付阶段，放同一个专家更顺畅。这样既保证了职责清晰，又减少了Agent创建次数，提高了效率。"
- 如果客户问"扫描结果是真实的吗"，诚实回答："当前Demo版本是基于公开知识库的模拟扫描，主要展示多专家协作流程。生产环境可以接入Snyk、Trivy、OSV等真实扫描工具API，架构完全兼容。"
