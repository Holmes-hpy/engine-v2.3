# 两层Skill架构 vs 单层Skill架构：投入产出全面分析

> 版本：v1.0 | 日期：2026-07-30
>
> 本文档对"两层Skill架构（原子计算器层 + 上层应用层）vs 单层Skill架构（B类复合计算引擎直接嵌入模板）"的投入产出进行全面量化与定性分析，回答一个核心问题：**两层架构是否值得投入？**

---

## 零、前置约定

### 0.1 Token换算标准

本分析采用中文混合文本的实际换算率：

```
1KB ≈ 750 tokens
```

此换算率基于以下事实：中文混合文本（含Markdown格式、代码块、公式等）中，1个中文字符约占2-3 tokens，加上格式标记和代码，综合平均约750 tokens/KB。

### 0.2 架构定义

| 架构 | 定义 |
|------|------|
| **单层架构（v2.0.0原始状态）** | B类复合计算引擎直接嵌入公式，上层A类模板直接调用B类引擎。B类48个文件，每个12-13KB。 |
| **两层架构（当前拆分后）** | 新增"原子计算器层"（74个文件，平均3.6KB），上层A/C类模板通过 `composed_calculators` 和 `required_data` 字段引用计算器。 |

## 一、Token消耗对比（核心量化维度）

### 1.1 场景1：简单单指标计算（如"帮我算一下MRR"）

这是最典型的"轻量级使用"场景，用户只需要一个具体数值。

| 对比维度 | 单层架构 | 两层架构 |
|---------|---------|---------|
| 加载文件 | 财务指标计算器（完整） | 财务-MRR计算器 |
| 文件大小 | 12.9 KB | 1.6 KB |
| Token消耗 | 12.9 × 750 = **9,675 tokens** | 1.6 × 750 = **1,200 tokens** |
| 加载内容 | MRR + ARR + NDR + LTV + CAC + 毛利率 + Runway（7个指标全加载） | 仅MRR一个指标 |

| 差额 | 两层架构节省 **8,475 tokens** |
|------|------|
| 节省比例 | **87.6%** |

**结论：场景1下，两层架构碾压式胜出。** 单层架构的"一颗老鼠屎坏一锅粥"问题——用户只想算MRR，却被迫加载7个指标的全部公式和逻辑——被两层架构完美解决。

---

### 1.2 场景2：复杂多指标分析（如"给我做一份完整的SaaS财务分析报告"）

需要加载17个指标：MRR、ARR、NDR、LTV、CAC、毛利率、Runway、DCF、可比估值、分部加总、Beta、VaR、夏普比率、最大回撤、WACC、ROE、ROI。

#### 单层架构

| 加载文件 | 大小 | 覆盖指标 |
|---------|------|---------|
| 财务指标计算器（B1） | 12.9 KB | MRR、ARR、NDR、LTV、CAC、毛利率、Runway |
| 估值计算引擎（B2） | 9.3 KB | DCF、可比公司、分部加总 |
| 风险量化计算器（B3） | 12.0 KB | Beta、VaR、夏普比率、最大回撤 |
| 融资测算工具（B38） | ~10.0 KB | WACC、ROE、ROI（内嵌公式） |
| **合计** | **44.2 KB** | |

Token消耗：44.2 × 750 = **33,150 tokens**

#### 两层架构

| 加载文件 | 数量 | 大小 |
|---------|------|------|
| 17个原子计算器 | 17 × 3.6 KB = 61.2 KB |  |
| 上层模板（含composed_calculators + required_data） | 1 | ~18.0 KB |
| **合计** | **79.2 KB** | |

Token消耗：79.2 × 750 = **59,400 tokens**

| 差额 | 两层架构多消耗 **26,250 tokens** |
|------|------|
| 增幅 | **+79.2%** |

**结论：场景2下，两层架构严重吃亏。** 复杂的多指标分析需要加载几乎所有相关计算器，而单层架构的B类引擎恰好"打包"了对这些指标的支持。两层架构的拆分粒度反而成了累赘——每个计算器文件的元数据开销（文件头、注册信息、Markdown格式）在批量加载时被放大了17倍。

---

### 1.3 场景3：中等复杂度（如"给这个商品做动态定价方案"）

| 对比维度 | 单层架构 | 两层架构 |
|---------|---------|---------|
| 加载内容 | 动态定价方案模板（公式已inline） | 模板（去掉公式）+ 3个计算器 + required_data |
| 文件大小 | 10.9 KB | 7.0 + 3×3.6 + 1.0 = 18.8 KB |
| Token消耗 | 10.9 × 750 = **8,175 tokens** | 18.8 × 750 = **14,100 tokens** |

| 差额 | 两层架构多消耗 **5,925 tokens** |
|------|------|
| 增幅 | **+72.5%** |

**结论：场景3下，两层架构同样吃亏。** 中等复杂度场景恰好是大部分实际使用场景——用户需要的是一个"方案"，而不是孤立的计算。单层架构的模板化设计让公式随模板一起加载，恰好契合了这种需求模式。

---

### 1.4 三场景汇总

| 场景 | 单层 tokens | 两层 tokens | 差额 | 胜者 |
|------|-----------|-----------|------|------|
| 场景1：简单单指标 | 9,675 | 1,200 | **-8,475（-87.6%）** | 两层 |
| 场景2：复杂多指标 | 33,150 | 59,400 | **+26,250（+79.2%）** | 单层 |
| 场景3：中等复杂度 | 8,175 | 14,100 | **+5,925（+72.5%）** | 单层 |

**关键洞察：两层架构仅在"简单单指标"场景胜出，在"中等复杂度"和"复杂多指标"场景均显著吃亏。** 而实际业务中，用户很少仅仅问"帮我算一下MRR"（这个需求用计算器即可），更多时候是要"做一份定价方案"、"写一份财务分析报告"——这些场景恰好是两层架构的劣势场景。

---

### 1.5 Token消耗的"临界点"分析

两层架构的额外开销来自两个固定成本：
1. **上层模板的 `composed_calculators` + `required_data` 字段**：约3KB/模板
2. **每个计算器文件的元数据开销**：约1KB/个（文件头、注册信息、Markdown格式标记）

因此，两层架构的Token消耗公式为：

```
两层Token = 模板(去公式后) + N × 3.6KB + 3KB(composed_calculators)
单层Token = 模板(含公式inline) = 模板(去公式后) + N × 公式大小
```

其中，N为需要加载的计算器数量。单层架构中公式嵌入的"边际成本"约为每个指标1.0-1.5KB（共享文件头），而两层架构中每个计算器的"边际成本"为3.6KB（独立文件头）。

**临界点计算**：当 N=1 时，两层架构因"按需加载"节省了未使用指标的开销，胜出。但当 N>=2 时，两层架构的独立文件头开销开始累积，逐步劣势。

这意味着，**两层架构仅在"用户只需要1个指标"时有利，而实际业务中绝大多数场景需要2个以上指标的协同输出**。

## 二、管理成本对比（核心定性维度）

### 2.1 文件数量变化

| 架构 | 文件数 | 说明 |
|------|--------|------|
| 单层 | 223 | A78 + B48 + C39 + D28 + E20 + F10 |
| 两层 | 221 | 74计算器 + A78 + C39 + E20 + F10 |

**分析**：文件数量几乎持平（223 vs 221），仅减少2个。看似"没增加复杂度"，但文件结构发生了根本性变化——从"平铺"变成了"两层嵌套"。维护者需要同时理解两个层级的关系。

### 2.2 跨文件引用关系

两层架构新增了 **200+个跨层引用关系**：

| 引用方向 | 数量估算 | 说明 |
|---------|---------|------|
| 上层Skill → 计算器注册中心 | 147条 | 每个上层Skill需要查询注册中心 |
| 上层Skill → 概念注册表 | 147条 | 每个上层Skill通过 `required_data` 引用概念 |
| 计算器 → 概念注册表 | 74条 | 每个计算器的 `formula_reference` 指向概念注册表 |
| 计算器 → 计算器依赖 | ~10条 | 如ARR依赖MRR，WACC依赖Beta |
| **合计** | **~380条引用关系** | |

单层架构的引用关系：A类模板 → B类引擎，约100条（一个模板通常引用1-4个B类引擎）。

**引用关系爆炸式增长：从~100条 → ~380条，增幅约3.8倍。**

任何一次计算器改名、删除、合并，都需要同步更新所有引用它的上层Skill。这是一个"牵一发而动全身"的维护负担。

### 2.3 新增基础设施文档

两层架构新增了2个核心基础设施文档：

| 文档 | 说明 | 维护频率 |
|------|------|---------|
| 概念注册表（concept_registry） | 所有公式的权威来源，69个概念 | 低（概念定义不常变） |
| 计算器注册中心（calculator_registry） | 所有计算器的索引，74个条目 | 中（新增/修改计算器时更新） |

这两个文档本身不大（概念注册表约9KB，注册中心约10KB），但它们构成了额外的"一致性维护负担"——每次新增计算器，必须同时更新注册中心（添加条目 + 更新 `被引用` 列表），并检查概念注册表是否需要新增概念。

单层架构不需要这些基础设施，因为B类引擎本身就是"自包含"的——公式、计算逻辑、文档都在一个文件里。

### 2.4 公式修改成本

| 场景 | 单层架构 | 两层架构 |
|------|---------|---------|
| 公式本身修改 | 需要逐个检查所有引用了该公式的B类引擎和A类模板，可能遗漏 | 只需修改概念注册表 + 对应计算器（1处），但需确认所有上层Skill的兼容性 |
| 新增一个公式 | 在B类引擎中写一段代码即可 | 创建新计算器文件 → 注册中心添加条目 → 概念注册表添加公式 → 上层Skill添加引用 |
| 删除一个公式 | 从B类引擎中删除代码段 | 删除计算器文件 → 注册中心删除条目 → 清理所有上层Skill的引用 |

**两层架构的"改一处生效"优势被夸大了。** 现实情况是：公式修改后，所有引用该计算器的上层Skill都需要回归验证——因为上层Skill的 `required_data` 字段预设了计算器的输入输出格式，任何公式变更都可能导致数据传递断裂。实际修改成本与单层架构相当，但多了一层"注册表同步"的额外负担。

### 2.5 新增Skill成本

| 步骤 | 单层架构 | 两层架构 |
|------|---------|---------|
| 1 | 确定需要的指标 | 确定需要的指标 |
| 2 | 直接写公式或嵌入B类引擎 | 查询注册中心，确认是否有现成计算器 |
| 3 | 完成 | 若有：引用计算器，配置 `composed_calculators` |
| 4 | — | 若无：创建新计算器 → 注册中心 → 概念注册表 → 再引用 |
| 5 | — | 完成 |

**两层架构新增一个Skill的步骤从2步增加到4-5步。** 而且步骤2（查询注册中心）是"阻塞性"的——如果找不到现成计算器，必须先创建计算器，再回来写上层Skill。这种"来回切换"的开发体验，会显著降低开发效率。

我主观认为，这种"先查再用"的流程在团队协作中尤其痛苦——当多个开发者同时新增Skill时，注册中心会成为竞争热点，需要额外的协调成本。

## 五、魔鬼代言人：为两层架构辩护

在给出结论前，让我们站在"两层架构支持者"的角度，看看还有哪些有利论据没有被前面的量化分析覆盖。

### 5.1 概念一致性的"隐性收益"

两层架构最大的不可量化收益是**概念一致性**。在单层架构中，同一个概念（如"毛利率"）可能在A42中定义为 `(收入-成本)/收入`，在A17中定义为 `(售价-进货价-平台扣点)/售价`，两个公式语义不同但名称相同，这是bug的温床。

概念注册表强制要求"每个概念只有一个定义，变体必须显式区分"，这确实消除了这一类隐患。

**但问题是**：这个收益不依赖于两层架构。即使在单层架构中，也可以引入概念注册表作为"公式权威来源"——B类引擎的公式引用注册表，模板直接引用B类引擎。概念注册表是独立于架构层的"正交基础设施"。

### 5.2 未来扩展性的"期权价值"

当前74个计算器平均复用率仅1.14，但如果未来上层Skill数量增长到300+，复用率可能提升到2.0以上，届时两层架构的优势才会显现。

**但问题是**：这个"期权"需要现在就支付成本（380条引用关系、2个注册文档、每次新增Skill的4-5步流程），而"行权"时间不确定。如果上层Skill数量在可预见的未来（1-2年）不会翻倍，那这个期权就是负EV的。

### 5.3 团队协作的"分治"优势

两层架构允许"计算器开发"和"上层Skill开发"由不同角色并行进行。计算器开发者专注于公式正确性，上层Skill开发者专注于业务逻辑和模板结构。

**但问题是**：当前团队规模下，这种"分治"是否有必要？如果团队只有2-3人，且每个人既写计算器又写上层Skill，那"分治"的优势就退化为"自己和自己分工"的形式主义。

## 六、结论与建议

### 6.1 核心结论

**两层架构在当前的Skill数量和复用率下，投入产出比为负。**

具体来说：
- Token消耗：3个场景中2个吃亏，1个占优，且占优场景（简单单指标）在实际业务中占比很低
- 管理成本：引用关系膨胀3.8倍，新增2个基础设施文档，新增Skill步骤翻倍
- 复用收益：平均复用率仅1.14，远低于有效阈值2.0
- 文件数量：几乎持平，不构成差异化因素

两层架构的唯一明确优势（简单场景Token节省87.6%）被两个劣势（中等场景+72.5%、复杂场景+79.2%）完全抵消，且这三个劣势场景恰好是实际业务的高频场景。

### 6.2 建议方案：折中方案——"选择性保留两层"

**不建议全量回退到单层，也不建议全量保留两层。** 推荐以下折中方案：

#### 保留两层的领域（高复用潜力）

| 领域 | 保留理由 | 保留计算器 |
|------|---------|----------|
| **财务-SaaS指标** | 7个计算器（MRR/ARR/NDR/LTV/CAC/毛利率/Runway）被A42和A43两个模板同时引用，是唯一复用率 > 1.5 的计算器组 | MRR、ARR、NDR、LTV、CAC、毛利率、Runway（7个） |
| **财务-估值** | DCF/可比公司/分部加总被A43引用，且估值方法具有通用性，未来可能被更多上层Skill引用 | DCF、可比公司、分部加总（3个） |
| **数据-通用分析** | 趋势分析器被A31和A39引用（复用2次），信息源可信度被A39和A34引用（复用2次） | 趋势分析器、信息源可信度分级器（2个） |

**保留总计：12个计算器（占74个的16.2%）**

#### 回退单层的领域（低复用）

| 领域 | 回退理由 | 计算器数量 |
|------|---------|----------|
| 风险 | 5个计算器，仅被A43引用1次 | 5 |
| 电商 | 10个计算器，各被1个模板引用 | 10 |
| 供应链 | 9个计算器，各被1个模板引用 | 9 |
| 物流 | 2个计算器，各被1个模板引用 | 2 |
| 工程 | 4个计算器，各被1个模板引用 | 4 |
| 测试 | 7个计算器，各被1个模板引用 | 7 |
| 教育 | 3个计算器，各被1个模板引用 | 3 |
| 法律 | 5个计算器，各被1个模板引用 | 5 |
| 产品/增长 | 3个计算器，各被1个模板引用 | 3 |
| 咨询 | 1个计算器，被1个模板引用 | 1 |
| HR | 1个计算器，被1个模板引用 | 1 |
| 算法引擎 | 1个计算器，被1个模板引用 | 1 |
| 财务-低复用 | 有效税率、贷款资格预审、稀释、估值锚定、ROE、ROI、WACC（各被1个模板引用） | 7 |

**回退总计：62个计算器（占74个的83.8%）**

#### 回退方式

将62个计算器的公式直接inline回对应的上层Skill模板中，删除独立计算器文件。具体操作：

1. 将公式从计算器文件提取出来，嵌入到引用它的上层Skill的 `formula` 或 `calculation_logic` 字段中
2. 从计算器注册中心删除该条目
3. 从概念注册表中保留概念定义（概念注册表本身是正交基础设施，可以保留）
4. 删除独立计算器文件

回退后的架构变为：

```
单层部分（62个计算器回退）：上层Skill直接包含公式，无独立计算器层
两层部分（12个保留）：上层Skill通过 composed_calculators 引用独立计算器
```

### 6.3 如果坚持保留两层架构，需要满足的条件

如果团队决定保留完整的两层架构，需要满足以下条件才能让投入产出比转正：

1. **上层Skill数量增长到当前的2倍以上**（从117个 → 250+个），使计算器复用率提升到 >= 2.0
2. **建立自动化工具**：开发一个"计算器引用检查器"，自动验证所有 `composed_calculators` 引用的有效性，消除人工维护380条引用关系的负担
3. **建立计算器缓存机制**：在Agent运行时层面，将多个计算器的加载合并为一次批量加载，减少场景2和场景3的Token开销
4. **团队规模 >= 5人**，且明确分工为"计算器开发"和"上层Skill开发"两个角色

在不满足上述条件的情况下，两层架构的维护成本将持续超过其收益。

### 6.4 最终建议

**推荐执行"选择性保留两层"方案（6.2节）。**

理由如下：
- 保留12个高复用计算器，享受两层架构的"改一处生效"优势
- 回退62个低复用计算器，消除81.6%的引用关系维护负担
- 概念注册表独立保留，继续提供概念一致性保障
- 架构复杂度大幅降低：从"全部两层"变为"少数两层 + 多数单层"

这个方案不是"非黑即白"的二元选择，而是承认一个事实：**不同领域的计算器，复用潜力天生不同，不应该用同一把尺子量。**
