# 原子计算器架构与完整执行方案（v2.0）

> 版本：v2.0 | 日期：2026-07-30
>
> 本文档是 v1.0 的全面修订版。基于魔鬼代言人深度评估和用户反馈，对以下内容做了重大调整：
> - 预估数据机制：从"独立注册表+六层防御"简化为"LLM实时估值+会话标记"
> - 元数据传播：从"运行时聚合"改为"迁移时固化到上层Skill"
> - 重点融入：维度7（公式一致性）、维度1（引用关系膨胀）、维度3（命名歧义）
> - 移除：预估数据注册表、版本管理相关内容
>
> 决策依据：用户确认采用纯原子计算器逻辑，先底层计算器后上层Skill，预估由LLM实时完成。

## 一、架构总览

### 1.1 为什么先做底层？

如果底层计算器的接口、参数、输出格式还没定好，上层Skill就只能"硬编码"计算逻辑，导致：

1. **重复造轮子**：同一个ROI公式出现在10个Skill中，改一处要改十处
2. **口径不一致**：两个Skill对"毛利率"的算法不同，结果矛盾
3. **无法复用**：上层Skill写死了计算逻辑，别的Skill无法单独调用

### 1.2 三层架构

```
┌─────────────────────────────────────────────────────────────────┐
│  L3: 上层应用层（用户直接调用）                                    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐           │
│  │A类-模板  │ │C类-框架  │ │E类-清单  │ │F类-代码  │           │
│  │ 78个     │ │ 39个     │ │ 20个     │ │ 10个     │           │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘           │
│       │            │            │            │                  │
│       └────────────┴────────────┴────────────┘                  │
│                          │                                       │
│              调用底层计算器 + 声明数据依赖                          │
│                          │                                       │
├──────────────────────────┼───────────────────────────────────────┤
│  L2: 数据与知识层                                                │
│  ┌──────────────────────────────────────────┐                    │
│  │ D类-知识库（28个）                         │                    │
│  │ 领域知识/规则查询，不调用计算器             │                    │
│  └──────────────────────────────────────────┘                    │
│                                                                   │
├───────────────────────────────────────────────────────────────────┤
│  L1: 原子计算器层（基础设施）                                      │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐       │
│  │财务计算│ │风险计算│ │电商计算│ │工程计算│ │通用计算│  ...   │
│  │  ~15个 │ │  ~5个  │ │  ~8个  │ │  ~6个  │ │  ~10个 │       │
│  └────────┘ └────────┘ └────────┘ └────────┘ └────────┘       │
│                                                                   │
│  每个原子计算器 = 一个纯函数：输入→计算→输出                        │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 关键设计原则

| 原则 | 说明 |
|------|------|
| **单向依赖** | L3→L1，禁止L1→L3、L1→L2 |
| **计算器纯函数化** | 输入参数 + 计算公式 + 输出结果，无副作用 |
| **数据弹性** | 用户可提供全部/部分/不提供数据，缺失数据由LLM实时估值 |
| **预估透明** | 预估数据仅在会话中标注，不写入最终文档 |
| **数据依赖固化** | 上层Skill的 `required_data` 在本次迁移中一次性写入 |

## 二、原子计算器定义

### 2.1 判定标准

| 维度 | 判定标准 | 是原子 | 是复合 |
|------|---------|--------|--------|
| **输入原子性** | 输入是一组同质参数，不依赖其他计算器输出 | 毛利率计算器：收入+成本 | 企业估值：需要DCF+可比公司 |
| **输出单一性** | 输出一个明确的计算结果 | 安全库存量 | 同时输出MRR/ARR/NDR/LTV/CAC |
| **公式独立性** | 使用一组紧密关联的公式，不涉及方法选择 | ROE = 净利润÷净资产 | 需求预测：ARIMA/指数平滑/促销增量三选一 |
| **领域内聚性** | 属于一个明确的计算领域 | 齿轮强度计算器 | 仪表盘类（跨多领域） |

### 2.2 拆分规则

| 触发条件 | 处理方式 |
|---------|---------|
| 一个Skill输出多个不相关指标 | 每个指标拆为一个独立计算器 |
| 一个Skill包含多种计算方法 | 每种方法拆为一个独立计算器 |
| 一个Skill是"仪表盘/看板"类 | 拆为底层计算器组合，原Skill重新归类为C类 |

### 2.3 原子计算器标准格式

```markdown
## name
[领域前缀]-[计算器名称]
# 示例：财务-MRR计算器、风险-VaR计算器、电商-利润测算器

## description
[计算功能描述] + [适用场景] + [触发词] + [排除词]
# 注意：description必须包含触发词和排除词，以降低维度3（命名歧义）风险

## category
atomic-calculator

## sub_category
[财务/风险/电商/供应链/工程/测试/教育/法律/通用/...]

## domain  ← 新增：解决维度7（公式一致性）
[本计算器所属领域，用于概念注册表校验]
# 示例：财务-通用、财务-SaaS、电商-平台、机械工程

## formula_reference  ← 新增：解决维度7（公式一致性）
[引用概念注册表中的公式定义]
# 示例：concept_registry.毛利率.财务通用

## inputs
### 必填参数（无默认值，用户必须提供）
| 参数名 | 类型 | 说明 | 示例 |
|--------|------|------|------|

### 可选参数（用户可提供，不提供则LLM估值）
| 参数名 | 类型 | 说明 | 估值逻辑 |
|--------|------|------|---------|
# 估值逻辑：描述LLM应如何估算该参数（如"查询当前市场数据"、"按行业均值估算"、"按历史趋势推算"）

## formula
[计算公式，使用数学符号]

## output
| 字段名 | 类型 | 说明 |
|--------|------|------|

## example
[一个完整计算示例，包含输入和输出]
```


## 三、数据弹性与预估机制（简化版）

### 3.1 设计原则

> 不再维护独立的"预估数据注册表"。预估由LLM在每次调用时实时完成。
> 原则：有MCP查市场数据就用，查不到就基于逻辑估值，会话中标记，文档中不体现。

### 3.2 参数两级分级

```
┌──────────────────────────────────────────────────────┐
│              启动Skill                                 │
│                      ↓                                 │
│  ┌──────────────────────────────────────────────┐    │
│  │  展示数据需求（读取 required_data 字段）        │    │
│  │                                                │    │
│  │ ● 必填数据：月付费客户数、ARPU、期初ARR...      │    │
│  │ ○ 可选数据：行业平均MRR、行业平均LTV...         │    │
│  │                                                │    │
│  │ [开始计算] [跳过可选数据，全部使用估值]          │    │
│  └──────────────────────────────────────────────┘    │
│                      ↓                                 │
│  ┌──────────────────────────────────────────────┐    │
│  │  用户选择：                                    │    │
│  │  A. 提供全部数据                               │    │
│  │  B. 提供部分数据，其余估值                      │    │
│  │  C. 全部使用估值                               │    │
│  └──────────────────────────────────────────────┘    │
│                      ↓                                 │
│  ┌──────────────────────────────────────────────┐    │
│  │  LLM估值（仅对缺失的可选参数）：                │    │
│  │  1. 尝试MCP查询市场数据（如有）                 │    │
│  │  2. 基于逻辑推算（行业均值/历史趋势/经验公式）   │    │
│  │  3. 查不到也算不出 → 标记"无法估值"            │    │
│  └──────────────────────────────────────────────┘    │
│                      ↓                                 │
│  ┌──────────────────────────────────────────────┐    │
│  │  执行计算 + 会话中标注预估项                    │    │
│  │  "ROE = 15.2%（其中行业ROE=12%为预估值）"      │    │
│  └──────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────┘
```

### 3.3 预估标记规则（仅会话中）

| 数据类型 | 会话标记 | 是否写入文档 |
|---------|---------|-------------|
| 用户提供 | 无标记 | 正常写入 |
| MCP查到 | `（数据来源：MCP查询）` | 不写入 |
| LLM逻辑估值 | `（⚠️ 预估值，基于XX逻辑）` | 不写入 |
| 无法估值 | `（❌ 无法估值，原因：XX）` | 标注"数据缺失" |

### 3.4 可选参数的估值逻辑

每个原子计算器的可选参数必须写明估值逻辑，LLM据此实时估值：

```markdown
## inputs
### 可选参数（用户可提供，不提供则LLM估值）
| 参数名 | 类型 | 说明 | 估值逻辑 |
|--------|------|------|---------|
| 行业平均ROE | number | 同行业ROE均值 | ①MCP查询Wind/东方财富行业ROE数据；②无MCP时按行业类型估算（制造业8-12%，金融业10-15%，科技业5-10%） |
| 无风险利率 | number | 当前无风险利率 | ①MCP查询最新国债收益率；②无MCP时按3.0%估算 |
| 月流失率 | number | SaaS客户月流失率 | ①按公司规模估算（初创5-8%，成长期3-5%，成熟期1-3%）；②无规模信息时按5%估算 |
```

## 四、维度7：公式一致性（重点融入）

### 4.1 问题本质

> 56个原子计算器由不同人（或不同时间）编写，同一概念可能出现不同公式。"毛利率"在财务领域是 `(收入-成本)/收入`，在电商领域可能是 `(售价-进货价-平台扣点)/售价`。两个计算器都叫"毛利率"但公式不同，上层Skill调用时产生矛盾结果。

### 4.2 解决方案：概念注册表

在本次迁移中，创建一个独立的"概念注册表"文档，作为所有计算器的公式权威来源：

```
概念注册表结构：

┌─────────────────────────────────────────────────────────────┐
│  概念注册表（concept_registry）                              │
│                                                              │
│  1. 财务通用概念                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 毛利率 = (收入 - 成本) / 收入                          │   │
│  │   ├─ 变体：电商毛利率 = (售价 - 进货价 - 平台扣点) / 售价│   │
│  │   └─ 使用计算器：财务-毛利率计算器、电商-利润测算器       │   │
│  │                                                        │   │
│  │ ROI = 净收益 / 投资成本                                 │   │
│  │   ├─ 变体：项目ROI = (收益 - 成本) / 成本               │   │
│  │   └─ 使用计算器：财务-ROI计算器、项目管理-组合ROI计算器  │   │
│  │                                                        │   │
│  │ ROE = 净利润 / 净资产                                   │   │
│  │   └─ 使用计算器：财务-ROE计算器（待创建）               │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  2. SaaS指标概念                                             │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ MRR = 付费客户数 × ARPU                                │   │
│  │   └─ 使用计算器：财务-MRR计算器                         │   │
│  │                                                        │   │
│  │ NDR = (期初ARR + 扩张 - 收缩 - 流失) / 期初ARR         │   │
│  │   └─ 使用计算器：财务-NDR计算器                         │   │
│  │                                                        │   │
│  │ LTV = ARPU × 毛利率 / 月流失率                         │   │
│  │   └─ 使用计算器：财务-LTV计算器                         │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  3. 风险管理概念                                             │
│  4. 供应链概念                                               │
│  5. ...（按领域展开）                                        │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 一致性校验规则

在编写原子计算器时，必须满足：

1. **每个计算器的 `formula_reference` 必须指向概念注册表中的条目**
2. **如果概念注册表中无对应条目，需先在注册表中新增**
3. **同一概念的不同领域变体，必须在注册表中明确区分**
4. **代码审查时检查：同一概念是否出现两个不同公式**

**魔鬼追问**：概念注册表会不会变成另一个"预估数据注册表"——需要持续维护的负担？

**答**：不会。概念注册表是"定义文档"而非"数据中心"。定义不会频繁变化（毛利率的定义几十年不变），只需要在新增计算器时检查是否有冲突。维护成本极低，且只需要在本次迁移中一次性建立。

## 五、维度1：引用关系膨胀（重点融入）

### 5.1 问题本质

> 拆分后从223个到约235个，绝对数量增长不大（5.4%），但新增了 ~200+ 个跨层引用关系（上层Skill → 原子计算器）。开发者可能不知道某个计算器已经存在，又自己写一套计算逻辑，导致重复。

### 5.2 解决方案：计算器注册中心（INDEX文档）

在本次迁移中，创建一个"计算器注册中心"索引文档。所有上层Skill开发者在引用计算器之前，必须先查注册中心：

```
计算器注册中心结构：

┌─────────────────────────────────────────────────────────────┐
│  计算器注册中心（calculator_registry）                       │
│                                                              │
│  【财务领域】                                                │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 财务-MRR计算器                                        │   │
│  │   输入：月付费客户数、ARPU                             │   │
│  │   输出：MRR                                           │   │
│  │   被引用：财务分析报告模板、SaaS健康度仪表盘、...       │   │
│  │                                                       │   │
│  │ 财务-ARR计算器                                        │   │
│  │   输入：MRR（从MRR计算器获取）                         │   │
│  │   输出：ARR                                           │   │
│  │   被引用：财务分析报告模板、融资测算工具、...           │   │

│  │   输出：NDR                                           │   │
│  │   ...                                                 │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  【风险领域】                                                │
│  【电商领域】                                                │
│  【供应链领域】                                              │
│  ...（按领域展开）                                           │

```

### 5.3 新增计算器的流程

```
开发者想创建新计算器
    ↓
查"计算器注册中心" → 已存在？→ 复用现有，不新建
    ↓ 不存在
查"概念注册表" → 公式已定义？→ 引用注册表条目
    ↓ 未定义
先在概念注册表中新增公式定义
    ↓
创建新计算器，写入 formula_reference
    ↓
在计算器注册中心注册
    ↓
上层Skill引用时，从注册中心查名称
```

## 六、维度3：命名歧义（重点融入）

### 6.1 问题本质

> 56个计算器中，可能出现"看起来差不多"的。Agent动态检索时，把"组合ROI计算器"当成"财务ROI计算器"使用，结果完全错误。

### 6.2 解决方案：三层防歧义机制

#### 第一层：领域前缀命名

所有计算器名称强制使用 `领域-名称` 格式：

```
✅ 正确：财务-MRR计算器、风险-VaR计算器、电商-利润测算器
❌ 错误：MRR计算器、VaR计算器、利润测算器
```

#### 第二层：description 包含触发词和排除词

```markdown
## description
计算单个投资项目的财务ROI（投资回报率=净收益/投资成本）。
适用于：单一项目、单一投资决策。
不适用于：多项目组合、IT项目组合、风险调整后ROI。
触发词：ROI、投资回报率、单项目、投资回报
```

**触发词和排除词的作用**：Agent动态检索时，语义匹配会同时命中触发词和排除词，让Agent意识到"这个计算器可能不是我要的"。

#### 第三层：Agent确认步骤

在Agent v2.0提示词中增加"计算器选择确认"规则：

```
当有多个候选计算器时（如同时检索到"财务-ROI计算器"和"项目管理-组合ROI计算器"），
必须先向用户确认：
"检测到多个匹配的计算器：
 1. 财务-ROI计算器（适用于单个投资项目的财务回报率计算）

 请问您需要哪个？"
```

### 6.3 歧义场景预检表

在本次迁移中，需要对以下高风险歧义场景逐一检查：

| 歧义场景 | 计算器A | 计算器B | 歧义原因 | 处理方式 |
|---------|--------|--------|---------|---------|
| ROI歧义 | 财务-ROI计算器 | 项目管理-组合ROI计算器 | 都叫"ROI"但适用范围不同 | 领域前缀+description排除词 |
| 毛利率歧义 | 财务-毛利率计算器 | 电商-利润测算器 | 都涉及"毛利率"但公式不同 | 概念注册表区分+领域前缀 |
| 估值歧义 | DCF估值器 | 可比公司估值器 | 都是"估值"但方法不同 | 名称精确化+description触发词 |
| 覆盖率歧义 | 代码覆盖率计算器 | 功能覆盖率计算器 | 都叫"覆盖率" | 领域前缀+名称精确化 |
| 预测歧义 | ARIMA预测器 | 指数平滑预测器 | 都是"预测"但方法不同 | 名称精确化+description排除词 |

### 步骤0: 创建基础文档（预计1小时）

**产出物**：
- `09-概念注册表.md`：公式权威来源，按领域定义所有概念
- `10-计算器注册中心.md`：所有原子计算器的索引，包含名称、输入、输出、被引用列表

**为什么步骤0在步骤1之前？**
概念注册表定义了"什么概念用什么公式"，计算器注册中心定义了"哪些计算器已经存在"。两个文档先建立，后续编写计算器和上层Skill时才有据可查——这是维度7和维度1的前置条件。

### 步骤1: 梳理原子计算器最终清单（预计2-3小时）

**产出物**：`11-原子计算器最终清单.md`

**详细操作**：
1. 确认27个"已是原子"的计算器，分配领域前缀
2. 拆分8个复合计算器，每个拆分后定义名称、输入、公式、输出
3. 拆分8个仪表盘/看板，识别独立计算
4. 处理5个待讨论计算器
5. 检查上层Skill中是否还有"隐性计算"需要提取
6. 输出最终清单，按领域分组

### 步骤2: 编写原子计算器Skill文件（预计4-6小时）

**产出物**：`Skills_v2.1.0/calculators/` 目录下的56个Skill文件

**优先级**：
- 第一批（高优先级）：财务类（MRR、ARR、NDR、LTV、CAC、DCF、可比估值等）
- 第二批（中优先级）：风险类、电商类、供应链类
- 第三批（低优先级）：工程类、教育类、法律类、测试类

**每个Skill文件必须包含**：
- 领域前缀命名
- formula_reference 引用概念注册表
- description 包含触发词和排除词
- 可选参数的估值逻辑
- 完整计算示例

### 步骤3: 重构上层Skill（预计3-4小时）

**产出物**：更新后的A类/C类/E类/F类Skill文件（版本号2.1.0）

**核心变更**：
1. 识别硬编码计算逻辑 → 替换为引用原子计算器
2. 新增 `composed_calculators` 字段 → 声明依赖的计算器
3. 新增 `required_data` 字段 → 固化数据依赖（本次迁移一次性写入，含去重）
4. 去重规则：同一参数出现在多个计算器时，在 `required_data` 中只列一次，标注"所属计算器"列表

**⚠️ 关键提醒**：`required_data` 的编写是本次迁移的核心工作量。需要逐个上层Skill分析其依赖的计算器，汇总所有参数，去重后写入。这不是运行时动态聚合，而是迁移时人工整理。

### 步骤4: 更新Agent v2.0提示词（预计1-2小时）

**产出物**：更新后的86个Agent v2.0提示词

**核心变更**：
1. 更新可调用的计算器列表（旧B类名称 → 新领域前缀名称）
2. 增加"计算器选择确认"规则（维度3第三层防歧义）
3. 更新静态绑定和动态检索配置

### 步骤5: 更新平台需求文档（预计0.5小时）

**产出物**：`06-平台需求文档-Skill版本管理机制.md` 补充

**新增内容**：L7-Skill间调用需求（参数聚合引擎、依赖链执行、结果注入、优雅降级）

### 步骤6: GitHub提交

**产出物**：GitHub仓库提交
