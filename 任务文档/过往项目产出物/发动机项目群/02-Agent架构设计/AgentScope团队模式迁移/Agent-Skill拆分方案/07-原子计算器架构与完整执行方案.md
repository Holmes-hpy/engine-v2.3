# 原子计算器架构与完整执行方案

> 版本：v1.0 | 日期：2026-07-30
>
> 本文档定义原子计算器架构的完整设计方案，包含三层Skill架构、数据弹性机制、原子计算器拆分规则，以及详细的执行步骤。
> 决策依据：用户确认采用纯原子计算器逻辑（非混合方案），且执行顺序为"先底层计算器→后上层Skill"。

---

## 一、架构总览：三层Skill架构

### 1.1 为什么先做底层？

> **地基不牢，上层建筑就是空中楼阁。**

底层计算器是纯函数——输入确定、输出确定、无副作用。上层Skill（模板、框架、检查清单）本质上是"编排层"，它们调用底层计算器来完成具体计算。如果底层计算器的接口、参数、输出格式还没定好，上层Skill就只能"硬编码"计算逻辑，这会导致：

1. **重复造轮子**：同一个ROI计算公式出现在10个上层Skill中，每次修改都要改10个地方
2. **口径不一致**：两个Skill对"毛利率"的计算方式可能不同，导致结果矛盾
3. **无法复用**：上层Skill写死了计算逻辑，别的Skill无法单独调用这个计算器

### 1.2 三层架构

```
┌─────────────────────────────────────────────────────────────────┐
│  L3: 上层应用层（用户直接调用）                                    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐           │

│  └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘           │
│       │            │            │            │                  │
│       └────────────┴────────────┴────────────┘                  │
│                          │                                       │
│                    调用底层计算器                                  │
│                          │                                       │
├──────────────────────────┼───────────────────────────────────────┤
│  L2: 数据与知识层                                                │
│  ┌──────────────────┐ ┌──────────────────┐                      │
│  │D类-知识库 28个   │ │预估数据注册表(NEW)│                     │
│  │(领域知识/规则)   │ │(行业基准值/默认值)│                     │
│  └────────┬─────────┘ └────────┬─────────┘                      │
│           │                    │                                  │

│           │                    │                                  │
├───────────┼────────────────────┼──────────────────────────────────┤

│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐       │

│  │  ~15个 │ │  ~8个  │ │  ~6个  │ │  ~5个  │ │  ~8个  │       │

│  每个原子计算器 = 一个纯函数：输入→计算→输出                        │
│  不依赖其他Skill，可被任意上层Skill独立调用                         │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 三层调用关系

- **L1 原子计算器**：纯函数，不调用任何Skill（只使用数学/统计公式）
- **L2 数据与知识库**：提供数据查询，不调用计算器
- **L3 上层应用**：调用L1计算器获取计算结果，调用L2知识库获取参考数据
- **预估数据注册表**（L2新增）：当用户未提供数据时，L1计算器从此处获取行业基准值/默认值

### 1.4 关键设计原则

| 原则 | 说明 |
|------|------|
| **单向依赖** | L3→L1、L3→L2，禁止L1→L3、L2→L3 |
| **计算器纯函数化** | 每个原子计算器 = 输入参数 + 计算公式 + 输出结果，无副作用 |
| **数据弹性** | 计算器不强制要求用户提供全部数据，缺失数据从预估数据注册表获取 |
| **置信度透明** | 预估数据参与计算时，输出结果必须标注置信度 |
| **版本独立** | 每个计算器独立版本管理，修改不影响其他计算器 |

## 二、原子计算器定义

### 2.1 什么是原子计算器？

**原子计算器 = 一个不可再拆分的、独立可复用的计算单元。**

判定标准（四维度）：

| 维度 | 判定标准 | 示例（是原子） | 反例（是复合） |
|------|---------|--------------|--------------|
| **输入原子性** | 输入是一组同质参数，不依赖其他计算器输出 | 毛利率计算器：输入收入+成本 | 企业估值计算器：需要用DCF计算器+可比公司计算器 |
| **输出单一性** | 输出一个明确的计算结果，而非多项不相关结果 | 安全库存计算器：输出安全库存量 | 财务指标计算器：同时输出MRR/ARR/NDR/LTV/CAC |
| **公式独立性** | 使用一个或一组紧密关联的公式，不涉及方法选择 | ROE计算器：净利润÷净资产 | 需求预测计算器：ARIMA/指数平滑/促销增量三选一 |
| **领域内聚性** | 属于一个明确的计算领域，不跨领域 | 齿轮强度计算器（机械工程） | 仪表盘类（跨多个计算领域） |

### 2.2 复合计算器 → 原子计算器拆分规则

当前B类48个Skill中，部分属于"复合计算器"（一个Skill包含多个独立计算功能），需要拆分：

| 拆分触发条件 | 处理方式 | 示例 |
|-------------|---------|------|
| **一个Skill输出多个不相关指标** | 每个指标拆为一个独立计算器 | B1财务指标计算器 → MRR计算器 + ARR计算器 + ... |
| **一个Skill包含多种计算方法** | 每种方法拆为一个独立计算器 | B2估值计算引擎 → DCF估值器 + 可比公司估值器 + 分部加总估值器 |
| **一个Skill是"仪表盘/看板"类** | 拆为底层计算器组合 + 重新归类为C类 | B34退货分析仪表盘 → 退货率计算器 + 原因分类器 + 回收率计算器 + 欺诈指标计算器 |

## 三、数据弹性机制

### 3.1 设计目标

技能在被调用时，不应该因为用户"没给数据"就罢工。它应该：
1. **主动提示**用户可以提供的参数（建议用户填写）
2. **接受不完整数据**，缺失部分用预估值填充
3. **标注置信度**，让用户知道哪些结果是基于真实数据的、哪些是基于预估的
4. **敏感性分析**，告诉用户哪些参数对结果影响最大（值得花时间去获取准确数据）

### 3.2 参数三级分级

```
┌──────────────────────────────────────────────────────┐
│              启动Skill                                 │
│                      ↓                                 │
│  ┌──────────────────────────────────────────────┐    │

│  │  ┌──────────────────────────────────────┐    │    │
│  │  │ 📋 建议您提供以下数据（可提升精度）：      │    │    │
│  │  │                                        │    │    │
│  │  │ ● 必填参数：净利润、净资产（无默认值）    │    │    │
│  │  │ ○ 建议参数：行业平均ROE（默认12%）       │    │    │
│  │  │ ○ 可选参数：调整系数（默认1.0）          │    │    │
│  │  │                                        │    │    │
│  │  │ [开始计算] [跳过，使用全部默认值]         │    │    │
│  │  └──────────────────────────────────────┘    │    │
│  └──────────────────────────────────────────────┘    │
│                      ↓                                 │
│  ┌──────────────────────────────────────────────┐    │
│  │  用户选择：                                    │    │
│  │  A. 提供全部数据 → 置信度 ★★★★★              │    │
│  │  B. 提供部分数据 → 置信度 ★★★☆☆（标注预估项）  │    │
│  │  C. 全部使用默认值 → 置信度 ★★☆☆☆（标注全部）  │    │
│  └──────────────────────────────────────────────┘    │
│                      ↓                                 │
│  ┌──────────────────────────────────────────────┐    │
│  │  执行计算 + 输出结果 + 置信度 + 敏感性分析       │    │

└──────────────────────────────────────────────────────┘
```

### 3.3 置信度标记规则

| 置信度 | 星级 | 条件 | 输出示例 |
|--------|------|------|---------|
| 高 | ★★★★★ | 所有必填+建议参数均由用户提供 | `ROE = 15.2%（置信度：★★★★★）` |
| 中 | ★★★☆☆ | 必填参数由用户提供，建议参数使用默认值 | `ROE ≈ 15.2%（置信度：★★★☆☆，预估值：行业ROE=12%）` |
| 低 | ★★☆☆☆ | 所有参数均使用默认值 | `ROE ≈ 12.0%（置信度：★★☆☆☆，全部使用预估值）` |
| 极低 | ★☆☆☆☆ | 预估数据注册表中无匹配默认值，使用通用默认值 | `ROE ≈ 10.0%（置信度：★☆☆☆☆，通用默认值）` |

### 3.4 敏感性分析规则

每个原子计算器需要定义1-3个关键参数进行敏感性分析：

```

│  │ 净利润 +10% → ROE = 16.7%            │    │

└──────────────────────────────────────────────┘
```

## 五、预估数据注册表（新增 L2 层）

### 5.1 为什么需要预估数据注册表？

当用户没有提供数据时，原子计算器不能"凭空"计算。它需要从"预估数据注册表"中获取行业基准值、市场默认值、经验参数等。

**魔鬼代言人警示**：预估数据注册表如果设计不当，可能成为"垃圾进垃圾出"的源头。因此需要：
- 每个默认值必须有明确来源（行业报告/市场数据/经验值）
- 默认值需要定期更新（至少每季度审核一次）
- 默认值需要标注"适用场景"（不是所有场景都适用同一个默认值）

## 七、魔鬼代言人：风险与应对

### 风险1：原子计算器数量膨胀

**风险描述**：拆分后计算器从48个膨胀到50-60个，管理成本上升，Agent选择计算器的复杂度增加。

**主观评估**：这个风险真实存在但可控。50-60个计算器按领域分组后，每个领域约5-12个，属于可管理范围。且动态检索机制会根据语义自动匹配，Agent不需要"记住"所有计算器名称。

**应对措施**：
- 领域分组命名（如 `财务-MRR计算器`、`财务-DCF估值器`），便于检索
- 每个计算器description必须精准描述功能，确保动态检索准确率
- 如果未来数量继续膨胀，可引入"计算器注册中心"概念

### 风险2：预估数据过时

**风险描述**：预估数据注册表中的默认值可能过时，导致计算结果偏差累积。

**应对措施**：
- 每个默认值标注来源和最后更新日期
- 在输出结果中明确标注"使用了预估值"和预估值来源
- 设计定期审核机制（建议每季度）
- 用户提供的数据优先级始终高于预估值

### 风险3：拆分过度导致调用链过深

**风险描述**：一个上层Skill可能需要调用5-10个原子计算器，调用链变长，出错概率增加。

**应对措施**：
- 上层Skill不直接调用原子计算器，而是通过"编排逻辑"批量调用
- 每个原子计算器独立执行，一个失败不影响其他
- 错误传播机制：原子计算器失败时返回错误标记+使用预估值，而非阻断整个流程

### 风险4：复合计算器拆分后用户使用不便

**风险描述**：原来用户调用一个"财务指标计算器"就能拿到MRR/ARR/NDR/LTV/CAC，现在需要调用5个计算器。

**应对措施**：
- 上层Skill（如"财务分析报告模板"）负责编排，一次性调用所有需要的原子计算器
- 用户不需要感知底层拆了多少个计算器
- 用户直接调用的是上层Skill，上层Skill再调用原子计算器
