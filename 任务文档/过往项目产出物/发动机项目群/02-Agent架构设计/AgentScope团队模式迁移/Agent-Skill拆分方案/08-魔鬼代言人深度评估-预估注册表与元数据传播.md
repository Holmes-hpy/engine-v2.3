## 一、垃圾进垃圾出：六层防御体系

### 1.1 问题本质

> 预估数据注册表是一个"数据中心"，如果里面的数据是垃圾，所有依赖它的计算器产出的结果就是垃圾。更糟糕的是，用户可能因为"置信度标注"的存在而放松警惕——"反正标注了是预估的，错了也无所谓"。

**核心矛盾**：预估数据注册表越"好用"（覆盖面广、默认值全），越容易让用户产生依赖，越容易被滥用。而预估数据天然是不准确的——否则就不叫"预估"了。

### 1.2 六层防御体系

```
┌─────────────────────────────────────────────────────────────────┐
│                    六层防御：从源头到终端的全链路守护               │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  L6: 用户断路器（终端拦截）                                        │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 当预估值占比 > 50% → 显式警告 + 阻断（需用户确认才继续）     │  │
│  │ "⚠️ 本次计算使用了 7/10 个预估值，结果可信度极低。"          │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                       │
│  L5: 交叉验证（结果比对）                                          │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 当同一数据项有多个来源时，自动比对差异                        │  │
│  │ "行业平均ROE：来源A=12%，来源B=15%，差异25%>阈值10%，请确认"  │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                       │
│  L4: 置信度透明（输出标注）                                        │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 每个输出结果标注：哪些用了预估、预估来源、置信度星级          │  │
│  │ "ROE = 15.2%（★★★☆☆，预估值：行业ROE=12%，来源：Wind2026Q2)"│  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                       │
│  L3: 适用性门禁（场景匹配）                                        │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 每个预估值标注适用场景，场景不匹配时拒绝使用                  │  │
│  │ "行业ROE=12% 适用于：制造业，不适用于：金融业 → 拒绝使用"     │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                       │
│  L2: 新鲜度衰减（时间折扣）                                        │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 预估值随时间衰减置信度，超期自动标记为"待审核"                │  │
│  │ <3个月=100%  |  3-6个月=80%  |  6-12个月=60%  |  >12月=停用 │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                       │
│  L1: 源头质量（录入规范）                                          │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 每个预估值必须满足"五有"标准：有来源、有更新时间、有适用范围、  │  │
│  │ 有更新频率、有负责人。缺任何一项，拒绝录入。                  │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 逐层详解

#### L1：源头质量——"五有"录入标准

| 必须项 | 说明 | 反面示例（禁止） |
|--------|------|----------------|
| **有来源** | 行业报告名称/数据库名称/标准编号 | ❌ "行业经验" |
| **有更新时间** | 精确到季度的最后更新日期 | ❌ "最近" |
| **有适用范围** | 适用的行业/地区/企业规模 | ❌ "通用" |
| **有更新频率** | 每季度/每半年/每年 | ❌ 不填 |
| **有负责人** | 负责审核更新的角色 | ❌ 不填 |

**魔鬼追问**：如果某个预估值确实找不到权威来源，只有一个"经验值"，怎么办？

**答**：允许录入，但：
- 来源标注为"经验值（无权威来源）"
- 置信度自动降一级（从★★★☆☆降到★★☆☆☆）
- 更新频率设为"每次使用前建议用户确认"
- 在输出中明确标注"该预估值无权威来源，建议用户提供实际数据"

#### L2：新鲜度衰减——时间折扣函数

```
预估值置信度 = 原始置信度 × 新鲜度系数

新鲜度系数：
  < 3个月  → 1.0  （新鲜）
  3-6个月  → 0.8  （可用）
  6-12个月 → 0.6  （陈旧）
  > 12个月 → 0.0  （停用，需人工审核后才能恢复）
```

**示例**：
- 行业平均ROE=12%，来源：Wind 2026Q1，当前：2026年7月
- 距今：约4个月 → 新鲜度系数=0.8
- 输出：`ROE ≈ 15.2%（★★★☆☆，预估值：行业ROE=12%，来源Wind 2026Q1，已过4个月，新鲜度80%）`

**魔鬼追问**：新鲜度衰减函数是否过于机械？比如GDP增长率这种缓慢变化的指标，12个月也不算过时吧？

**答**：你说得对。不同类别的预估值衰减速度不同：

| 数据类别 | 衰减速度 | 停用阈值 | 示例 |
|---------|---------|---------|------|
| 高频市场数据 | 每月衰减15% | 3个月 | 利率、汇率、股价 |
| 行业基准数据 | 每季度衰减10% | 12个月 | 行业ROE、流失率 |
| 结构性参数 | 每半年衰减5% | 24个月 | 税率、人口结构 |
| 物理常数 | 不衰减 | 无限期 | 材料强度、重力加速度 |

**需要在预估数据注册表中为每个数据项标注"数据类别"以匹配不同衰减曲线。**

#### L3：适用性门禁——场景不匹配则拒绝使用

每个预估值必须标注"适用场景"标签：

```
数据项：行业平均ROE
默认值：12%
适用场景：制造业 | 中型企业 | 中国市场
不适用场景：金融业 | 初创企业 | 海外市场
来源：Wind行业数据库 2026Q2
```

**使用时的匹配逻辑**：

```
IF 用户场景 ∈ 适用场景标签 → 使用（置信度按新鲜度衰减）
ELSE IF 用户场景 ∈ 不适用场景标签 → 拒绝使用，提示用户必须提供数据
ELSE → 使用但额外降一级置信度，并标注"适用场景不匹配"
```

**示例**：
- 用户场景：某金融科技公司 → 行业ROE默认值12%的适用场景是"制造业" → 拒绝使用
- 输出：`ROE = ?（无法计算，行业ROE默认值不适用于金融业，请提供实际数据）`

#### L4：置信度透明——标注到每个输出字段

输出格式强制要求：

```
计算结果：
  ROE = 15.2%
  ┌────────────────────────────────────────────┐
  │ 置信度：★★★☆☆（中）                        │
  │                                            │
  │ 用户提供数据（2/4）：                       │
  │   ✅ 净利润 = 1000万（用户提供）             │
  │   ✅ 净资产 = 6600万（用户提供）             │
  │                                            │
  │ 使用预估值（2/4）：                         │
  │   ⚠️ 行业ROE = 12%（来源：Wind 2026Q1，已过4个月）  │
  │   ⚠️ 调整系数 = 1.0（经验值，无权威来源）    │
  │                                            │
  │ ⚠️ 建议：行业ROE数据已过4个月，建议更新。    │
  │         调整系数为经验值，精确度有限。        │
  └────────────────────────────────────────────┘
```

#### L5：交叉验证——多源比对

当预估数据注册表中同一数据项有多个来源时，自动执行比对：

```
数据项：行业平均ROE
  来源A：Wind数据库 → 12.0%（2026Q1）
  来源B：东方财富 → 13.5%（2026Q1）
  来源C：行业协会 → 11.8%（2025Q4）

差异检测：max(12.0, 13.5, 11.8) - min(12.0, 13.5, 11.8) = 1.7%
差异率：1.7% / 12.4% = 13.7% > 阈值10%

→ 触发交叉验证警告：
  "行业ROE存在多源差异（12.0% ~ 13.5%，差异率13.7%），建议取中位数12.0%或提供实际数据。"
```

#### L6：用户断路器——终端拦截

当预估值占比过高时，不应该是"提醒"而是"阻断"：

| 预估值占比 | 处理方式 |
|-----------|---------|
| 0% | 正常输出，置信度★★★★★ |
| 1-30% | 正常输出，置信度标注 |
| 31-50% | 正常输出，置信度标注 + 黄色警告 |
| 51-80% | **阻断**：显示警告"本次计算使用了超过半数预估值，结果可信度低，建议提供更多数据"，用户可主动选择"继续使用预估值" |
| >80% | **阻断**：显示"本次计算几乎全部依赖预估值，结果可信度极低，强烈建议提供数据"，用户可主动选择"继续使用预估值（不推荐）" |

**魔鬼追问**：如果用户每次都选择"继续使用预估值"，断路器不就形同虚设了吗？

**答**：确实。但这是设计取舍——我们不能替用户做决定，只能确保用户"知情"。附加措施：
- 对于预估值占比>50%的结果，输出文件顶部加红色水印："基于预估值，仅供参考"
- 记录用户每次"跳过"的行为，如果同一用户连续3次跳过，推送提示"建议完善数据以获得更准确结果"

## 二、管理成本：全维度风险评估

### 2.1 评估框架

从10个维度逐一评估管理成本上升的风险，每个维度包含：风险描述、具体案例、定量评估、应对措施。

---

### 维度1：Skill数量膨胀

**风险描述**：从223个增加到约235个（+12个新增原子计算器），绝对数量增长不多（5.4%），但结构复杂度显著增加——新增了一个完整的"原子计算器层"。

**定量评估**：

| 指标 | 拆分前 | 拆分后 | 增幅 |
|------|--------|--------|------|
| Skill总数 | 223 | ~235 | +5.4% |
| 分类数 | 6（A-F） | 7（新增atomic-calculator） | +1 |
| 层级数 | 1（平铺） | 3（L1/L2/L3） | +2 |
| 跨层引用关系 | 0 | ~200+（上层Skill→计算器） | 新增 |

**具体案例**：

> 原来"A14-风险评估报告模板"内部硬编码了风险评估矩阵的计算逻辑（影响×可能性）。拆分后，A14需要显式声明"调用L1-风险评估矩阵计算器"。如果A14的开发者不知道这个计算器已经存在，可能又自己写一套计算逻辑，导致重复。

**风险等级**：🟡 中（数量增长可控，但引用关系复杂度是新增的）

**应对措施**：
- 建立"计算器注册中心"（一个索引文档），所有上层Skill开发者必须先查注册中心再写代码
- 代码审查规则：发现硬编码计算逻辑 → 自动提醒"存在可复用的原子计算器"

### 维度2：版本同步地狱

**风险描述**：56个原子计算器各自独立版本管理，上层147个Skill引用它们。任何一个计算器发生breaking change，所有引用它的上层Skill都可能受影响。

**定量评估**：

| 场景 | 影响范围 | 修复成本 |
|------|---------|---------|
| 1个计算器升级（兼容） | 0个上层Skill | 0 |
| 1个计算器升级（breaking） | 平均约3-5个上层Skill | 每个上层Skill约0.5h |
| 1个计算器废弃 | 平均约3-5个上层Skill需要找替代 | 每个上层Skill约1h |
| 56个计算器中有10%发生breaking change | ~15-25个上层Skill | 总计约15-25h |

**具体案例**：

> "毛利率计算器" v2.0 输出格式从 `毛利率: 0.35` 变为 `{毛利率: 35%, 置信度: ★★★★☆, 预估值使用: []}`。所有引用了这个计算器的上层Skill（财务分析报告模板、利润分析框架、竞品分析模板等）需要同步更新解析逻辑。

**风险等级**：🔴 高（这是拆分架构的固有风险，无法根除，只能管理）

**应对措施**：
- **计算器输出格式向后兼容**：新增字段只能追加，不能修改已有字段
- **弃用期（Deprecation Period）**：breaking change需要提前2个版本声明弃用
- **版本兼容性矩阵**：每个计算器维护一个 `compatibility` 字段，声明兼容哪些上层Skill版本
- **自动检测**：平台需要支持"影响分析"——当计算器升级时，自动列出所有引用它的上层Skill

```
# 计算器版本兼容性声明示例
## compatibility
| 计算器版本 | 兼容上层Skill版本 | 备注 |
|-----------|-----------------|------|
| v2.0.0 | 上层Skill >= v2.1.0 | 输出格式变更 |
| v1.3.0 | 上层Skill >= v2.0.0 | 稳定版本 |
| v1.0.0 | 上层Skill >= v1.0.0 | 初始版本，已弃用 |
```

### 维度3：命名与检索歧义

**风险描述**：56个计算器按语义相似度排列，可能出现"看起来差不多"的计算器，Agent动态检索时选错。

**定量评估**：

| 歧义类型 | 涉及计算器 | 错误率预估 |
|---------|-----------|-----------|
| 同义词歧义 | ROI计算器 vs 投资回报率计算器 vs 组合ROI计算器 | 15-20% |
| 领域歧义 | 毛利率计算器（财务） vs 毛利率计算器（电商利润测算） | 10-15% |
| 粒度歧义 | 财务指标计算器（复合） vs MRR计算器（原子） | 20-30% |

**具体案例**：

> Agent收到任务："计算这个项目的ROI"。
> 候选计算器：ROI计算器（通用）、组合ROI计算器（项目管理）、投资回报率计算器（财务）。
> 如果Agent选错了（比如选了组合ROI计算器但用户想要的是财务ROI），结果完全错误。

**风险等级**：🔴 高（动态检索的核心风险）

**应对措施**：
- **description必须包含"触发词"和"排除词"**
  ```
  description: 计算单个投资项目的财务ROI（投资回报率=净收益/投资成本）。
  适用于：单一项目、单一投资决策。
  不适用于：多项目组合、IT项目组合、风险调整后ROI。
  触发词：ROI、投资回报率、单项目、投资回报
  ```
- **计算器名称加领域前缀**：`财务-ROI计算器`、`项目管理-组合ROI计算器`
- **Agent提示词中增加"计算器选择确认"步骤**：当有多个候选计算器时，先向用户确认再执行

### 维度4：依赖链断裂风险

**风险描述**：上层Skill → 5个原子计算器 → 每个计算器调用预估数据注册表。这是一个3层调用链，任何一层断裂都会导致最终结果缺失。

**定量评估**：

```
假设每个环节的可用性为99%：
  上层Skill：99%
  原子计算器(5个)：99%^5 = 95.1%
  预估数据注册表：99%
  整体可用性：99% × 95.1% × 99% = 93.2%

即：每次调用有约6.8%的概率出现部分失败。
```

**具体案例**：

> 用户调用"财务分析报告模板"，需要依次调用MRR计算器、ARR计算器、NDR计算器、LTV计算器、CAC计算器。如果NDR计算器因为无法获取"期初ARR"数据而失败，整个报告是"部分成功"还是"整体失败"？

**风险等级**：🟡 中（单一计算器失败不应导致整体失败，但这需要显式设计）

**应对措施**：
- **优雅降级**：单个计算器失败不阻断整体流程，失败的计算器输出"无法计算（原因：XXX）"
- **部分结果标注**：输出中明确标注哪些指标计算成功、哪些失败
- **重试机制**：计算器失败时自动重试一次（使用不同的预估值或降级参数）
- **降级策略**：每个计算器定义"降级输出"——当无法计算时输出什么

### 维度5：测试与验证负担

**风险描述**：56个原子计算器 + 147个上层Skill = 203个需要测试的单元。每个计算器需要验证：正常输入、边界输入、缺失数据、预估数据场景。

**定量评估**：

| 测试类型 | 数量 | 每个用例数 | 总用例数 |
|---------|------|-----------|---------|
| 原子计算器单元测试 | 56 | 5-8个场景 | 280-448 |
| 数据弹性测试 | 56 | 3个场景（全数据/部分数据/全预估） | 168 |
| 上层Skill集成测试 | 50+ | 2-3个场景 | 100-150 |
| 预估数据注册表测试 | 1 | 按领域 | 10-20 |
| **合计** | | | **558-786** |

**具体案例**：

> "DCF估值器"至少需要测试：
> 1. 正常输入（5年现金流+折现率+终值增长率）→ 验证输出在合理范围
> 2. 边界输入（现金流为0、折现率极高）→ 验证不崩溃
> 3. 缺失数据（无终值增长率）→ 验证从预估注册表获取默认值
> 4. 全部预估 → 验证置信度标注正确
> 5. 敏感性分析 → 验证±10%波动结果合理

**风险等级**：🟡 中（测试用例数量增长，但可自动化）

**应对措施**：
- 每个计算器必须包含 `example` 字段（即黄金测试用例）
- 标准化测试框架：根据输入schema自动生成边界测试
- 计算器上线前必须通过"四场景测试"：正常、边界、缺数据、全预估

### 维度6：学习与认知成本

**风险描述**：新加入的开发者或Agent使用者需要理解三层架构、原子计算器概念、数据弹性机制、置信度标注、预估数据注册表等概念。

**定量评估**：

| 概念 | 学习难度 | 理解时间 | 误解风险 |
|------|---------|---------|---------|
| 三层架构 | 中 | 30min | 低 |
| 原子计算器定义 | 高 | 1h | 中（容易与复合计算器混淆） |
| 数据弹性机制 | 高 | 1h | 高（参数分级逻辑复杂） |
| 置信度标注 | 低 | 15min | 低 |
| 预估数据注册表 | 中 | 30min | 中（容易误用预估值） |
| 敏感性分析 | 中 | 30min | 中 |
| Skill间引用 | 高 | 1h | 高（循环依赖风险） |
| **合计** | | **~5h** | |

**风险等级**：🟡 中（概念较多，但分层清晰后降低了单个概念的复杂度）

**应对措施**：
- 配套教学文档（已有"平台教学-Agent与Skill实例演示"）
- 原子计算器模板（复制粘贴即可创建新计算器）
- FAQ文档：常见误解和正确做法

---

### 维度7：一致性与口径统一

**风险描述**：56个原子计算器由不同人（或不同时间）编写，可能出现同一概念不同公式的情况。

**具体案例**：

> "毛利率"在财务领域的标准公式是 `(收入-成本)/收入`。
> 但在电商领域，有人可能定义为 `(售价-进货价-平台扣点)/售价`。
> 如果两个计算器都叫"毛利率计算器"但公式不同，上层Skill调用时会产生矛盾结果。

**风险等级**：🔴 高（隐蔽且后果严重——两个计算器都"正确"但结果不一致）

**应对措施**：
- **概念注册表**：在预估数据注册表中增加"概念定义"章节
  ```
  ## 概念定义
  | 概念名称 | 标准公式 | 适用领域 | 变体说明 |
  |---------|---------|---------|---------|
  | 毛利率 | (收入-成本)/收入 | 财务通用 | 电商变体：(售价-进货价-平台扣点)/售价 |
  | ROI | 净收益/投资成本 | 财务通用 | 项目变体：(收益-成本)/成本 |
  ```
- 计算器description中引用概念注册表
- 代码审查时检查公式一致性

---

### 维度8：预估数据注册表的维护成本

**风险描述**：预估数据注册表需要定期更新，涉及多个领域的数据采集和审核，谁来维护？多久维护一次？

**具体案例**：

> 2026年央行降息，无风险利率从3.0%降到2.5%。如果预估数据注册表没有及时更新，所有DCF估值结果都会偏高。
> 问题：谁负责监控央行利率变化并更新注册表？更新频率是多少？

**风险等级**：🔴 高（持续维护成本，且容易被忽视）

**应对措施**：
- 每个数据项标注"更新触发条件"：
  ```
  | 数据项 | 更新触发条件 | 监控方式 |
  | 无风险利率 | 央行利率调整 | 自动监控（RSS/API） |
  | 行业ROE | 季度财报发布后 | 手动更新（每季度） |
  | 物流成本占比 | 行业报告发布 | 手动更新（每半年） |
  ```
- 区分"自动更新"和"手动更新"数据项
- 平台需求：数据过期自动告警

---

### 维度9：性能与延迟

**风险描述**：上层Skill需要串行调用多个原子计算器，每个计算器可能需要查询预估数据注册表，导致总体延迟增加。

**风险等级**：🟢 低（LLM系统本身延迟较高，计算器调用延迟相比可忽略）

**应对措施**：无需特殊处理，但需注意：如果未来某个计算器需要联网查询实时数据（如汇率），延迟可能显著增加。

---

### 维度10：废弃与迁移

**风险描述**：当某个原子计算器被废弃或替换时，所有引用它的上层Skill需要迁移。迁移过程可能遗漏，导致"僵尸引用"。

**具体案例**：

> "B1-财务指标计算器"被拆分为7个原子计算器，原来的Agent提示词中仍然引用"B1-财务指标计算器"，但该Skill已不存在。Agent调用失败。

**风险等级**：🟡 中（迁移过程可控，但容易遗漏）

**应对措施**：
- 废弃的Skill不删除，而是标记为"已废弃"并保留一个"转发"逻辑
  ```
  ## status
  deprecated
  
  ## migration_guide
  本Skill已被拆分，请使用以下原子计算器：
  - MRR计算器 → 替代原MRR指标
  - ARR计算器 → 替代原ARR指标
  ...
  ```
- 平台支持"废弃Skill调用时自动提示替代方案"

---

### 2.2 风险评估汇总

| 维度 | 风险等级 | 核心问题 | 可控性 |
|------|---------|---------|--------|
| 1. Skill数量膨胀 | 🟡 中 | 引用关系复杂度 | 可控 |
| 2. 版本同步 | 🔴 高 | Breaking change传播 | 需平台支持 |
| 3. 命名与检索歧义 | 🔴 高 | 动态检索选错计算器 | 需description规范 |
| 4. 依赖链断裂 | 🟡 中 | 单点失败影响全局 | 需优雅降级设计 |
| 5. 测试负担 | 🟡 中 | 500+测试用例 | 可自动化 |
| 6. 学习成本 | 🟡 中 | 概念多、理解门槛高 | 需配套文档 |
| 7. 一致性 | 🔴 高 | 同概念不同公式 | 需概念注册表 |
| 8. 预估数据维护 | 🔴 高 | 持续维护成本高 | 需明确责任 |
| 9. 性能延迟 | 🟢 低 | 影响可忽略 | 无需特殊处理 |
| 10. 废弃迁移 | 🟡 中 | 僵尸引用 | 需迁移指南 |

**关键结论**：10个维度中有4个🔴高风险、5个🟡中风险、1个🟢低风险。**高风险项集中在前3个维度（版本同步、命名歧义、一致性）和第8个维度（预估数据维护）**。这些风险不是"可能发生"而是"必然发生"，需要前置设计而非事后补救。

## 三、预估注册表归属与元数据传播

### 3.1 预估数据注册表在哪类Skill中体现？

**答案：D类（知识库类），位于L2数据与知识层。**

```
┌─────────────────────────────────────────────────────────────────┐
│  L2: 数据与知识层                                                │
│                                                                   │
│  ┌─────────────────────────┐  ┌─────────────────────────────┐   │
│  │ D类-知识库（28个）       │  │ 预估数据注册表（D类，新增）   │   │
│  │                         │  │                             │   │
│  │ D1. 贷款产品知识库      │  │ name: 预估数据注册表          │   │
│  │ D2. 平台定价规则知识库  │  │ category: knowledge-base     │   │
│  │ D3. 医疗行政知识库      │  │ sub_category: estimation     │   │
│  │ ...                     │  │                             │   │
│  │                         │  │ 包含：                       │   │
│  │ 职责：领域知识查询       │  │ - 财务领域默认值             │   │
│  │ 不调用计算器             │  │ - 电商领域默认值             │   │
│  │                         │  │ - 供应链领域默认值           │   │
│  └─────────────────────────┘  │ - 概念定义（公式统一）       │   │
│                                │ - 数据新鲜度管理             │   │
│                                └─────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

**为什么是D类而不是独立类别？**
- 预估数据注册表本质是"数据查询"——输入数据项名称，输出默认值和元数据
- 与D类知识库（如"贷款产品知识库查利率"）功能模式一致
- 不需要新增分类，降低认知负担

### 3.2 元数据传播问题——这是本次讨论最关键的架构发现

#### 问题场景重现

```
用户调用"财务分析报告模板"（A类，L3）
  → 模板需要 MRR、ARR、NDR、LTV、CAC 五个指标
  → 模板调用5个原子计算器（L1）
  → 每个计算器需要不同参数：
      MRR：月付费客户数、ARPU
      ARR：MRR（可以从MRR计算器获取）
      NDR：期初ARR、扩张ARR、收缩ARR、流失ARR
      LTV：ARPU、毛利率、月流失率
      CAC：销售营销总费用、新获客户数
  → 问题：模板怎么知道要给用户展示哪些参数？
```

**核心矛盾**：公式在计算器里，参数定义在计算器里，但"向用户要数据"这件事发生在上层Skill。上层Skill如果不读取每个计算器的参数定义，就不知道要问用户要什么。

#### 解决方案：参数聚合与去重模式

```
┌─────────────────────────────────────────────────────────────────┐
│                    参数聚合与去重流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  步骤1：上层Skill声明依赖的计算器                                  │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 财务分析报告模板:                                          │  │
│  │   composed_calculators:                                    │  │
│  │     - MRR计算器                                            │  │
│  │     - ARR计算器（依赖MRR计算器输出）                         │  │
│  │     - NDR计算器                                            │  │
│  │     - LTV计算器                                            │  │
│  │     - CAC计算器                                            │  │
│  │     - 毛利率计算器                                         │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↓                                       │
│  步骤2：平台读取每个计算器的input schema                            │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ MRR计算器.inputs:                                          │  │
│  │   必填: 月付费客户数, 平均月付费额(ARPU)                    │  │
│  │   建议: 行业平均MRR                                        │  │
│  │                                                            │  │
│  │ ARR计算器.inputs:                                          │  │
│  │   必填: MRR ← 标记为"可从MRR计算器获取"                     │  │
│  │                                                            │  │
│  │ NDR计算器.inputs:                                          │  │
│  │   必填: 期初ARR, 扩张ARR, 收缩ARR, 流失ARR                 │  │
│  │                                                            │  │
│  │ LTV计算器.inputs:                                          │  │
│  │   必填: ARPU（与MRR计算器重复!）, 毛利率, 月流失率          │  │
│  │   建议: 行业平均LTV                                        │  │
│  │                                                            │  │
│  │ CAC计算器.inputs:                                          │  │
│  │   必填: 销售营销总费用, 新获客户数                          │  │
│  │                                                            │  │
│  │ 毛利率计算器.inputs:                                       │  │
│  │   必填: 收入, 成本                                         │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↓                                       │
│  步骤3：合并 + 去重                                               │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 原始参数总数：6个计算器 × 平均2.5个参数 = 15个参数          │  │
│  │                                                            │  │
│  │ 去重后：                                                   │  │
│  │   必填参数(8个)：                                          │  │
│  │     月付费客户数, ARPU, 期初ARR, 扩张ARR, 收缩ARR,         │  │
│  │     流失ARR, 月流失率, 销售营销总费用, 新获客户数,         │  │
│  │     收入, 成本                                             │  │
│  │                                                            │  │
│  │   自动计算参数(1个)：MRR（从MRR计算器输出）                 │  │
│  │                                                            │  │
│  │   建议参数(2个)：行业平均MRR, 行业平均LTV                   │  │
│  │                                                            │  │
│  │   去重说明：ARPU 在 MRR计算器 和 LTV计算器 中重复出现，     │  │
│  │           合并为一个参数，只问用户一次。                     │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↓                                       │
│  步骤4：展示给用户                                               │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 📋 财务分析报告需要以下数据：                               │  │
│  │                                                            │  │
│  │ ● 必填参数（11个）：                                       │  │
│  │   月付费客户数、ARPU、期初ARR、扩张ARR、收缩ARR、           │  │
│  │   流失ARR、月流失率、销售营销总费用、新获客户数、           │  │
│  │   收入、成本                                               │  │
│  │                                                            │  │
│  │ ○ 建议参数（2个）：行业平均MRR、行业平均LTV                 │  │
│  │   （不提供将使用预估值）                                    │  │
│  │                                                            │  │
│  │ ⚡ 自动计算（1个）：MRR（由MRR计算器自动计算）               │  │
│  │                                                            │  │
│  │ [开始计算] [跳过，使用全部默认值]                           │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 这需要上层Skill新增什么？

**上层Skill需要新增一个 `composed_calculators` 字段：**

```markdown
## name
财务分析报告模板

## description
生成SaaS企业财务分析报告，包含MRR/ARR/NDR/LTV/CAC等核心指标...

## version
2.1.0

## category
template

## composed_calculators
本模板依赖以下原子计算器，平台将自动聚合参数并去重：

| 计算器 | 用途 | 依赖关系 |
|--------|------|---------|
| MRR计算器 | 计算月经常性收入 | 无 |
| ARR计算器 | 计算年经常性收入 | 依赖MRR计算器输出 |
| NDR计算器 | 计算净收入留存率 | 无 |
| LTV计算器 | 计算客户生命周期价值 | 无 |
| CAC计算器 | 计算客户获取成本 | 无 |
| 毛利率计算器 | 计算毛利率 | 无 |

## template
[报告模板内容，使用 {{MRR计算器.output.MRR}} 等占位符引用计算结果]
```

### 3.4 平台需要支持什么？

**新增平台需求：L7-Skill间调用与参数聚合**

| 需求编号 | 需求名称 | 说明 |
|---------|---------|------|
| L7.1 | 参数聚合引擎 | 读取 `composed_calculators` 中所有计算器的input schema，合并去重后展示给用户 |
| L7.2 | 参数去重 | 同名参数（如"ARPU"在多个计算器中）合并为一个，只让用户提供一次 |
| L7.3 | 依赖链执行 | 按依赖关系排序执行（如先执行MRR计算器，再执行ARR计算器） |
| L7.4 | 结果注入 | 计算器执行结果自动注入到上层Skill的模板占位符中 |
| L7.5 | 优雅降级 | 单个计算器失败不阻断整体流程，失败指标标注"无法计算" |
| L7.6 | 预估数据集成 | 参数聚合时自动标注哪些参数有默认值，用户可跳过 |

### 3.5 原子计算器还需要新增什么？

**原子计算器需要新增 `output_schema` 字段，让上层Skill知道可以引用什么输出：**

```markdown
## name
MRR计算器

## output_schema
| 字段名 | 类型 | 说明 | 引用方式 |
|--------|------|------|---------|
| MRR | number | 月经常性收入 | {{MRR计算器.output.MRR}} |
| 置信度 | string | 结果置信度星级 | {{MRR计算器.output.置信度}} |
| 预估值使用 | list | 使用了哪些预估值 | {{MRR计算器.output.预估值使用}} |

## output
| 字段名 | 类型 | 说明 |
|--------|------|------|
| MRR | number | 月经常性收入 |
| 置信度 | string | ★★★☆☆ |
| 预估值使用 | list | ["行业平均MRR=50万"] |
```
