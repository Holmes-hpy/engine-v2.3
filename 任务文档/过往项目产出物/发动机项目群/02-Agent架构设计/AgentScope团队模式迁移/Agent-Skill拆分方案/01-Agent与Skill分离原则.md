# Agent 与 Skill 分离原则

> 版本：v1.0 | 日期：2026-07-28
>
> 本文档定义智能体平台中 Agent 与 Skill 的边界划分原则，是后续所有专家拆分工作的依据。

---

## 一、问题背景

### 1.1 当前专家的结构问题

现有的专家提示词存在三层内容的混合：

```
┌─────────────────────────────────────────┐
│ 第1层：身份层（WHO）                       │
│ "我是投资研究员，14年经验，覆盖金融科技..."    │
├─────────────────────────────────────────┤
│ 第2层：工作流/决策逻辑（WHEN & WHAT）        │
│ "先做筛选，再做初步评估，再深度研究..."        │
│ "看多论点要写，看空论点更要写..."            │
├─────────────────────────────────────────┤
│ 第3层：具体方法/模板（HOW）                  │
│ DCF模型模板、尽调清单、可比分析表格...        │
│ 具体的计算公式、检查项、输出格式...           │
└─────────────────────────────────────────┘
```

第1层 + 第2层 → **Agent**（决定做什么、什么时候做）
第3层 → **Skill**（具体怎么做，可被多个Agent复用）

### 1.2 为什么要分离

| 问题 | 不分离的后果 | 分离后的收益 |
|------|-------------|-------------|
| 方法复用时复制粘贴 | 多个专家的提示词中有大量重复内容（如DCF模板、SWOT模板） | Skill 一次定义，多个 Agent 调用 |
| Agent 提示词爆炸 | 单个专家文件数千字，决策逻辑被淹没在模板细节中 | Agent 瘦身，聚焦决策和判断 |
| 维护成本高 | 改一个分析方法要改所有用到它的专家文件 | 改一个 Skill，所有 Agent 自动受益 |
| 用户困惑 | 用户不知道哪些能力是独立的、可复用的 | Skill 作为独立能力单元，可被用户发现和组合 |

## 二、核心定义

### 2.1 什么是 Agent

Agent 是一个**具有身份和决策能力的智能体**。它的核心职责是：

- 知道自己是谁（角色身份）
- 理解用户需要什么（需求理解）
- 决定用什么方法解决（任务编排）
- 判断结果的合理性（质量把关）
- 以特定风格与用户沟通（表达方式）

**Agent 的本质：做判断的人。**

### 2.2 什么是 Skill

Skill 是一个**具有明确输入输出规范的专业能力单元**。它的核心特征是：

- 接受明确的输入参数
- 按照固定的方法/规则执行
- 产出结构化的输出
- 不依赖特定角色身份
- 可被多个不同 Agent 调用

**Skill 的本质：能执行的方法。**

## 三、四维判定模型

判断一个内容块应该归 Agent 还是 Skill，用以下四个维度：

### 3.1 维度一：可变性（Variability）

| 判断标准 | 归 Agent | 归 Skill |
|----------|----------|----------|
| 内容随场景变化程度 | 高度依赖具体场景，同一角色不同项目判断不同 | 相对固定，每次执行逻辑一致 |
| 示例 | "根据客户预算和行业选择销售策略" | "MEDDPICC 资质审查检查清单" |

**判断方法**：问自己 ——"换一个项目，这段内容还需要改吗？"如果需要改 → Agent；如果直接拿来用 → Skill。

### 3.2 维度二：可复用性（Reusability）

| 判断标准 | 归 Agent | 归 Skill |
|----------|----------|----------|
| 能否被多个不同角色使用 | 高度绑定该角色身份，其他角色用不了 | 可被多个不同 Agent 调用 |
| 示例 | "我是投资研究员，我关注的是..." | DCF 估值模型（财务分析师、投资研究员、风控师都能用） |

**判断方法**：问自己 ——"把这段内容给另一个完全不同的专家，他也能用吗？"如果能 → Skill；如果不能 → Agent。

### 3.3 维度三：决策含量（Decision Density）

| 判断标准 | 归 Agent | 归 Skill |
|----------|----------|----------|
| 需要多少判断和权衡 | 需要判断、权衡、取舍 | 按规则执行，不需要替代人的判断 |
| 示例 | "看多论点要写，看空论点更要写——没有平衡的主张是营销" | "毛利率 =（收入-成本）/收入 × 100%" |

**判断方法**：问自己 ——"一个初级员工按照这段文字操作，能做出正确结果吗？"如果能 → Skill；如果还需要经验和判断 → Agent。

### 3.4 维度四：输入输出明确性（IO Clarity）

| 判断标准 | 归 Agent | 归 Skill |
|----------|----------|----------|
| 输入输出格式 | 模糊目标 → 需要拆解为子任务 | 明确输入 → 结构化输出 |
| 示例 | "帮我分析一下这家公司" | 输入：三张财务报表 → 输出：财务比率分析表 |

**判断方法**：问自己 ——"能用一个函数签名来描述这个过程吗？"如 `function skillName(input: TypeA) -> TypeB`。如果能 → Skill。

## 四、边界规则

### 4.1 应该拆成 Skill 的内容

以下类型的内容**强烈建议**拆成 Skill：

1. **结构化模板**：报告模板、检查清单、评分卡、表格框架
2. **计算方法**：财务比率计算、估值模型、评分算法、排名逻辑
3. **分析框架**：SWOT、PEST、波特五力、MEDDPICC、AARRR
4. **标准化流程**：代码审查清单、部署检查清单、合规检查流程
5. **格式转换**：数据格式转换、图表生成、翻译
6. **清单类交付物**：尽调清单、测试用例清单、上线检查清单

### 4.2 不应该拆成 Skill 的内容

以下类型的内容**不适合**拆成 Skill：

1. **角色身份声明**："我是XX专家，有XX年经验"
2. **决策规则**："区分论点和叙事"、"量化下行风险"——这些是判断逻辑
3. **跨技能协调**："分析师说X，税务师说Y，我怎么权衡"——这是 Agent 的核心能力
4. **沟通风格**：表达方式、语气、用词偏好
5. **高度情境化的判断**："幕僚长判断什么该升级给老板"——这无法标准化
6. **领域知识框架**："看一个行业要看哪些维度"——这是认知框架，不是执行方法

### 4.3 不适合拆分的专家类型

以下类型的专家，其内容**高度内聚**，强行拆分反而破坏能力：

| 专家类型 | 原因 | 例子 |
|----------|------|------|
| 高度情境化判断型 | 核心能力是"什么情况下做什么判断"，无法标准化 | 幕僚长、销售教练 |
| 纯身份定义型 | 内容本身就是身份+沟通风格，没有可独立执行的方法 | 趣味注入师、图书联合作者 |
| 全流程内聚型 | 工作流程早中后期紧密关联，拆开后各阶段失去上下文 | 部分全流程设计专家 |

### 4.4 Skill 的粒度要求

- **太粗**：一个 Skill 等于整个专家能力 → 跟没拆一样
- **太细**：碎片化，Agent 调用成本高 → "请帮我计算毛利率" 不需要专门一个 Skill
- **合适粒度**：一个 Skill 对应一个**完整的、可独立交付的专业产出单元**

## 五、判定流程图

```
一段内容 → 第1问：能写成一个函数签名吗？
              │
              ├─ 不能 → 第2问：需要经验和判断吗？
              │              │
              │              ├─ 需要 → Agent
              │              └─ 不需要 → 格式转换/模板 → Skill
              │
              └─ 能 → 第3问：换一个角色也能用吗？
                         │
                         ├─ 不能 → Agent
                         └─ 能 → 第4问：换一个项目需要改吗？
                                    │
                                    ├─ 需要改 → Agent
                                    └─ 不需要 → Skill
```

## 六、与现有工作的关系

### 6.1 之前的团长Agent方案是否作废？

**不作废，但需要重新审视。** 之前的12个团长Agent方案解决的是"多专家协作"问题，本次 Agent/Skill 分离解决的是"单专家能力拆分"问题。两者是正交的：

- Agent/Skill 分离 → 适用于**所有**专家，无论是否参与团队协作
- 团队模式 → 适用于**需要多角色协作**的场景

一个合理的最终架构是：Agent（身份+决策） + Skills（可复用方法） + 团队模式（可选的多Agent协作）。

### 6.2 本次分析范围

本次分析覆盖全部86个可迁移专家（等级0：68个 + 等级1：18个）。
等级2和等级3的专家因涉及外部服务依赖，暂不纳入本次分析范围。
