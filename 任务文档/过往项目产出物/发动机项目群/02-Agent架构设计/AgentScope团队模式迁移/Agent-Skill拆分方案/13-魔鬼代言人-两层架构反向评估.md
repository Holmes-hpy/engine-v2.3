> 版本：v1.0 | 日期：2026-07-30
>
> 本文档扮演魔鬼代言人角色，对"两层Skill架构（74个原子计算器 + 147个上层应用Skill）"进行全面的反向评估。核心假设：**两层架构是不必要的，所有收益都可以通过更简单的方案获得。**

## 零、先看数据——魔鬼代言人的开场质问

在进入具体维度之前，先看几个让人不安的数字：

|------|-------------------|---------------------|------|
| Skill文件总数 | 223 | 74+147+28=249 | +11.7% |

**魔鬼代言人的第一个问题**：你花了12-17小时的迁移工作量，增加了26个文件，引入200+个脆弱引用关系，创建了3个需要持续维护的基础设施文档——你确定这是在"优化"而不是在"制造问题"？

## 维度1：Token经济性——两层真的省钱吗？

### 1.1 数据核算

先做数学题。当前方案给出的数据：

- **单层模型**：复合计算器（如"财务指标计算器"）12.9KB，含7个指标，Agent一次加载全部
- **两层模型**：7个原子计算器 x 3.6KB = 25.2KB，Agent可以按需加载单个

但这里有一个精心设计的数学陷阱。

**陷阱1：场景选择偏差**

"财务指标计算器"是单层模型中最差的情况（7个指标打包在一起），而"按需加载1个计算器"是两层模型中最理想的情况。你把单层最差的场景和两层最好的场景对比，得出"两层更省Token"的结论——这是典型的统计学操纵。

实际场景分布是什么？

| 使用场景 | 占比（我主观估计） | 单层Token消耗 | 两层Token消耗 | 两层是否更省？ |
|---------|-------------------|-------------|-------------|-------------|
| 做一份财务分析报告（需要5-7个指标） | 60% | 12.9KB | 5x3.6=18KB ~ 7x3.6=25.2KB | **否，多消耗40-95%** |
| 做一次估值分析（需要3个估值方法） | 15% | ~8KB | 3x3.6=10.8KB | **否，多消耗35%** |
| 做一次库存健康度评估（需要3个指标） | 10% | ~6KB | 3x3.6=10.8KB | **否，多消耗80%** |
| 算一个MRR | 10% | 12.9KB | 3.6KB | 是，节省72% |
| 算一个ROE | 5% | 8KB | 3.6KB | 是，节省55% |

**加权计算**：
- 单层加权：60%x12.9 + 15%x8 + 10%x6 + 10%x12.9 + 5%x8 = 7.74 + 1.2 + 0.6 + 1.29 + 0.4 = **11.23KB**
- 两层加权：60%x21.6 + 15%x10.8 + 10%x10.8 + 10%x3.6 + 5%x3.6 = 12.96 + 1.62 + 1.08 + 0.36 + 0.18 = **16.2KB**

**结论：两层架构在加权平均下比单层多消耗约44%的Token。** 两层架构只在那15%的"单一指标计算"场景下省钱，在85%的"复合分析"场景下反而更贵。

**陷阱2：认知开销无法量化**

即使Agent按需加载单个计算器，也需要理解该计算器的接口（参数名、类型、输出格式）。单层架构下，Agent直接看到模板中的公式，认知路径是"看公式 → 理解 → 计算"。两层架构下，认知路径是"查注册中心 → 理解计算器接口 → 加载计算器 → 理解公式 → 计算"。多出来的两步是需要消耗Token的——每次调用注册中心查询、每次加载计算器文件的元数据读取，这些都是方案文档中没有计入的Token消耗。

**陷阱3：注册中心的Token开销**

上层Skill调用计算器前，需要先查注册中心确认计算器是否存在。如果注册中心本身是74个条目的文档，Agent每次需要检索其中的一部分。注册中心文档约800行，加上概念注册表约750行，这两个基础设施文档本身就是Token消耗大户。如果Agent需要理解整个架构（比如一个新加入的Agent），它需要一次性加载和理解这两个文档。

### 1.2 Token经济性结论

**魔鬼代言人判断：两层架构在Token经济性上的论证是片面的。** 方案文档只展示了"算一个指标"的极端有利场景，忽略了85%的"复合分析"场景中Token消耗反而增加的事实。更关键的是，认知开销和注册中心检索开销完全没有计入模型。

如果你真的想省Token，应该问：为什么不让复合计算器支持"按需计算部分指标"？比如财务指标计算器增加一个参数 `metrics: ["MRR", "ARR"]`，Agent只加载12.9KB的完整文件但只执行其中2个指标的计算。这样既保留了单层架构的简洁性，又实现了按需计算的灵活性。

## 维度2：管理复杂度——拆得越细，管得越累

### 2.1 文件数量暴增的实际影响

从223个文件变成249个文件，绝对数量增加不多（+11.7%），但结构复杂度是质变而非量变：

| 管理维度 | 单层架构 | 两层架构 | 新增管理负担 |
|---------|---------|---------|------------|
| 文件命名规范 | 6类前缀 | 6类前缀 + 14个领域前缀 + atomic-calculator类别 | 需要理解两层命名体系 |
| 文件间关系 | 无显式关系 | 200+个 `composed_calculators` 引用 | 每个引用是可断裂的依赖 |
| 版本管理 | 每文件独立版本 | 每文件独立版本 + 计算器/上层Skill版本兼容性 | 需要维护兼容性矩阵 |
| 新增文件流程 | 创建1个文件 | 先查注册中心→创建计算器→注册→上层Skill引用 | 4步替代1步 |
| 废弃文件流程 | 删除1个文件 | 标记废弃+检查所有引用+迁移上层Skill+更新注册中心 | 4步替代1步 |

### 2.2 "一个公式的修改"需要改几处？

单层架构下，修改"毛利率公式"只需要改复合计算器中的1行。两层架构下：

```
步骤1：修改概念注册表中"毛利率"的公式定义
步骤2：修改"财务-毛利率计算器"的formula_reference（如果变体不变则不需要）
步骤3：检查"电商-利润测算器"是否使用了电商毛利率变体
步骤4：检查所有上层Skill的required_data是否受影响
步骤5：修改后全部重新测试
```

你告诉我这个"管理成本更低"？

### 2.3 注册中心的维护是个无底洞

方案文档说概念注册表"维护成本极低——定义不会频繁变化"。这个论述有两个问题：

**问题1：定义确实不频繁变化，但"引用关系"会频繁变化。** 每新增一个上层Skill，就需要在注册中心的"被引用"字段中增加一行。每废弃一个上层Skill，就需要去掉一行。如果74个计算器被147个上层Skill引用，平均每个计算器被约2个Skill引用（实际上分布极不均匀，见维度3），那么"被引用"字段的维护就是一个持续的手工劳动。

**问题2：概念注册表需要持续"发现冲突"。** 方案文档说"在新增计算器时检查是否有冲突"——但谁来检查？怎么检查？如果开发者A在财务领域定义了"毛利率"的公式，开发者B在不知道的情况下给电商领域也定义了一个"毛利率"公式，概念注册表不会自动报警。你指望人工代码审查来发现这种冲突？

### 2.4 1-2人团队的维护噩梦

**我主观认为，这套架构是为5人以上的团队设计的，但当前项目很可能只有1-2人维护。**

如果只有1-2人维护：
- 概念注册表不需要——因为维护者自己知道所有公式
- 计算器注册中心不需要——因为维护者自己知道哪些计算器存在
- 200+个引用关系不是"协作保障"而是"认知负担"——每改一个计算器，开发者需要记住所有引用它的上层Skill

这套架构解决的是"多人协作时如何保证一致性"的问题——但如果根本没有多人协作，这些基础设施就是纯粹的负担。

**魔鬼代言人判断：管理复杂度不是"略有增加"而是"质变"。** 从平铺的一层变成了三层，从0个引用关系到200+个，从0个基础设施文档到3个需要持续维护的文档。对于1-2人团队，这套架构的收益-成本比严重倒挂。

## 维度3：实际复用率——真的有人复用吗？

### 3.1 引用关系的真实分布

这是整个两层架构中最致命的问题。方案文档中每个计算器的"被引用"字段几乎都是：

```
被引用：（待步骤3确认）
```

这意味着**在方案文档撰写时，连设计者自己都不知道每个计算器会被几个上层Skill引用**。你连"复用率"的数据都没有，就断言"需要通过拆分来提高复用率"——这就像还没测血糖就给自己开胰岛素。

### 3.2 按引用数量估算的复用率分布

基于现有数据，我做一个合理的估算：

| 引用数量 | 计算器数量 | 占比 | 典型例子 |
|---------|-----------|------|---------|
| 0个引用（低复用） | ~20个 | 27% | 咨询-ESN利润计算器、HR-绩效分布模型、智能助推决策引擎 |
| 1个引用（一对一） | ~30个 | 41% | 物流-物流方案对比计算器、教育-位次分析器、测试-质量门禁评分器 |
| 2-3个引用（中度复用） | ~15个 | 20% | 电商-产品成本核算器、风险-风险评估矩阵计算器 |
| 4+个引用（高度复用） | ~9个 | 12% | 财务-MRR/ARR/NDR/LTV/CAC、毛利率、DCF、安全库存 |

**核心发现：约68%的计算器（50个）被0-1个上层Skill引用。** 如果一个计算器只被1个上层Skill使用，把它从上层Skill中拆出来，你做了什么？你在两个文件之间建立了一个"一对一"的引用关系——这本质上只是把一个文件拆成两个文件，用一个脆弱的引用链接起来。

### 3.3 领域专属计算器的拆分悖论

逐个审视那些"几乎不可能被复用"的计算器：

| 计算器 | 为什么不可能被复用 | 拆分价值 |
|--------|-------------------|---------|
| 咨询-ESN利润计算器 | 法国ESN咨询的利润计算，只有法国咨询市场模板使用 | **零** |
| 智能助推决策引擎 | 算法引擎，只有行为助推引擎使用 | **零** |
| 教育-位次分析器 | 高考位次分析，只有高考志愿填报模板使用 | **零** |
| 教育-选科组合分析器 | 高考选科分析，只有高考志愿填报模板使用 | **零** |
| 教育-录取概率评估器 | 高考录取概率，只有高考志愿填报模板使用 | **零** |
| 法律-信托账户对账器 | 律所信托对账，只有律所计费模板使用 | **零** |
| 物流-物流方案对比计算器 | 物流方案对比，只有1个上层Skill使用 | **零** |
| 工程-齿轮强度计算器 | 机械工程齿轮设计，只有机械设计模板使用 | **零** |
| 工程-轴疲劳校核器 | 机械工程轴设计，只有机械设计模板使用 | **零** |
| 工程-螺栓设计计算器 | 机械工程螺栓设计，只有机械设计模板使用 | **零** |
| 工程-振动模态分析器 | 机械工程振动分析，只有机械设计模板使用 | **零** |

**这11个计算器（占74个的15%）被拆分出来，纯属浪费。** 它们在原来的复合Skill中作为公式存在，现在被拆成独立文件，只是为了满足"所有计算都要原子化"的教条。它们不会被任何其他上层Skill复用，因为它们的领域太专了。工程领域4个计算器都只被1个"机械设计模板"使用——如果把它们合并回机械设计模板，文件数量减少4个，引用关系减少4个，管理成本显著降低，功能完全不受影响。

### 3.4 复用率结论

**魔鬼代言人判断：两层架构的复用率假设是空中楼阁。** 约68%的计算器只有0-1个引用，拆分它们不是"提高复用率"而是"制造无意义的一对一引用"。真正值得拆分的只有那9个（12%）高频共享的计算器——MRR/ARR/NDR/LTV/CAC/DCF/毛利率/安全库存/风险评估矩阵。

## 维度4：Agent认知负担

### 4.1 认知路径对比

**单层架构的认知路径**（Agent执行"计算ROI"）：
```
1. 用户说"算ROI"
2. Agent加载复合计算器（12.9KB）
3. 看到公式：ROI = 净收益 / 投资成本
4. 向用户要参数：净收益、投资成本
5. 计算并输出
```
认知步骤：3步。认知复杂度：低。

**两层架构的认知路径**（Agent执行"计算ROI"）：
```
1. 用户说"算ROI"
2. Agent查询计算器注册中心，检索"ROI"关键词
3. 发现两个候选：财务-ROI计算器、项目管理-组合ROI计算器
4. 读取两个计算器的description，对比触发词和排除词
5. 触发歧义确认流程："检测到多个匹配的计算器..."
6. 用户选择"财务-ROI计算器"
7. Agent加载财务-ROI计算器（3.6KB）
8. 看到formula_reference: concept_registry.财务.ROI
9. 可选：加载概念注册表确认公式定义
10. 看到公式：ROI = 净收益 / 投资成本
11. 向用户要参数
12. 计算并输出
```
认知步骤：8-10步。认知复杂度：高。

Agent的每一步都是Token消耗，每一步都可能出错。两层架构让Agent多做了5-7步额外工作，这些工作对最终结果（"ROI=15%"）没有任何贡献——它们只是在"管理架构"。

### 4.2 误选计算器的代价

方案文档承认了歧义风险，设计了"三层防歧义机制"。但问题在于：

**即使有防歧义机制，Agent仍然可能选错。** 防歧义机制只是降低了选错的概率，但增加了认知负担。而且，如果Agent选错了（比如选了"项目管理-组合ROI计算器"而不是"财务-ROI计算器"），错误结果可能已被用于决策，等到发现时已经晚了。

单层架构不存在这个问题——因为只有一个"ROI计算器"，公式就在模板里，Agent不会选错。

### 4.3 防歧义机制本身是认知负担

方案文档设计了"三层防歧义机制"：
1. 领域前缀命名
2. description包含触发词和排除词
3. Agent确认步骤

这听起来很合理，但换个角度想：**你引入了一个问题（拆分导致歧义），然后设计了三个解决方案来弥补这个问题——为什么不直接避免这个问题？**

就像在房间里挖了一个坑，然后安装了三层护栏来防止掉进去。但如果你不挖坑，你根本不需要护栏。

### 4.4 Agent认知负担结论

**魔鬼代言人判断：两层架构将Agent的认知负担增加了约2-3倍。** 单层架构下Agent的认知路径是"看到公式→计算"，两层架构下变成了"查注册中心→对比候选→歧义确认→加载计算器→查概念注册表→计算"。这些额外步骤不产生任何价值，纯粹是为了管理架构而存在的开销。

## 维度5：收益的边际递减——为什么前20个和后54个不一样？

### 5.1 帕累托分析

假设按照引用频率排序，前20个计算器（约27%）贡献了约80%的复用价值：

**高价值计算器（值得拆分，约20个）**：
- 财务-MRR/ARR/NDR/LTV/CAC（5个，SaaS核心指标，被多个模板/框架复用）
- 财务-毛利率/DCF/可比估值/有效税率/ROI/ROE（6个，财务通用指标）
- 风险-Beta/VaR/夏普比率/最大回撤/风险评估矩阵（5个，风险分析通用）
- 供应链-安全库存/周转天数（2个，供应链通用）
- 数据-实验统计分析器/异常检测器（2个，数据通用）

**低价值计算器（不值得拆分，约54个）**：
- 领域专属计算器（11个，见维度3.3）
- 仪表盘拆分产物（14个，如退货率/退货原因/回收率/欺诈指标等，这些只被1个退货分析框架使用）
- 一对一映射计算器（约20个，如测试-代码覆盖率/功能覆盖率/缺陷密度等，只被1个测试报告模板使用）
- 隐性提取计算器（1个，供应链-需求预测方法选择器，连方案文档都承认"不是纯计算器"）

### 5.2 边际收益分析

| 拆分数量 | 累计复用价值 | 累计管理成本 | 边际收益 |
|---------|------------|------------|---------|
| 前10个 | 高（SaaS核心指标，每个被3-5个上层Skill引用） | 低（10个文件，财务1个领域） | **极高** |
| 前20个 | 高（增加风险/估值指标，每个被2-4个引用） | 中（20个文件，2-3个领域） | **高** |
| 前30个 | 中（增加供应链/数据指标，每个被1-2个引用） | 中（30个文件，5个领域） | **中** |
| 前50个 | 低（大量一对一映射开始出现） | 高（50个文件，10+领域） | **低** |
| 全部74个 | 极低（27%的计算器零引用或只有一个引用） | 极高（74个文件，14个领域，200+引用） | **负** |

**边际收益在大约第20-30个计算器处变为负值。** 当拆分到第50个计算器时，新增的每个计算器都在增加管理成本但几乎不产生复用价值。当拆分到所有74个时，整体收益可能已经为负。

### 5.3 按领域拆分的边际收益

| 领域 | 计算器数 | 上层Skill数（大致） | 平均复用率 | 是否值得全部拆分？ |
|------|---------|-------------------|-----------|-----------------|

| 工程 | 4 | 1 | 极低 | **全部不值得** |
| 测试 | 7 | 2-3 | 低 | 只有2-3个值得 |
| 教育 | 3 | 1 | 极低 | **全部不值得** |
| 法律 | 5 | 2 | 低 | 只有1-2个值得 |

### 5.4 边际收益结论

**魔鬼代言人判断：全量拆分74个计算器是典型的"过度拆分"——为了追求架构的纯粹性而忽略了边际收益递减。** 对于物流、工程、教育、咨询、HR这5个领域（共11个计算器），拆分不仅没有收益，还增加了管理负担。如果只保留前20-25个高频共享计算器，把其余约50个回退到上层Skill中，既能保留核心复用收益，又能大幅降低管理成本。

## 维度6：替代方案——有更简单的方法吗？

### 6.1 方案A：公式库模式（推荐）

**核心理念**：保持单层架构，用一个集中的公式定义文件来保证一致性，不需要拆分文件。

```
结构：
┌─────────────────────────────────────────┐
│  formula_library.md（公式库）             │
│                                          │
│  ## 财务-SaaS                            │
│  - MRR = 付费客户数 × ARPU              │
│  - ARR = MRR × 12                       │
│  - NDR = (期初ARR + 扩张 - 收缩 - 流失)   │
│          / 期初ARR                       │
│  - LTV = ARPU × 毛利率 / 月流失率        │
│  - CAC = 销售营销总费用 / 新获客户数     │
│                                          │
│  ## 财务-通用                            │
│  - 毛利率 = (收入 - 成本) / 收入         │
│  - ROI = 净收益 / 投资成本               │
│  - ROE = 净利润 / 净资产                 │
│  ...                                     │
└─────────────────────────────────────────┘

上层Skill中使用：
## template
### 核心指标计算
本报告使用以下公式（引用公式库 v1.0）：
- MRR：{{公式库.财务-SaaS.MRR}}
- ARR：{{公式库.财务-SaaS.ARR}}
...
```

**与两层架构的对比**：

| 维度 | 两层架构 | 公式库模式 |
|------|---------|-----------|
| 文件数 | 249（+74个计算器） | 224（+1个公式库） |
| 引用关系 | 200+个跨文件引用 | 0个（所有引用在同一文件内） |
| 新增Skill流程 | 4步 | 1步（在上层Skill中引用公式库） |
| Agent认知路径 | 查注册中心→找计算器→加载→调用 | 看到公式→计算 |
| 公式一致性 | 需要计算器+概念注册表双重保障 | 公式库本身是单一权威来源 |
| 维护成本 | 高（3个基础设施文档+200+引用） | 低（1个公式库文件） |
| 复用性 | 计算器作为独立文件可复用 | 公式作为定义可引用 |
| 版本管理 | 每个计算器独立版本 | 公式库统一版本 |

**关键优势**：公式库模式解决了两层架构声称要解决的所有问题（公式一致性、复用性），但没有引入任何新问题（引用关系膨胀、认知负担增加、管理复杂度上升）。

### 6.2 方案B：混合模式（折中方案）

**核心理念**：只拆分高频共享的计算器（约20个），其余保留在复合Skill中。

```
结构：
┌─────────────────────────────────────────┐
│  L1: 核心计算器（~20个，独立文件）        │
│  - 财务-MRR/ARR/NDR/LTV/CAC             │
│  - 财务-毛利率/DCF/可比估值/ROI           │
│  - 风险-Beta/VaR/夏普/最大回撤/矩阵       │
│  - 供应链-安全库存                       │
│  - 数据-实验统计分析/异常检测             │
│  - 电商-产品成本核算                     │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│  L3: 上层Skill（~155个，含内嵌公式）      │
│  - 高频指标引用L1计算器                  │
│  - 低频/领域专属指标内嵌公式              │
│  - composed_calculators 只声明L1计算器   │
└─────────────────────────────────────────┘
```

**与全量两层架构的对比**：

| 维度 | 全量两层 | 混合模式 |
|------|---------|---------|
| 计算器数量 | 74 | ~20 |
| 引用关系 | 200+ | ~50-80 |
| 管理成本 | 高 | 中 |
| 公式一致性 | 概念注册表保障 | 核心计算器用概念注册表，其余内嵌 |
| 文件总数 | 249 | ~225 |
| 迁移工作量 | 12-17h | ~5-7h |

**优势**：保留了核心复用价值，大幅降低了管理成本。约50个低频计算器不需要维护独立文件、版本号、兼容性矩阵。

### 6.3 方案C：代码片段模式

**核心理念**：将公式定义为可引用的片段（类似代码片段），但不独立成文件。

```
上层Skill中使用：
## template
### 核心指标计算
```formula MRR
MRR = 付费客户数 × ARPU
```

```formula ARR
ARR = MRR × 12
```

```formula NDR
NDR = (期初ARR + 扩张ARR - 收缩ARR - 流失ARR) / 期初ARR
```

Agent在执行时，平台自动识别 `formula` 代码块，提取公式并执行计算。公式片段可以在多个Skill中复用（通过复制粘贴或引用），但不需要独立文件管理。

**优势**：最轻量，不需要任何基础设施，不需要任何引用关系管理。缺点是公式一致性靠人工保证（但1-2人团队本来就不需要自动化保障）。

### 6.4 替代方案对比总结

| 方案 | 文件数 | 引用关系 | 基础设施 | Agent认知负担 | 公式一致性 | 适用场景 |
|------|--------|---------|---------|-------------|-----------|---------|
| 单层（原方案） | 223 | 0 | 0 | 低 | 靠人工 | 1-2人团队 |
| 公式库（方案A） | 224 | 0 | 1（公式库） | 低 | 公式库保障 | 1-3人团队 |
| 混合（方案B） | ~225 | ~50-80 | 2（注册中心+概念表） | 中 | 核心有保障 | 3-5人团队 |
| 全量两层（当前） | 249 | 200+ | 3 | 高 | 全部有保障 | 5+人团队 |
| 代码片段（方案C） | 223 | 0 | 0 | 低 | 靠人工 | 1人团队 |

**魔鬼代言人判断：当前方案是四种方案中成本最高、复杂度最高的方案，但目标用户场景（1-2人维护）与方案设计假设（5+人团队）严重不匹配。** 方案A（公式库）或方案B（混合模式）更适合当前项目的实际情况。

## 维度7：结论——魔鬼代言人的最终判断

### 7.1 核心判断

**两层架构是"过度设计"而非"必要的优化"。**

论据总结：

1. **Token经济性论证片面**：只展示了最优场景（算单个指标），忽略了加权平均下两层架构多消耗44% Token的事实。

2. **管理复杂度质变而非量变**：从0个引用关系增加到200+个，从0个基础设施文档增加到3个，从1步操作增加到4步操作。对于1-2人的维护团队，这些成本远大于收益。

3. **复用率假设未经数据验证**：方案文档中几乎所有计算器的"被引用"字段都是"待步骤3确认"，设计者自己都不知道复用率。我估算约68%的计算器（50个）只有0-1个引用，拆分它们纯属浪费。

4. **Agent认知负担增加2-3倍**：单层架构"看到公式→计算"的3步路径，变成了两层架构"查注册中心→对比候选→歧义确认→加载计算器→查概念注册表→计算"的8-10步路径。

5. **边际收益严重递减**：前20个计算器贡献了80%的复用价值，后54个计算器几乎不产生额外收益，但显著增加了管理成本。

6. **存在更简单的替代方案**：公式库模式（方案A）或混合模式（方案B）能以更低的成本解决同样的问题。

### 7.2 如果必须保留两层架构的调整建议

如果团队出于某种原因必须保留两层架构（比如未来团队规模扩展到5+人），我建议以下调整：

1. **立即回退约50个低频计算器**：将物流、工程、教育、咨询、HR、法律（部分）、测试（部分）、电商（部分）、供应链（部分）领域的计算器回退到对应的上层Skill中，只保留约25个核心计算器。

2. **取消概念注册表**：将概念定义直接合并到公式库中，减少一个独立维护的基础设施文档。

3. **简化计算器注册中心**：从"每个计算器一个完整条目"简化为"一个按领域分组的表格"，一页内可完整浏览。

4. **取消`composed_calculators`字段**：上层Skill直接通过文件引用调用计算器，不需要显式声明依赖关系。这一步消除了200+个脆弱的引用关系。

5. **取消三层防歧义机制**：在计算器数量减少到25个后，歧义场景大幅减少，依靠领域前缀命名即可区分。减少Agent的认知负担。

### 7.3 如果回退到单层架构的具体方案

1. 将74个原子计算器中的公式提取到一个集中的公式库文件（`formula_library.md`）
2. 将原来的147个上层Skill + 28个知识库Skill恢复为直接在模板中引用公式库
3. 删除计算器注册中心、概念注册表
4. 删除74个原子计算器文件
5. 文件总数：从249减少到约224（223个原Skill + 1个公式库）

**预计工作量**：约3-5小时（比正向迁移的12-17小时少得多）。

### 7.4 最后一个问题

**魔鬼代言人问设计者**：如果今天只有你一个人维护这个项目，你还会选择拆分74个计算器吗？如果答案是"不会"，那说明你心里知道这个架构是为更大的团队设计的——但更大的团队现在并不存在。

**架构应该是"刚好够用"的，而不是"为未来完美设计"的。** 过度设计不仅浪费当下的时间，还会让未来的重构更加困难（因为已经基于过度设计的架构做了太多依赖）。
