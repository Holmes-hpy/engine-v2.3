# 项目管理框架

## 一、输入要求

| 参数名 | 类型 | 必填 | 说明 | 示例 |
|--------|------|------|------|------|
| `project_name` | string | 是 | 项目名称 | `智能客服系统V2.0升级` |
| `project_type` | string | 是 | 项目类型，`software_dev` / `marketing` / `engineering` / `general` | `software_dev` |
| `project_phase` | string | 是 | 项目阶段，`initiation` / `planning` / `execution` / `monitoring` / `full_lifecycle` | `full_lifecycle` |
| `deliverables` | array | 是 | 项目交付物列表 | `["智能客服Web端","工单管理系统","数据看板"]` |
| `stakeholders` | array | 否 | 利益方列表 | 见下方利益方结构 |
| `budget` | object | 否 | 项目预算信息 | `{"total": 500, "unit": "万元", "contingency_pct": 0.15}` |
| `timeline` | object | 否 | 项目时间线 | `{"start": "2026-08-01", "end": "2026-12-31"}` |
| `team_size` | number | 否 | 项目团队人数 | `12` |
| `known_risks` | array | 否 | 已知风险列表 | `["第三方API稳定性不足","核心开发人员可能离职"]` |
| `methodology` | string | 否 | 项目管理方法论，默认按项目类型推荐 | `agile` / `waterfall` / `hybrid` / `scrum` |
| `output_language` | string | 否 | 输出语言，默认中文 | `zh` / `en` |

### 利益方结构

```
stakeholders: [
  {
    "name": "CTO",
    "role": "项目发起人",
    "influence": "high",     // 影响力：high / medium / low
    "interest": "high",      // 关注度：high / medium / low
    "expectations": "系统稳定运行，用户满意度提升20%",
    "communication": "每周邮件汇报+月度演示"
  },
  ...
]
```

### 项目类型与默认方法论映射

| 项目类型 | 推荐方法论 | 核心特征 |
|----------|-----------|----------|
| software_dev | Agile/Scrum | 迭代开发、需求变更频繁、用户故事驱动 |
| marketing | Hybrid | 策略规划阶段用瀑布，执行阶段用敏捷 |
| engineering | Waterfall | 需求明确、变更成本高、阶段门控严格 |
| general | Hybrid | 灵活组合，按子项目特性选择 |

## 二、执行逻辑

### 整体流程

```
输入项目参数
├── 步骤1：确定方法论组合和项目阶段范围
├── 步骤2：生成WBS工作拆解
├── 步骤3：输出利益方分析矩阵
├── 步骤4：生成风险评估模板
├── 步骤5：制定资源分配策略
└── 步骤6：整合输出完整项目管理框架
```

### 步骤1：方法论选择

根据 `project_type` 和 `methodology` 参数确定最终使用的方法论。

```
决策逻辑：
if methodology 已指定 → 使用指定方法论
else → 根据 project_type 使用默认推荐

方法论影响：
- Waterfall → 阶段串行，WBS按阶段拆解，门控评审
- Agile/Scrum → 迭代并行，WBS按Sprint拆解，故事点估算
- Hybrid → 前期规划用瀑布，开发执行用敏捷
```

### 步骤2：WBS工作拆解

**WBS拆解原则：**
- 100%原则：WBS必须覆盖项目的全部工作范围
- 互斥原则：各工作包之间不重叠
- 可交付原则：每个工作包产出可验证的交付物
- 80小时原则：单个工作包工时不超过80小时（2周）

**按项目类型的WBS模板：**

### 步骤3：利益方分析矩阵

**分析维度：**

```
利益方分析矩阵 = 影响力 × 关注度

影响力：该利益方对项目目标的决策权/影响能力
关注度：该利益方对项目进展/结果的关注程度

策略矩阵：
┌──────────────┬──────────────────┬─────────────────┐
│              │   低关注度(Low)   │  高关注度(High)  │
├──────────────┼──────────────────┼─────────────────┤
│ 高影响力(High)│  令其满意         │  重点管理         │
│              │  (Keep Satisfied) │  (Manage Closely)│
├──────────────┼──────────────────┼─────────────────┤
│ 低影响力(Low) │  最低关注         │  保持知情         │
│              │  (Monitor)        │  (Keep Informed) │
└──────────────┴──────────────────┴─────────────────┘
```

**利益方管理策略：**

| 象限 | 策略 | 沟通频率 | 沟通方式 | 关注点 |
|------|------|----------|----------|--------|
| 高影响力+高关注 | 重点管理 | 周度 | 当面汇报+周报 | 风险、里程碑、预算 |
| 高影响力+低关注 | 令其满意 | 月度 | 邮件摘要 | 关键节点、重大变更 |
| 低影响力+高关注 | 保持知情 | 双周 | 邮件+群消息 | 进展、障碍、交付物 |
| 低影响力+低关注 | 最低关注 | 月度 | 项目简报 | 重大里程碑 |

### 步骤4：风险评估模板

**风险识别维度：**

| 风险类别 | 说明 | 软件开发案例 | 市场营销案例 | 工程建设案例 |
|----------|------|-------------|-------------|-------------|
| 技术风险 | 技术方案可行性、成熟度 | 第三方API不稳定 | 投放平台算法变更 | 地质条件不确定 |
| 资源风险 | 人力/资金/设备可用性 | 核心开发离职 | 预算削减 | 材料供应短缺 |
| 进度风险 | 关键路径延误 | 需求变更频繁 | 审批流程延迟 | 天气影响工期 |
| 质量风险 | 交付物不达标 | Bug率过高 | 投放效果不达预期 | 施工质量缺陷 |
| 外部风险 | 政策/市场/环境变化 | 数据安全法规更新 | 竞品突然降价 | 环保政策加严 |
| 沟通风险 | 信息不对称、误解 | 跨部门协作不畅 | 供应商理解偏差 | 设计变更沟通不及时 |

**风险量化评估：**

```
风险评分 = 发生概率 × 影响程度

发生概率：1(极低) ~ 5(极高)
影响程度：1(可忽略) ~ 5(灾难性)

风险等级：
- 1-6分：低风险（绿色）—— 接受，定期监控
- 7-15分：中风险（黄色）—— 制定应对计划，每月回顾
- 16-25分：高风险（红色）—— 立即行动，每周回顾，升级汇报
```

### 步骤5：资源分配策略

**管道分级模型：**

```
资源分配管道：
├── 一级管道（核心项目）：60-70%资源
│   ├── 公司战略级项目
│   ├── 已承诺交付的客户项目
│   └── 有明确ROI的优化项目
├── 二级管道（成长项目）：20-25%资源
│   ├── 新业务探索
│   ├── 技术升级/平台化
│   └── 内部效率提升工具
└── 创新管道（探索项目）：10-15%资源
    ├── 前沿技术验证
    ├── 创新孵化项目
    └── 个人兴趣项目（如Google 20%时间）
```

**资源分配表模板：**

| 管道 | 资源占比 | 预算分配 | 人员配置 | 审批流程 | 交付节奏 |
|------|----------|----------|----------|----------|----------|
| 一级 | 60-70% | {budget} | 资深+骨干 | 标准流程 | 按承诺交付 |
| 二级 | 20-25% | {budget} | 骨干+潜力 | 部门审批 | 阶段性验证 |
| 创新 | 10-15% | {budget} | 混合 | 轻量审批 | Demo驱动 |

```
| 风险 | 🟢 正常 | 高风险{n}个，中风险{n}个 |
| 团队 | 🟢 正常 | 满意度{score}分，流失率{rate}% |
| 利益方 | 🟡 预警 | {name}满意度下降，需关注 |
```

### 异常处理

| 异常情况 | 处理方式 |
|----------|----------|
| deliverables 为空 | 终止生成，提示"请至少提供1个交付物以构建WBS" |
| stakeholders 为空 | 生成利益方分析模板框架，标注"请补充利益方信息" |
| 项目周期过短（<2周） | 简化WBS层级至2级，提示"项目周期较短，建议使用轻量级任务清单替代完整WBS" |
| 项目周期过长（>2年） | 仅输出前6个月的详细WBS，后续阶段输出概要级（Level 2），提示"建议将长周期项目拆分为多个子项目分期管理" |
| 预算 = 0 或未提供 | 跳过预算分配明细，标注"未提供预算信息，预算分配表需手动填写" |
| 已知风险中含模糊描述 | 将模糊风险拆分，提示"建议将'{risk}'拆分为更具体的风险描述，例如：技术风险/资源风险/进度风险" |
| 方法论与项目类型不匹配 | 给出提示，如"Waterfall方法论通常不适合需求频繁变更的软件项目，建议切换为Agile或Hybrid"，但仍按用户指定输出 |
