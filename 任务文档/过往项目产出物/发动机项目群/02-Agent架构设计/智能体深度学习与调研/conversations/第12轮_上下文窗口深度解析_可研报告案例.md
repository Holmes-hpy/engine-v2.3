## 专家回答

### 已记录：元框架（Meta-Framework）

待基础内容吃透后深入研究。元框架问题：能否构建不绑定任何具体架构模式、允许自由组合嵌套不同模式的通用Agent框架。属于前沿研究方向。

### AgentScope 2.0上下文窗口构成

每次调用LLM时，框架构建`messages`数组：

```
messages = [
  {role: "system", content: "[System Prompt + SKILL内容 + Tool定义]"},  // 永远在最前面
  {role: "user", content: "用户初始输入/任务描述"},
  {role: "assistant", content: "Agent的回复（含思考过程）"},
  {role: "user", content: "[Tool Result: Read(...)返回内容]"},  // Tool结果也是user消息
  {role: "assistant", content: "Agent下一轮回复"},
  {role: "user", content: "[HintBlock: TeamSay from Leader]"},  // 其他Agent消息
  ...  // 单向累积，越滚越多
]
```

**关键理解**：messages数组单向累积，新消息追加到末尾，旧消息不会自动删除 — 这就是"上下文膨胀"的根本原因。

### 逐Step详解（可研报告案例）

**Step 0 — Leader初始加载（~7.5K tokens）**
- System Prompt (~1,500)：Leader人设
- SKILL文件 (~3,500)：SKILL.md + feasibility_common + chapter_writing + report_integration
- Tool定义 (~2,000)：Team工具 + File工具 + MCP工具
- 用户输入 (~500)
- 关键点：SKILL文件一次性加载到System Message，每次LLM调用都携带，所以SKILL要精简

**Step 1 — Leader确认输入（~8K）**
- 新增：Thought(~400) + Read文件列表结果(~300)
- 上下文开始缓慢膨胀

**Step 2 — Leader创建4个Parser（~9.5K）**
- 新增：4次AgentCreate调用记录(~1,500)
- 每次AgentCreate都在对话历史追加Thought+FunctionCall+ToolResult
- 多轮ReAct越来越贵：每多一轮上下文就多一层

**Step 3 — Parser-A开始执行（~4K）⭐关键对比**
- **全新session，全新messages数组！**
- System (~800) + feasibility_common (~500) + Tools (~1,500) + FirstTask (~1,200)
- Parser-A看不到Leader的9.5K历史
- Parser-A看不到Parser-B/C/D在做什么
- Parser-A只有TeamSay（Worker身份），没有TeamCreate/AgentCreate
- 这就是上下文隔离：不是在同一个上下文里加墙，而是给每个Worker独立房间

**Step 4 — Parser-A执行中（~7.8K）**
- 3轮ReAct循环：
  - R1：Thought(~300) + Read融资协议返回(~3,000) ← 原始材料3,000tk
  - R2：Thought(~400) + MCP返回(~800)
  - R3：Thought(~800) + Write结果
- 对话历史占64%
- **信息压缩**：原始材料4,500tk → 输出信息表1,500tk

**Step 5 — Leader检查信息表（~15.5K）⚠窗口压力**
- 新增：TeamWait通知(~200) + 4份信息表内容(~3,800)
- Leader上下文从9.5K→15.5K
- Leader开始感到窗口压力
- 只检查信息表不读原始材料（否则更膨胀）

**Step 6 — Writer-1写第1章（~5.6K）**
- 全新session
- System(~600) + 第1章SKILL(~1,500) + Tools(~1,000) + 信息表摘要(~2,500)
- 只加载第1章相关规范，不加载第2-10章
- **细粒度分工的意义**：避免扛无关规范

**Step 7 — Writer-6写第6章财务（~7.6K）**
- 全新session
- 独享完整财务数据(~3,000tk)
- 起始7.6K，ReAct后可能膨胀到~12K
- 独占策略：复杂财务计算需要足够窗口空间

**Step 8 — Writer-9写结论（~33.1K）⚠⚠窗口危机**
- 全新session
- 需要读取前8章全文（26,000字→~30,000tk）
- 起始33.1K，占128K窗口26%
- **全方案最大单次上下文消耗！**
- 必须使用128K+模型，32K模型会爆窗口
- 剩余95K足够生成2,500字结论

**Step 9 — Integrator整合（~37.3K）⚠⚠全流程峰值**
- 全新session
- 读取全部9章(~28,500字→~33,000tk)
- 加载report_integration SKILL(~2,000tk)
- 总37.3K，占128K的29.1%
- 以"读"为主"写"很少，窗口压力略小于Writer-9

### 上下文管理4条法则

| 法则 | 可研报告中的体现 | 不遵守的后果 |
|------|-----------------|-------------|
| 1.按需加载SKILL | Writer-1只加载第1章规范 | 每个Worker多扛~2,000tk无关内容 |
| 2.信息压缩传递 | Parser输出精炼信息表，Writer读信息表而非原始材料 | Writer上下文膨胀3-5倍 |
| 3.并行隔离 | 4个Parser各自独立session | 所有人挤在一个上下文互相污染 |
| 4.终态依赖显式化 | Writer-9明确声明读前8章，Leader据此编排 | Writer-9可能读到半成品 |

## 本轮核心知识点

- messages数组构成：System→User→Assistant→Tool Result循环累积
- 上下文隔离本质：给每个Worker独立session，不是在同一个上下文里加墙
- SKILL按需加载：每个Worker只加载相关SKILL片段
- 信息压缩是关键设计：Parser做预处理精炼，Writer读精炼后数据
- 可研报告最大消耗点：Writer-9读8章(30K)、Integrator读9章(33K)
- 窗口管理4法则：按需加载SKILL、信息压缩、并行隔离、终态依赖显式化
