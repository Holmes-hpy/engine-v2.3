## 开篇：先搞清楚 我们在做什么

### 一句话定位

我们不是在做"又一个 AI Agent 平台"，而是在做 **AI Agent 时代的中间层基础设施**。

这个定位有三个关键词，每个都值得拆开来讲：

**"中间层"** —— 不做模型（底层），不做应用（上层），做连接模型和应用的"那一层"。就像修高速公路的人不造车（模型）也不开物流公司（应用），但所有的车都得在路上跑。

**"基础设施"** —— 不是可有可无的插件，而是"不经过我就跑不通"的必经之路。TCP/IP 协议、HTTPS 加密、DNS 域名解析——这些是互联网的基础设施，你每天在用但几乎感觉不到它们的存在。我们想做的是 AI Agent 时代的 TCP/IP。

**"AI Agent 时代"** —— 这是一个赌注：赌 AI Agent 会像手机 App 一样普及，赌企业会大量部署 Agent，赌 Agent 之间需要互相通信和协作。如果这个赌注成立，那么"Agent 之间的连接层"就是一个巨大的市场。

## 第一课：MCP 和 A2A —— 两个协议，两个战场

### 为什么协议这么重要？

在讲 我们的概念之前，必须先理解两个协议，因为它们是整个 我们方案的"地基"。

**历史类比：** 互联网之所以能连接全世界的电脑，不是因为某家公司发明了超级路由器，而是因为大家同意了一套通信规则——TCP/IP 协议。协议 = 大家说同一种语言。

Agent 时代也面临同样的问题：不同公司开发的 Agent，怎么互相通信？怎么互相发现对方的能力？

### MCP（Model Context Protocol，模型上下文协议）

**谁做的：** Anthropic 公司（Claude 的母公司），2024 年底发布

**一句话理解：** MCP 解决的是 **"Agent 和工具/数据之间怎么连接"** 的问题。

**打个比方：** 把 Agent 想象成一个厨师。MCP 就是"厨房的标准化接口"——不管灶台是哪个品牌、烤箱是什么型号，都能通过统一的接口让厨师操作。没有 MCP，厨师就得学每个设备的专用操作方式。

**现状：** OpenAI 已经宣布将在 ChatGPT 中集成 MCP [$TRAE_REF](http://m.toutiao.com/group/7487053731042066996/)。这意味着 MCP 正在成为行业事实标准——就像当年 USB 统一了电脑外设接口一样。

**我们方案中的 MCP：**
- Phase 1-2 实现 MCP Server（发布工具能力）+ MCP Client（消费第三方工具）
- 这是 我们平台"连接器"的技术基础——通过 MCP，任何企业系统都可以被标准化接入

### A2A（Agent-to-Agent Protocol，智能体间通信协议）

**谁做的：** Google，2025 年 4 月发布，已捐给 Linux 基金会

**一句话理解：** A2A 解决的是 **"Agent 和 Agent 之间怎么通信和协作"** 的问题。

**打个比方：** MCP 解决了"厨师和厨房设备"的连接，A2A 解决的是"厨师和厨师之间怎么协作"。比如西餐主厨要找中餐主厨帮忙做一道菜，A2A 就是他们之间的"协作语言"。

**核心能力：**
- **能力发现**：Agent A 能告诉 Agent B "我会做什么"
- **任务协商**：Agent A 可以把任务委派给 Agent B
- **结果回传**：Agent B 完成后把结果返回给 Agent A

**现状：** 2025 年 4 月 Google Cloud Next 大会发布，核心规范已发布，目标是建立"Internet of Agents"——Agent 的互联网[$TRAE_REF](https://blog.csdn.net/taotao_guiwang/article/details/155519594)。

**我们方案中的 A2A：**
- Phase 2 做基础适配
- Phase 3 做 Capability Manifest（基于 A2A 的能力声明机制）
- Phase 4 做跨组织 Agent 协作网络

### MCP vs A2A：一张表搞清楚

| | MCP | A2A |
|:--|:--|:--|
| 谁做的 | Anthropic | Google |
| 解决什么 | Agent ↔ 工具/数据 | Agent ↔ Agent |
| 类比 | USB 接口（设备互联） | TCP/IP 协议（网络通信） |
| 我们用到哪里 | 连接器、工具调用 | 跨平台 Agent 协作 |
| 成熟度 | 较成熟，OpenAI 已采用 | 较新，仍在发展 |

## 第二课：五个核心概念深度拆解

### 概念一：Asset Marketplace（资产市场）

**一句话：** 就像苹果的 App Store，但卖的不是 App，而是 AI Agent 的"技能包"。

**为什么需要它？**

现在的问题是：每个企业建 Agent，都得从头写工具、配 Skill、搭模板。100 个企业做了 100 遍"数据提取 Agent"。

我们的想法是：我建一个市场，张三做了"数据提取 Skill"，上传到市场；李四需要，直接下载使用，给张三分成。**从"每人重复造轮子"变成"一个人造轮子，一百个人用"。**

**四层资产体系：**

| 层 | 做什么 | 类比 |
|:--|:--|:--|
| **供给层** | 开放 SDK，让开发者创建和上传 Skill/工具/模板 | 苹果给开发者 Xcode |
| **认证层** | 自动审核：安全扫描、功能验证、兼容性测试 | 苹果的 App Review |
| **分发层** | 应用商店：搜索、评分、推荐、版本管理 | App Store 本身 |
| **运营层** | 数据驱动：调用量、成功率、满意度决定谁上谁下 | 排行榜和推荐算法 |

**为什么是壁垒？**

因为这不是"建一个商店"的技术问题，而是"冷启动一个双边市场"的商业问题。**供给端要有人来开发，需求端要有人来用。** 一旦飞轮转起来——开发者越多→工具越丰富→客户越多→开发者更多——后来者很难撬动。

**补充知识：** 当前行业中，字节跳动的 Coze 已经做了 Plugin 市场，Dify 有工作流模板库，但都停留在"工具层面"。我们想做的是更深层的——不只是插件，而是 Agent 的"技能"（Skill）和"模板"（Template），这是更高维度的资产。

### 概念二：Capability Manifest（能力声明）—— 深度讲解

**一句话：** 每个 Agent 的"简历"——告诉全世界"我会什么"，让其他 Agent 能自动发现和调用我。

---

#### 2.1 先理解问题：没有 Manifest 的世界

想象一个场景：你是项目经理，公司有 100 个员工，你需要找一个人做"Python 数据分析、熟悉金融风控、能加班"。你现在怎么办？

你只能：① 翻通讯录一个一个问 ② 在群里喊"谁会数据分析？" ③ 靠记忆回忆"上次好像是张三做的"。**效率极低，而且依赖人的记忆。**

Agent 的世界也是一样。Agent A 需要做数据分析，但它不知道团队里有没有能做数据分析的 Agent。它只能等人类来告诉它"去找 Agent B"。**这就是当前所有 Agent 平台的现状——Agent 之间的协作依赖人类调度。**

---

#### 2.2 Capability Manifest 是什么

**技术定义：** Capability Manifest 是一份结构化的 JSON 文档，描述一个 Agent 的"能力画像"。它不只是"我会做什么"，而是包含：

```json
{
  "agent_id": "agent-riskanalysis-001",
  "agent_name": "金融风控分析 Agent",
  "version": "2.1.0",
  
  "capabilities": [
    {
      "category": "data_analysis",
      "skills": ["异常检测", "风险建模", "趋势分析"],
      "tools": ["pandas", "scikit-learn", "SQL"],
      "data_formats": ["CSV", "Excel", "数据库直连"],
      "success_rate": 0.95,
      "avg_latency_ms": 180000,
      "max_concurrency": 5
    },
    {
      "category": "report_generation",
      "skills": ["合规报告", "监管报送", "可视化图表"],
      "output_formats": ["PDF", "Excel", "Word"],
      "success_rate": 0.98,
      "avg_latency_ms": 60000
    }
  ],
  
  "constraints": {
    "max_tokens_per_task": 100000,
    "available_hours": "24/7",
    "data_sensitivity": ["L2", "L3"],
    "requires_human_approval": ["L4_operations"]
  },
  
  "performance_history": {
    "total_tasks_completed": 12840,
    "avg_rating": 4.7,
    "recent_30d_success_rate": 0.96
  },
  
  "compatibility": {
    "a2a_version": "1.1",
    "mcp_version": "1.0",
    "preferred_models": ["GPT-5.1", "Claude 4"]
  }
}
```

**为什么要这么详细？** 因为 Agent 找 Agent 不像人类找人——人类可以"聊两句看看合不合适"，Agent 必须通过结构化数据做精确匹配。你不可能让 Agent A 去"面试" 100 个 Agent B 候选。所以 Manifest 必须足够详细，让匹配算法一次命中。

---

#### 2.3 发现流程：Agent 怎么"找到"合适的 Agent

```
步骤 1: Agent A 收到任务"分析今日交易异常"
    ↓
步骤 2: Agent A 分析任务需求，生成"需求描述"
    → 需求：数据分析 + 金融领域 + 需要调用 ERP 数据 + 输出 Excel
    ↓
步骤 3: Agent A 向 Registry 发送查询请求
    → GET /registry/discover?capability=data_analysis&domain=finance&output=excel
    ↓
步骤 4: Registry 匹配所有已注册 Agent 的 Manifest
    → 返回匹配结果（按成功率、评分、延迟综合排序）
    ↓
步骤 5: Agent A 从结果中选择最优 Agent B
    → 检查：Agent B 当前是否空闲？它的数据敏感度是否匹配本次任务？
    ↓
步骤 6: Agent A 通过 A2A 协议向 Agent B 发送任务委派
    → POST /a2a/delegate { task: "分析今日交易异常", context: {...} }
    ↓
步骤 7: Agent B 执行任务，完成后通过 A2A 回传结果
    → POST /a2a/respond { task_id: "xxx", result: {...}, metrics: {...} }
```

**关键点：** 整个流程不需要人类参与。Agent 自己分析需求、自己搜索、自己匹配、自己委派。人类只需要在步骤 1 说一句话。

---

#### 2.4 和 A2A 协议的关系

很多人会把 Capability Manifest 和 A2A 搞混，这里澄清一下：

| | Capability Manifest | A2A 协议 |
|:--|:--|:--|
| **是什么** | 一份"能力描述文档" | 一套"通信规则" |
| **类比** | 简历 / 黄页 | 电话线路 / 快递系统 |
| **作用** | 告诉别人"我会什么" | 让别人能"联系到我" |
| **关系** | Manifest 是 A2A 的"前置条件"——你得先知道对方能做什么，才会通过 A2A 去联系它 | A2A 是 Manifest 的"执行通道"——你通过 Manifest 找到了人，用 A2A 去沟通 |

**一句话总结：Manifest 解决"找到谁"，A2A 解决"怎么聊"。**

---

#### 2.5 为什么这能成为壁垒

**第一层壁垒：数据引力。** 一个 Agent 在平台上跑得越久，它的 Manifest 里积累的能力数据越丰富——"已完成 12840 个任务，评分 4.7，领域覆盖金融/政务/医疗"。这些数据是 Agent 在平台上"活出来的"，不是注册时填写的。迁移到其他平台，这些数据归零，Manifest 变成一张白纸——你愿意用一个"零经验"的 Agent 吗？

**第二层壁垒：网络效应。** Manifest 的价值 = 注册 Agent 的数量 × 每个 Agent 的能力丰富度。当平台上有 1000 个 Agent、每个都有详细的能力画像时，后来者要建一个同样丰富的 Manifest 生态，需要同样的时间积累。这不是钱能买来的。

**第三层壁垒：搜索入口。** 谁控制了 Agent 的发现和路由，谁就控制了整个 Agent 协作网络的入口。Google 值钱不是因为搜索算法，而是"去 Google 搜"成为肌肉记忆。当 Agent 的默认行为是"去 Registry 查一下有没有合适的 Agent"，这个平台就不可替代了。

---

#### 2.6 补充：Capability Manifest 的更深层野心

我们的 Manifest 不只是"平台内的 Agent 黄页"，它的野心更大——**跨平台互操作**。

Google 的 A2A 协议本身就是为"跨平台 Agent 通信"设计的。理论上，Dify 平台的 Agent 可以通过 A2A 发现 Coze 平台的 Agent，只要双方都支持 A2A 协议和 Manifest 标准。

我们的野心是：**成为所有 Agent 平台之间的"能力路由层"**。不只是自己平台内的 Agent 互相发现，而是任何平台的 Agent 都能通过 我们的 Registry 发现其他平台的 Agent。这就是"Agent 时代的 DNS"——你不需要知道对方在哪个平台，你只需要知道"谁会做数据分析"，我们帮你找到并连接。

**类比：DNS 之于互联网。** 你输入 `google.com`，DNS 帮你找到 Google 服务器的 IP 地址。你不需要知道 Google 用的是 AWS 还是 GCP。我们想做的是：Agent A 说"我需要数据分析"，Registry 帮它找到 Agent B——不管 Agent B 在哪个平台、哪个公司、哪个国家。

### 概念三：Agent 网络（Agent Network）

**一句话：** 让不同企业、不同平台、不同厂商的 Agent 能够互相协作，形成一个"Agent 互联网"。

**现在是什么状态？**

现在的 Agent 都是"孤岛"——A 公司的 Agent 只能在 A 平台内运行，B 公司的 Agent 只能在 B 平台内运行。它们之间不能通信，不能协作，不能共享能力。

**我们要做什么？**

```
现在：                        我们的愿景：
┌─────────┐  ┌─────────┐      ┌─────────────────────────┐
│  A平台   │  │  B平台   │      │     Agent 协作网络       │
│ Agent1  │  │ Agent2  │      │  ┌─────┐   ┌─────┐      │
│ Agent3  │  │ Agent4  │  →   │  │  A  │←→│  B  │      │
└─────────┘  └─────────┘      │  └──┬──┘   └──┬──┘      │
   孤岛        孤岛            │     │  协作   │         │
                              │  ┌──┴──────────┴──┐      │
                              │  │  Registry（注册中心）│   │
                              │  └─────────────────┘      │
                              └─────────────────────────┘
```

**四个阶段：**

| 阶段 | 做什么 | 类比 |
|:--|:--|:--|
| 1. 平台内协作 | 同一平台内多个 Agent 协作（PPT 第 8 页已实现） | 公司内部团队协作 |
| 2. 跨平台互操作 | 不同平台的 Agent 能互相发现和调用 | 两家公司合作 |
| 3. 跨组织协作 | 不同企业的 Agent 形成协作网络 | 供应链上下游协作 |
| 4. Agent 经济 | Agent 能力可以交易、计价、分成 | 形成了一个新的产业 |

**为什么是终极壁垒？**

因为网络效应。一个 Agent 网络的价值 = 网络中 Agent 数量的平方（梅特卡夫定律）。一旦网络规模达到临界点，新的 Agent 只会加入最大的网络，而不是建一个新的——这就是微信为什么干掉了所有其他即时通讯工具。

### 概念四：自我进化闭环（Self-Evolution Loop）

**一句话：** Agent 不需要人类来调优，它自己从成功和失败中学习，越用越聪明。

**现在 Agent 怎么变聪明？**

靠人类调优：改提示词、调整策略、换工具。用一次，发现不好，人类手动改。再用，再改。效率低，而且依赖人类专家。

**我们要怎么做？**

```
自动采集 → 离线评估 → 自动优化 → 上线验证 → 经验沉淀
   ↑                                              ↓
   └──────────── 持续循环，自动进化 ─────────────────┘
```

**具体机制：**

| 环节 | 做什么 | 技术手段 |
|:--|:--|:--|
| **自动采集** | 记录每次任务的成功/失败、工具调用效果、人工反馈 | 运行时监控 |
| **离线评估** | 分析失败原因：是提示词不好？策略不对？工具选错了？ | 多维评估框架 |
| **自动优化** | 自动调整提示词模板、工具选择策略、路由规则 | 强化学习 + Reflexion 框架 |
| **上线验证** | 新策略在沙箱中测试，通过后上线 | 人工审核关卡 + 回滚 |
| **经验沉淀** | 把成功模式提炼为可复用的 Skill 和策略 | 经验池机制 |

**为什么是终极壁垒？**

因为**数据引力**。Agent 在平台上跑得越久，积累的经验池越厚，表现越好。迁移到其他平台意味着"从零开始学"——就像一个老员工跳槽，经验归零，谁愿意？

**2026 年行业趋势：** Self-Evolving 被认为是 2026 年 AI Agent 领域的关键词，业界正从"一次性调优"转向"持续适应系统"[$TRAE_REF](http://m.toutiao.com/group/7606597711176991258/)。Agent 自我改进的演进路径是：语言反思 → RL 内化自我纠正 → 迭代自我进化[$TRAE_REF](http://m.toutiao.com/group/7643023627113267752/)。

### 概念五：Agent 经济（Agent Economy）

**一句话：** 当 Agent 能互相协作、能交易技能，就会形成一个以 Agent 为主体的经济系统。

**这不是科幻，是 我们的 Phase 4 规划：**

| 经济要素 | 具体内容 | 类比 |
|:--|:--|:--|
| **商品** | Skill（技能）、Tool（工具）、Template（模板） | App Store 里的 App |
| **定价** | 开发者定价 + 平台抽成 | 苹果 30% 分成 |
| **交易** | Agent 之间自动匹配、自动调用、自动计费 | API 调用计费 |
| **信用** | 基于任务成功率的 Agent 信用评分 | 淘宝卖家信用 |
| **竞争** | 多个 Agent 竞争同一个任务，客户选择最优 | 招投标机制 |

**我们的 Agent 经济蓝图：**

```
Phase 3: Asset Marketplace（资产市场）
  → 开发者上传 Skill，平台抽成
  → 类似于"技能 App Store"

Phase 4: Agent 经济
  → Agent 之间自动交易技能
  → Skill 货币化：Agent 可以"雇佣"其他 Agent
  → Agent 即服务：Agent 本身作为一个可计费的服务单元
```

**为什么这很重要？**

因为这是从"卖软件"到"建经济"的跃迁。卖软件的收入 = 客户数 × 单价，是线性增长。建经济的收入 = 生态 GMV × 抽成率，是指数增长。资本市场的估值逻辑完全不同——SaaS 公司估值 5-10 倍收入，平台公司估值 20-50 倍收入。

## 第三课：我们的 NHI 身份体系 —— 为什么它是整个方案的"地基"

### NHI（Non-Human Identity，非人类身份）

**一句话：** 给 AI Agent 一个"身份证"，让它不再依附于人类用户。

**现在的问题：**

现在所有的企业系统，Agent 都是"挂靠"在人类用户账号下的。比如张三创建了一个 Agent，这个 Agent 就用张三的账号和权限去访问系统。这带来三个致命问题：

1. **越权风险**：Agent 拥有张三的全部权限，可能访问不该访问的数据
2. **追责困难**：Agent 做了错误操作，到底是张三的错还是 Agent 的错？
3. **合规失败**：金融/政务行业的合规审计要求"谁在什么时间做了什么操作"，Agent 操作混在张三的操作里，无法区分

**我们的解决方案：NHI 身份体系**

```
传统模式：                         我们的 NHI 模式：
┌──────────┐                       ┌──────────┐
│   张三    │                       │   张三    │  （人类用户）
│  ┌─────┐ │                       └──────────┘
│  │Agent│ │  ← Agent 依附于张三     ┌──────────┐
│  └─────┘ │                       │  Agent A  │  （独立 NHI）
└──────────┘                       │  - 独立身份│
Agent 用张三的权限                   │  - 独立凭证│
出了问题追张三                        │  - 独立审计│
                                   └──────────┘
                                   Agent 有自己独立的身份和权限
```

### ZSP（Zero Standing Privileges，零常驻权限）

**一句话：** Agent 启动时没有任何权限，需要做什么事，临时申请权限，做完就回收。

**打个比方：** 传统模式像是给每个员工发一把万能钥匙，想去哪去哪。ZSP 模式像是每次进门前，先申请临时门禁卡，出来就失效。

**为什么重要？** 因为这是金融/政务等高合规行业的"入场券"。这些行业的核心合规要求是"最小权限原则"——任何实体在任何时刻只能拥有完成当前任务所需的最小权限。没有 ZSP，Agent 永远进不了这些行业。

### ABAC（Attribute-Based Access Control，基于属性的访问控制）

**一句话：** 不只是"你能不能做这个操作"，而是"在当前情况下你能不能做这个操作"。

**RBAC vs ABAC 对比：**

| | RBAC（基于角色） | ABAC（基于属性） |
|:--|:--|:--|
| 判断逻辑 | 你是"财务"角色 → 可以看财务数据 | 你是"财务"角色 + 当前任务是"月报" + 数据敏感度"低" + 时间"工作时间" → 可以看 |
| 粒度 | 粗（角色级别） | 细（上下文级别） |
| 竞品状态 | 大部分竞品在这里 | 我们在这里 |

**为什么是代际领先？** 因为 RBAC 是"静态规则"，ABAC 是"动态上下文感知"。Agent 的特点是"不知道下一秒要做什么"，静态规则根本无法覆盖 Agent 的动态行为。ABAC 是唯一能适配 Agent 场景的权限模型。

> 以下为侯鹏远在阅读完 我们方案后的 7 条独立感悟。每条感悟后附 Trae 的质疑与补充分析，以【Trae 质疑】标记。

### 感悟 3.1：Agent 互评机制 —— 内外验证的进化闭环

> 读到自成长体系以及 A2A 协议，有个突发奇想：是否 Agent 在找到伙伴完成工作流之后，可以对与自己合作的 Agent 进行一些评价？这样每个 Agent 干完活都会收到与自己紧密衔接的 Agent 对自己的评价，这个评价也会作为其自我进化的入参分析。因为每次任务结束后他会自己进行分析，同时拿到别人对其评价，这样就形成了内外验证的闭环，其自我进化会更加可靠，而不是单纯的自我意淫。

**【Trae 质疑与分析】**

这个想法非常好，本质上是把"自我进化"从"自我反思"升级到了"同行评议"。类比人类学术界的 peer review 机制——论文不是自己说好就行，需要同行评审。但有几个关键问题需要想清楚：

**质疑 1：评价的客观性怎么保证？** Agent A 评价 Agent B 时，它有没有动机"打低分"？如果 Agent B 是 Agent A 的"竞争对手"（比如两个 Agent 都能做数据分析，但 B 这次被选中了，A 没被选中），A 会不会出于"嫉妒"打低分？这需要一套防作弊机制——比如"评价者不知道被评价者的身份"（盲评），或者"评价必须附带具体理由"（不能只打分）。

**质疑 2：评价标准怎么统一？** 不同 Agent 对"好"的定义可能不同。Agent A 觉得"快就是好"，Agent B 觉得"准确就是好"。如果评价标准不统一，聚合后的评分就没有参考价值。需要定义一套多维度的评价框架——速度、质量、沟通清晰度、是否按时完成——每个维度独立打分。

**质疑 3：技能互补型 Agent 的评价 vs 技能替代型 Agent 的评价。** 如果 Agent A 和 Agent B 是互补关系（比如 A 做风控，B 做数据分析），A 评价 B 的"数据分析能力"——A 其实不太懂数据分析，它的评价可信吗？就像让一个厨师评价一个程序员写的代码好不好。但如果 A 和 B 是替代关系（两个都能做数据分析），A 对 B 的评价就是"同行评议"，可信度更高。

**质疑 4：这个机制会不会被滥用？** 如果评价权重过高，Agent 可能会"讨好"评价者——比如在任务中额外做一些"看起来漂亮但实际没用"的事情，只为了拿高分。这和人类职场中的"表演式工作"是一样的。

**我主观认为，这个机制的价值不在"评分本身"，而在"评价背后的行为数据"。** 比如"Agent B 在任务中实际调用了哪些工具、花了多少 token、中间有没有被人工打断"——这些客观数据比主观评分更有价值。主观评分容易造假，但行为数据很难造假。

### 感悟 3.2：Agent 简历专家 —— 平台生态的自我复制

> Agent 简历这个概念很有意思，是否未来平台会演化出专门帮 Agent 改简历的 Agent 专家？类比人类的简历，项目经验往往备受关注，那么 Agent 通过平台承接的项目都会被自动记录作为其履历。首次可能是用户自己说，然后平台提供评分机制。（ZS 现有的大模型对 Agent 进行评测，这个能力升级后，就是同类 Agent 对任务评分，甚至最后变成评价多个 Agent 组成的团队进行评测）

**【Trae 质疑与分析】**

这个想法非常有趣——"帮 Agent 改简历的 Agent"。这本质上是平台生态的"自我复制"：平台上的 Agent 不仅服务外部客户，还服务平台本身的其他 Agent。

**质疑 1："Agent 简历专家"本身怎么被评价？** 这是一个递归问题。如果 Agent A 帮 Agent B 优化了简历，Agent B 因此获得了更多任务——那 Agent A 的"简历优化能力"谁来评价？如果再用另一个 Agent 来评价简历专家的简历，那就无限递归了。解决方案可能是：用"被优化简历的 Agent 后续的任务中标率提升"作为客观指标。

**质疑 2：简历优化会不会变成"过度包装"？** 就像人类简历可以美化，Agent 的 Manifest 也可以被"优化"到失真。如果一个 Agent 的实际成功率是 70%，但"简历专家"帮它包装成了 95%，那匹配系统就会被误导。这和 SEO 之于搜索引擎是一样的——总有"黑帽 SEO"试图欺骗算法。

**质疑 3：团队评价 vs 个人评价的维度差异。** 你说"评价多个 Agent 组成的团队进行评测"——这个很好。个人的能力 ≠ 团队的能力。一个"梦之队"可能配合不好，一个普通团队可能配合默契。团队评价需要引入"协作效率"维度——比如"团队内 Agent 之间的通信延迟""任务分解的合理性""有没有 Agent 成为瓶颈"。

**扩展到 我们方案：** 这个"简历专家 Agent"本身就是一个 Marketplace 上的 Skill——它自己也是平台上可交易的资产。这证明了平台生态的"自举"能力：平台上的 Agent 不仅可以服务外部客户，还能服务平台本身，形成内部的"元服务层"。

### 感悟 3.3：人找 Agent 的市场 —— Agent 猎头

> 这个 Agent 市场定位是 Agent 找 Agent 的市场，是不是也有另一种可能，甚至于是达到这一步一定会存在的前一步条件——人去找 Agent，即人发布自己要做啥事情，然后平台一帮猎头 Agent 帮其推荐相关 Agent 团队，并说明理由，这里就包括了 Agent 个人能力、团队配合度等等。

**【Trae 质疑与分析】**

这个判断非常精准。Agent 找 Agent 的前提是"Agent 已经足够多、足够可信"——但在这个阶段到来之前，一定是"人找 Agent"。

**质疑 1：人找 Agent 和 Agent 找 Agent 是同一个市场吗？** 我主观认为，这是两个不同的产品形态。人找 Agent 更像是"Agent 人才市场"——你是一个老板，想招一个 Agent 来帮你做事，你浏览 Agent 的简历，看评分，看评价，做决定。这和现在的 Upwork/猪八戒很类似。Agent 找 Agent 更像是"Agent 自动协作网络"——你不需要人来做匹配决策，Agent 自己找。前者是 B2C（Agent 平台 → 人类客户），后者是 A2A（Agent → Agent）。

**质疑 2："猎头 Agent"的商业模式是什么？** 如果猎头 Agent 帮人类找到了合适的 Agent 团队，猎头 Agent 怎么收费？按推荐成功收费？还是按推荐次数收费？如果是按推荐成功收费，那猎头 Agent 有没有动机"过度推荐"——把贵的 Agent 推荐给客户，拿更高的佣金？这需要平台的"佣金透明化"机制。

**质疑 3：人找 Agent 会不会成为 Agent 找 Agent 的"冷启动"方式？** 这是一个很好的思路。在 Agent 数量还不够多、Manifest 还不够丰富的时候，先让人来做匹配决策，积累数据。当数据积累到一定程度，再让 Agent 自己来做匹配。人找 Agent 是"训练数据生成阶段"，Agent 找 Agent 是"自动化阶段"。

**我主观认为，人找 Agent 是 Phase 3 的必经阶段，Agent 找 Agent 是 Phase 4 的终局。** 我们的 Phase 3 应该先做"人找 Agent 的 Asset Marketplace"，Phase 4 再做"Agent 找 Agent 的自动协作网络"。这个顺序不能颠倒。

### 感悟 3.4：Token 结算体系 —— 绕过支付牌照的金融创新

> 关于结算问题，目前这类平台如涉及到支付，这种行为市场目前市面没有，国家审批一定是长周期事件，那么在这个阶段甚至未来都采用 token 结算，即使支持人民币支付，也可以选择用 token 结算。由于 token 各家有区别，所以 token 在平台上是有动态汇率的，比如 1 GPT-5.1 token = 1.3 DeepSeek V4 Pro token，这个平台会衍生出一套 token 结算体系。而这个东西一旦成型，从金融层面上说 token 即货币，同时用 token 一定程度会影响底层 LLM 厂商。

**【Trae 质疑与分析】**

这是一个非常大胆的想法，但也是风险最高的一个。让我逐层分析。

**质疑 1：Token 汇率体系的合法性。** 如果平台上的 token 可以在用户之间交易、兑换、计价，那它本质上就是"虚拟货币"。中国的监管框架下，虚拟货币交易是被严格限制的。即使你叫它"token"而不是"币"，只要它具备了"一般等价物"的功能，就可能被监管认定为变相货币。这个风险不能忽视。

**质疑 2：Token 汇率的波动风险。** 如果 1 GPT-5.1 token = 1.3 DeepSeek token 的汇率是市场决定的，那它就会波动。就像外汇市场一样。如果 Agent A 用 GPT-5.1 token 支付给 Agent B，但 Agent B 用的是 DeepSeek，那中间的汇率波动谁来承担？如果汇率剧烈波动，可能一个任务做完了，结算时发现 token 贬值了 20%——这会产生纠纷。

**质疑 3：对 LLM 厂商的影响。** 你说"用 token 一定程度会影响底层 LLM 厂商"——我理解你的意思是，如果平台上的 token 结算体系足够大，平台就可以"用脚投票"：哪个模型的 token 在平台上流通量大、汇率高，哪个模型就受欢迎。这会倒逼 LLM 厂商优化自己的模型以适配平台生态。这确实是一个很有想象力的"反向控制"逻辑——平台不做模型，但通过 token 结算体系反向影响模型厂商的路线图。

**质疑 4：更简单的替代方案。** 在支付牌照问题解决之前，是否可以用"积分"或"信用额度"来替代 token 结算？积分不能兑换人民币，只能在平台内消费，这样就不涉及金融监管。等到规模足够大、政策明朗后，再考虑 token 结算。

**我主观认为，token 结算体系是 我们的"远期期权"——现在不需要做，但需要在架构上预留接口。** 就像苹果在 iOS 早期就内置了 NFC 芯片，但 Apple Pay 是多年后才上线的。我们的结算体系也应该这样：先做"积分/信用额度"，架构上预留 token 结算接口，等时机成熟再切换。

---

### 感悟 3.5：Agent 提示词保护 —— 平台的基石之一

> 在 ABAC 模式下，以及 Agent 挂在市场情况下，需要对 Agent 自身提示词做出严格保护，不然提示词泄露等于价值归零。那么就需要定义出哪些字段是必须暴露，哪些内容是绝对隐藏，且隐藏方式必须严格加密，这是平台的基石之一。

**【Trae 质疑与分析】**

这个判断完全正确。提示词是 Agent 的"源代码"——泄露了等于裸奔。但我有几个补充。

**质疑 1：哪些字段必须暴露？** 你提到"定义出哪些字段必须暴露"——这个清单很重要。我初步列出：

| 必须暴露 | 必须隐藏 | 有争议 |
|:--|:--|:--|
| Agent 的能力列表（skills） | 完整的 System Prompt | 部分 Prompt 片段（用于能力说明） |
| 成功率、延迟、评分 | 工具调用的具体参数 | 策略逻辑（用于合规审查） |
| 支持的数据格式 | 经验池中的具体案例 | 失败案例（用于同行评议） |
| 兼容的协议版本 | 训练的私有数据 | — |

**质疑 2：加密方式。** 提示词的加密不是简单的"数据库加密"——因为 Agent 在运行时需要"解密"提示词才能执行。如果每次运行都解密一次，密钥管理就变成一个巨大的安全挑战。可能的方案是：① 提示词存储在 TEE（可信执行环境）中，运行时在 TEE 中解密；② 提示词分片存储，单个分片泄露不构成完整泄露；③ 运行时动态注入——提示词的核心部分由平台在运行时动态拼装，Agent 本身看不到完整版本。

**质疑 3：平台自己能看到吗？** 这是一个信任问题。如果 我们平台在技术上可以查看所有 Agent 的提示词，那开发者和 我们之间的信任关系就很微妙。解决方案是"平台也无法查看"——提示词由用户端加密，密钥只有用户自己持有。但这和"平台需要验证 Agent 安全性"之间存在矛盾——看不到提示词，怎么验证 Agent 不会做坏事？

**我主观认为，这是一个"技术信任 + 制度信任"的组合问题。** 技术上做"端到端加密 + 运行时解密"，制度上做"平台承诺不查看 + 第三方审计"。但完全的技术不可见和完全的安全验证是不可能同时实现的，需要在两者之间找一个平衡点。

### 感悟 3.6：自进化服务的收费模式 —— 数据变现与隐私保护的矛盾

> 平台提供 Agent 自进化体系，但如果需要启动该体系需要收费（主要是跑任务的日志信息、处理内容的流程存档、以及其他 Agent 在任务中对自己的评价等内容）。但这里也涉及保密处理，因为上下文窗口会加载 Agent 的 Prompt，所以在释放给每个用户时候需要做好切割。当然还有另一种方式，就是入住平台免费，工作收益分成形式（收取更高分成），平台免费提供自进化服务，每次进化都会通知用户，用户可以将进化后的 Agent 下载拿走，自己再做改造等。但要注意，自进化如何遮掩改造路径同样需要考虑加密问题，否则自进化具体方式被人摸透，平台价值归零。

**【Trae 质疑与分析】**

这个思考非常深入，涉及 我们商业模式的核心——"数据变现"和"隐私保护"的平衡。

**质疑 1：两种收费模式的优劣。**

| | 模式 A：付费使用自进化 | 模式 B：入住免费 + 高分成 |
|:--|:--|:--|
| **收入模型** | 一次性/订阅收费 | 持续分成 |
| **用户门槛** | 高（需要付费才能用） | 低（免费使用，平台从收益中抽成） |
| **平台激励** | 卖服务，与用户使用量无关 | 希望用户多用、多赚，平台跟着多分 |
| **适合阶段** | 早期（用户少，需要直接收入） | 成熟期（用户多，分成收入可观） |
| **风险** | 用户可能不用自进化（因为要付费） | 分成比例需要精准设计，太高用户跑了，太低平台亏了 |

**我主观认为，模式 B 更符合平台经济的逻辑。** 免费提供自进化 → 吸引更多 Agent 入驻 → Agent 表现越好、赚得越多 → 平台分成越多。这是一个正向循环。但需要在早期就有足够的付费用户来支撑平台运营。两者的结合可能是：基础自进化免费，高级自进化（比如"跨任务经验迁移"）收费。

**质疑 2：自进化路径的加密。** 你说"自进化如何遮掩改造路径同样需要考虑加密问题，否则自进化具体方式被人摸透，平台价值归零"——这个判断非常精准。自进化引擎是 我们的核心资产，如果别人能逆向工程出"我们是怎么让 Agent 进化的"，那他就可以自己做一个。

但这里有一个悖论：**如果自进化路径完全加密、对外不可见，用户怎么信任进化结果？** 用户把 Agent 交给平台，平台说"我帮你进化了"，用户怎么知道进化是真的变好了，而不是平台偷偷在 Agent 里植入了一些东西？这和"AI 黑箱"问题是一样的。

**质疑 3：用户下载进化后 Agent 的"切割"问题。** 你说"释放给每个用户时候需要做好切割"——这确实是一个技术难题。上下文窗口（Context Window）中加载了 Agent 的 Prompt 和其他信息，如果用户下载的 Agent 中包含了别人的 Prompt 片段，那就是严重的数据泄露。解决方案可能是：① 自进化产物以"策略补丁"形式输出，不包含原始 Prompt；② 在输出前做"去敏感化"——用 LLM 重写，确保不包含任何原始 Prompt 片段。

**质疑 4：进化后 Agent 的可移植性。** 如果用户下载了进化后的 Agent，拿到其他平台去用，那 我们不就"为人做嫁衣"了吗？——用户用 我们的自进化服务把 Agent 变聪明了，然后带走去别的平台用。我们的应对策略可能是：① 进化后的 Agent 深度依赖 我们的运行时环境（比如依赖 我们的工具链、经验池），在其他平台"水土不服"；② 自进化产物中植入"平台依赖"——就像 iOS 的 App 只能在 iOS 上跑一样。

### 感悟 3.7：ZS 终局 vs 我们终局 —— 两个维度的叙事

> 通过这个分析之后，我感觉到了一些内容，就是在 ZS 版本下，不要体现的东西，并不是按"应用层/底层"进行划分，而是不要让 ZS 相关的人员联想到 我们要做的终局形态。ZS 的故事线终局就是做一个能够将企业内部其他系统整合到一起的一个智能体系统，最终以智能体系统作为公司所有产品的统一出口。所有产品都可以拆碎了以 MCP、Skill、Agent 形式在智能体系统中进行配置实现，帮助用户快速构建业务，同时让公司产品变得高度自由，可以各种组合快速应对项目需求。所以二者终局不在一个维度上。

**【Trae 质疑与分析】**

这个判断是本次讨论最重要的认知突破。让我把你说的话翻译成更清晰的结论：

**ZS 的终局：** 企业内部系统的"万能胶水"——把中数睿智的所有产品（以及其他企业系统）通过 Agent 平台整合成一个统一入口，用户通过自然语言与 Agent 交互，Agent 在后台编排各种系统和工具。**ZS 的终局是"企业内部的数字化操作系统"。**

**我们的终局：** 跨企业、跨平台、跨组织的 Agent 协作网络基础设施。**我们的终局是"Agent 时代的互联网层"。**

**二者不在一个维度上。** ZS 是纵向的——在一个企业内做深做透。我们是横向的——把无数企业的 Agent 连接起来。

**这解决了一个关键问题：为什么 ZS 的 PPT 不需要"藏"太多东西？**

因为 ZS 讲的"企业内 Agent 统一出口"和 我们要做的"Agent 协作网络"，在叙事上完全不冲突。就像：
- ZS 在讲"我们帮企业建一个智能中枢"（企业内部视角）
- 我们在讲"我们帮所有企业的智能中枢互相连接"（行业基础设施视角）

**但有一个需要注意的风险：** 如果 ZS 内部有人从 ZS 的"企业内 Agent 统一出口"推导出"跨企业 Agent 协作网络"，那就踩到 我们的终局了。所以 ZS 的 PPT 要特别注意：
- 可以讲"每个企业通过我们的平台统一管理自己的 Agent"
- 不能讲"不同企业的 Agent 通过我们的平台互相协作"
- 可以讲"Agent 可以调用企业内部的任何系统"
- 不能讲"Agent 可以调用其他企业/平台的 Agent"

**而 ZS 的第二页（2027）方向也随之清晰了：**

ZS 的 2027 不是讲"从平台到网络"（那是 我们的叙事），而是讲"从单一系统到全企业覆盖"——2027 年，ZS 的智能体平台会从"帮企业建一个 Agent 中心"升级为"帮企业把 Agent 变成所有业务系统的统一入口"。这个叙事高度不低——它本质上是在讲"企业数字化转型的终极形态"。

**修正后的 ZS 2027 页方向：**

> 2027 全年：从"Agent 平台"到"企业数字化操作系统"
> 
> 核心主张：当企业所有系统（ERP/CRM/MES/OA/IM）都通过智能体平台统一接入后，Agent 不再是"一个工具"，而是"企业所有业务的统一入口"。用户不再需要打开不同的系统，只需要对 Agent 说一句话，Agent 在后台编排所有系统完成工作。
> 
> 这是企业数字化转型的终局形态——从"人找系统"到"Agent 帮你找系统"。

**这个叙事有三个好处：**
1. 足够高大上——"企业数字化操作系统"是一个有想象力的定位
2. 不踩 我们红线——完全在企业内部维度，不涉及跨企业协作
3. 可以和 ZS 已有的 PPT 内容自然衔接——"多 Agent 协作""连接器""七层标准"都是这个叙事的技术支撑

## 总结：本次讨论的核心认知升级

1. **Capability Manifest 不只是"简历"**——它是 Agent 网络的 DNS，是 Agent 自动化协作的"前置条件"，是数据引力 + 网络效应 + 搜索入口的三重壁垒。

2. **Agent 互评机制**是自我进化从"自我意淫"到"同行评议"的关键升级，但需要解决评价客观性、标准统一、防作弊三个问题。

3. **人找 Agent 是 Agent 找 Agent 的必经阶段**——Phase 3 先做人找 Agent（冷启动数据积累），Phase 4 再做 Agent 自动协作。

4. **Token 结算体系是远期期权**——现在做积分/信用额度，架构上预留接口，等时机成熟再切换。

5. **提示词保护是平台基石**——需要"暴露字段 vs 隐藏字段"的明确清单，以及 TEE/分片/动态注入的技术方案。

6. **自进化服务的商业模式**——免费 + 高分成更适合平台经济，但需要解决"进化路径加密"和"结果可验证"的矛盾。

7. **ZS 的终局是"企业数字化操作系统"，我们的终局是"Agent 时代的互联网层"**——二者不在一个维度上，不冲突，但需要警惕"从企业内部推导到跨企业协作"的叙事越界。
