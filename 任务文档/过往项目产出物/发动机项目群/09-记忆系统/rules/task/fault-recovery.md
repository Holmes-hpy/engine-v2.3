# 故障恢复规则

> **项目**: v1.3.0 (v1.3.0)
> **生成时间**: 2026-07-16T07:00:00+08:00
> **启动包版本**: 1.3.0

## 1. 概述

本规则定义任务执行过程中的故障检测、分级响应和恢复策略。故障恢复的目标是：在最小人工介入下，使系统恢复到可继续执行的状态。

## 2. 故障分级

### 2.1 故障等级定义

| 等级 | 名称 | 影响范围 | 响应时间 |
|------|------|----------|----------|
| L1 | 致命 (Fatal) | 整个系统不可用 | 立即 |
| L2 | 严重 (Critical) | 当前任务完全失败 | 5 分钟内 |
| L3 | 一般 (Major) | 当前任务部分失败 | 15 分钟内 |
| L4 | 轻微 (Minor) | 非核心功能受影响 | 下次执行时 |

### 2.2 故障等级判定

```
IF 磁盘空间耗尽 OR 数据库损坏 OR 核心规则丢失 THEN L1
IF 任务执行抛出未捕获异常 AND 无检查点 THEN L2
IF 任务执行抛出异常 BUT 有检查点 THEN L3
IF 输出格式不规范 OR 日志写入失败 THEN L4
```

## 3. 检查点机制

### 3.1 检查点创建

检查点在以下时机自动创建：

| 时机 | 检查点类型 | 内容 |
|------|-----------|------|
| 任务状态变更 | 状态检查点 | 当前任务完整状态 JSON |
| 每 N 分钟 | 定时检查点 | 所有活跃任务快照 |
| 关键步骤完成 | 步骤检查点 | 该步骤的输出和中间状态 |

### 3.2 检查点间隔

```
CHECKPOINT_INTERVAL = 300 秒
```

默认值为 300 秒（5 分钟）。

### 3.3 检查点存储

```
tasks/checkpoints/{task_id}/
├── checkpoint-{序号}-{timestamp}.json
└── metadata.json
```

## 4. 恢复策略

### 4.1 L1 恢复策略

L1 恢复操作清单（按顺序执行）：
1. [ ] 立即停止所有正在执行的任务，记录当前任务状态快照
2. [ ] 保存故障现场数据到 `logs/fault/scenes/{timestamp}/`
3. [ ] 从 `tasks/checkpoints/` 中查找最近的健康检查点
4. [ ] 执行回滚到检查点
5. [ ] 验证回滚后的系统状态（运行 `scripts/health_check.py`）
6. [ ] 如回滚失败，升级到人工介入（参见第 7 节人工介入）
7. [ ] 通知所有依赖方系统已回滚
8. [ ] 创建故障分析任务（P1 优先级，24 小时内完成）

### 4.2 L2 恢复策略

```
1. 标记当前任务状态为 failed
2. 记录故障详情到任务日志
3. 检查是否存在检查点
   - 存在 → 从检查点恢复，状态设为 pending，准备重试
   - 不存在 → 任务从头开始
4. 重试计数加 1
5. 如重试次数 >= 3，标记为永久失败
```

### 4.3 L3 恢复策略

```
1. 从最后检查点恢复任务状态
2. 跳过已完成的步骤
3. 从失败步骤继续执行
4. 记录恢复事件
```

### 4.4 L4 恢复策略

```
1. 记录 WARNING 日志
2. 跳过故障步骤，继续执行
3. 在交接报告中标注此问题
```

## 5. 重试策略

### 5.1 最大重试次数

```
MAX_RETRY_COUNT = 3
```

默认值为 3。

### 5.2 退避策略

| 重试次数 | 等待时间 |
|----------|----------|
| 第 1 次 | 立即 |
| 第 2 次 | 30 秒 |
| 第 3 次 | 2 分钟 |

### 5.3 重试限制

以下情况不重试，直接标记为永久失败：

- 语法错误（代码/配置）
- 权限不足
- 磁盘空间不足
- 依赖文件缺失

### 5.4 重试计数持久化

重试计数存储在任务状态 JSON 的 `retry_count` 字段中（参见规则 T1 状态机规范），确保重试计数在状态流转中不丢失。

## 6. 故障日志

所有故障记录到 `logs/fault-recovery.log`：

```
[YYYY-MM-DD HH:MM:SS] [L{等级}] [TASK-ID] 故障描述
  └─ 恢复策略: {策略}
  └─ 检查结果点: {是/否}
  └─ 重试次数: {N}/{MAX_RETRY_COUNT}
  └─ 结果: {成功/失败/人工介入}
```

## 7. 人工介入触发条件

以下情况必须请求人工介入：

1. 同一任务连续失败超过 3 次
2. L1 故障无法自动恢复
3. 检查点文件损坏或丢失
4. 检测到数据不一致（如状态机非法流转）
5. 系统资源持续不足超过 10 分钟

## 8. 故障恢复演练机制

### 8.1 演练周期

每季度至少执行一次完整的故障恢复演练，覆盖 L1 和 L2 级别。

### 8.2 演练流程

1. 制定演练计划（包含演练场景、预期结果、评估标准）
2. 在隔离环境中模拟故障
3. 按照恢复策略执行恢复操作
4. 记录实际耗时和偏差
5. 演练结束后 48 小时内产出《故障恢复演练报告》

### 8.3 演练报告格式

```markdown
# 故障恢复演练报告
- 演练日期: YYYY-MM-DD
- 演练级别: L1/L2
- 演练场景: {描述}
- 是否成功: 是/否
- 预期耗时: {时间}
- 实际耗时: {时间}
- 偏差分析: {描述}
- 改进项: {列表}
```

### 8.4 演练记录存储

演练报告保存在 `logs/drills/` 目录，命名格式：`DRILL-{级别}-{YYYYMMDD}.md`

### 8.5 演练失败处理

如果演练失败（恢复未在预期时间内完成），自动创建一个 P1 优先级的修复任务，目标是在下一次演练前修复恢复流程中的问题。

### 8.6 推荐演练场景

| 级别 | 演练场景 | 预期结果 | 验证要点 |
|------|----------|----------|----------|
| L1 | 删除 `.memory/knowledge.db` 后恢复 | 从检查点重建数据库 | 数据完整性、索引重建 |
| L1 | `rules/` 目录部分文件损坏 | 从备份或重写恢复 | 规则文件版本一致性 |
| L2 | 活跃任务 JSON 文件丢失且无检查点 | 标记为 failed 并重新创建 | 状态流转正确、依赖方通知 |
| L2 | 检查点文件损坏（部分可读） | 从最近可读检查点恢复 | 数据丢失范围可控 |
| L3 | 输出文件格式不规范 | 自动修复或标记为 draft | 格式修复后可正常读取 |
