# 任务生命周期规范

> **项目**: v1.3.0 (v1.3.0)
> **生成时间**: 2026-07-16T07:00:00+08:00
> **启动包版本**: 1.3.0

## 1. 概述

本规则定义任务从创建到关闭的完整生命周期，包括创建、执行、评审、完成和归档各阶段的标准操作流程。

## 2. 生命周期阶段

```
创建 → 分配 → 执行 → 评审 → 完成 → 交接 → 归档
```

## 3. 阶段详解

### 3.1 创建 (Create)

**触发条件**: 用户提出新需求或系统生成子任务

**创建标准**:
- 任务必须有明确的标题（不超过 100 字）
- 任务必须有可验证的完成标准
- 任务必须指定优先级（参见任务状态机规则）

**创建输出**:
- 任务定义文件: `tasks/active/TASK-{NNNN}-{标题}.json`
- 初始状态: `pending`

### 3.2 分配 (Assign)

**触发条件**: 任务创建后或依赖满足后

**分配逻辑**:
1. 检查当前活跃任务数是否达到上限 (10)
2. 如未达上限，分配可用 Agent
3. 分配完成后，任务状态由 `pending` 变更为 `in_progress`（参见规则 T1 状态机）
4. 如已达上限，将任务状态由 `pending` 变更为 `blocked`，等待资源释放

### 3.3 执行 (Execute)

**触发条件**: 任务状态变为 `in_progress`

**执行规范**:
1. 执行前读取相关规则文件
2. 按任务定义逐步执行
3. 每完成一个子步骤，更新任务状态文件

**执行 · 监控（子阶段）**:
- 任务执行时间是否异常（超过预期 2 倍）
- 任务输出是否符合预期格式
- 任务是否产生新的依赖
- **定期检查检查点完整性**（参见规则 T3 检查点机制）
- **分析检查点以发现执行异常**（如连续多个检查点无进展，触发 T3 故障分级）

**异常处理**:
- 执行时间异常 → 记录 WARNING，询问是否继续
- 格式异常 → 立即暂停，修正后继续
- 新依赖 → 状态变更为 `blocked`，创建依赖任务
- 检查点缺失 → 触发 T3 故障恢复流程（参见规则 T3）

### 3.4 评审 (Review)

**触发条件**: 任务执行完成，提交评审

**评审流程**:
1. 执行方完成任务后，状态变更为 `reviewing`
2. 评审方（用户或上级 Agent）检查任务产物
3. 评审方根据检查标准给出评审结论

**评审结论**:

| 结论 | 状态流转 | 说明 |
|------|----------|------|
| 通过 | reviewing → completed | 评审通过，进入完成阶段 |
| 不通过 | reviewing → in_progress | 返回修改，保留评审意见 |
| 严重问题 | reviewing → failed | 发现无法修复的严重问题 |

**评审记录**:
- 评审结论记录到任务 JSON 的 `review_result` 字段
- 评审意见记录到 `review_comment` 字段
- 评审事件记录到 `tasks/lifecycle.log`

### 3.5 完成 (Complete)

**完成标准**:
- [ ] 评审已通过（状态从 reviewing 转为 completed）
- [ ] 所有预期输出已生成
- [ ] 输出符合格式规范
- [ ] 无未处理的错误

**完成动作**:
1. 更新任务状态为 `completed`
2. 记录完成时间
3. 生成交接报告（参见交接契约规则 O2）

### 3.6 交接 (Handoff)

**触发条件**: 任务完成或 Agent 切换

**交接流程**:
1. 生成交接报告（参见规则 O2 交接契约）
2. **验证交接报告完整性**（参见 O2 自我验证检查清单）
   - 验证通过 → 进入下一步
   - 验证不通过 → 状态变更为 `handoff_incomplete`，要求执行方补充
3. 确保所有产物可访问
4. 更新相关任务依赖状态

**交接失败处理**:
- 标记任务状态为 `handoff_incomplete`
- 要求执行方在 24 小时内补充交接报告
- 如执行方不可用，由接收方基于现有信息逆向生成交接报告
- 逆向交接时接收方状态为 `in_progress`

### 3.7 归档 (Archive)

**触发条件**:
- 任务完成后 24 小时
- 或用户显式要求归档

**归档动作**:
1. 移动任务文件到 `tasks/completed/`
2. 压缩相关检查点（保留最近 3 个）
3. 更新任务索引

## 4. 任务存活时间

任务存活时间按优先级差异化设置，**仅累计 `in_progress` 状态的时长**：

| 优先级 | 允许执行时长 | 说明 |
|--------|-------------|------|
| critical | 24 小时 | 必须在一天内完成 |
| high | 72 小时 | 3 天内完成 |
| normal | 168 小时 (7 天) | 默认值 |
| low | 336 小时 (14 天) | 可延后处理 |

**计时规则**：
- 任务创建时根据优先级设置 `max_execution_seconds` 字段
- 每次进入 `in_progress` 状态时开始累计，离开时暂停累计
- 任务 JSON 中通过 `in_progress_seconds` 字段记录已累计执行时长
- 当 `in_progress_seconds` 达到 `max_execution_seconds` 的 75% 时触发超时预警
- 当 `in_progress_seconds` 达到 `max_execution_seconds` 时，任务自动进入 `blocked` 状态

## 4.1 超时预警和升级流程

- 执行时长达到 75% 时触发"即将超时"告警（写入 logs/ 并通知相关 agent）
- 执行时长达到 100% 时任务自动进入 `blocked` 状态
- 超时记录写入 `logs/timeout/` 目录
- 超时任务创建 P1 优先级的分析任务

## 6. 任务间关系

### 6.1 父子任务

- 父任务可以包含多个子任务
- 父任务在所有子任务完成后才能标记为 completed
- 任一子任务 failed 可导致父任务 blocked

### 6.2 依赖任务

- 任务 A 依赖任务 B 表示 A 在 B 完成后才能开始
- 依赖关系在任务创建时声明
- 依赖任务失败会自动阻塞依赖方

### 6.3 关系记录

任务关系记录在任务 JSON 的 `dependencies` 和 `subtasks` 字段中。
