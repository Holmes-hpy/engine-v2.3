# 可研报告智能体团队方案 v1.1

> 基于AgentScope"智驭·智能体操作系统"的企业投资项目可行性研究报告自动编写团队
> 版本：v1.1 | 日期：2026-07-16 | 状态：已修正

---

## 一、方案概述

### 1.1 目标

在"智驭·智能体操作系统"平台上，构建一个由Leader自主编排的智能体团队，能够根据用户提供的材料（可能不完整），自动完成符合国家发改委《企业投资项目可行性研究报告编写参考大纲》（2023年版）要求的10章可研报告编写，总字数约28,500字。

### 1.2 定位

本方案是**生产级**智能体团队方案，核心特点是：

- **自主编排**：Leader不是执行预定义工作流，而是根据输入材料情况，自主决定创建哪些Worker、以什么顺序执行
- **数据驱动**：材料齐全时直接写作，材料缺失时通过MCP接口和联网检索补全，严格遵循 U>M>W 优先级
- **质量兜底**：三层质检 + 三重截断保护 + 问题分级迭代，确保输出合规

### 1.3 核心设计理念

| 理念 | 说明 |
|------|------|
| **SKILL即宪法** | Leader的所有行为准则、全体团员的花名册、岗位说明书、工具箱清单，全部写在一个核心SKILL文件中。Leader通过加载这个SKILL来"知道"该干什么 |
| **细粒度分工** | 每章一个专职Writer，各司其职，避免单Agent处理多章导致的上下文污染和字数失控 |
| **数据准备融入流程** | 不设独立的Phase 1/Phase 2，Leader统一编排Parser和Writer的执行顺序 |
| **缺失标记不造假** | 数据来源优先级 U>M>W，三级都拿不到的数据标记【待补充】，财务数据零容忍估算 |
| **终态依赖显式化** | 每个Writer明确声明依赖哪些信息表，Leader据此编排并行/串行执行 |

### 2.2 执行阶段划分

团队执行分为**三个阶段**，由Leader自主编排：

| 阶段 | 参与者 | 并行度 | 产出 |
|------|--------|--------|------|
| **阶段一：数据准备** | Parser-A, Parser-B, Parser-C, Parser-D | 4个Parser并行 | 4份信息表文件 |
| **阶段二：报告写作** | Writer-1 ~ Writer-8 | 最多8个Writer并行（实际受信息表依赖约束） | 8份章节草稿（.txt） |
| **阶段三：整合交付** | Writer-9 → Integrator | 严格串行 | 第9章 + 完整Word文档 |

### 3.2 Leader行为规范

Leader加载SKILL后，必须严格按照以下步骤执行：

#### 步骤1：确认输入

Leader首先检查用户会话中的输入材料：

```
检查清单：
1. 是否有材料包文件？（扫描用户上传的docx/xlsx/pdf文件列表）
2. 是否有项目说明文档？（识别项目方案书/产品规划/白皮书/产品手册等）
3. 上述文件分别落入哪个Parser的职责范围？

输出：一份"材料分配清单"，格式如下：
- Parser-A（财务模块）：[文件列表] 或 [无]
- Parser-B（工商股权）：[文件列表] 或 [无]
- Parser-C（业务技术）：[文件列表] 或 [无]
- Parser-D（项目说明）：[文件列表] 或 [无]

注意：如果某个Parser没有对应材料，仍然需要创建该Parser，
但该Parser将仅通过MCP接口和联网检索获取数据，并在信息表中标注数据来源。
```

#### 步骤2：创建Parser团队

根据材料分配清单，创建4个Parser Worker（全部创建，无论有无材料）：

```
创建顺序：Parser-A、Parser-B、Parser-C、Parser-D（4个并行创建）
每个Parser的创建消息包含：
- 职责说明（从SKILL中的岗位说明书提取）
- 需要处理的文件列表
- 输出文件路径
- 可用的MCP接口列表（如果需要补全数据）
```

#### 步骤3：TeamWait等待Parser完成

```
调用TeamWait，等待4个Parser全部完成。
超时处理：如果某个Parser超时（>5分钟），Leader检查该Parser是否已有部分输出，
如果有则继续，如果没有则标记该信息表为"空"，让Writer自行通过MCP/联网补全。
```

#### 步骤4：检查信息表完整性

```
读取4份信息表，检查关键数据字段是否填充：
- 财务信息表：至少有企业名称、主营业务收入、净利润
- 工商信息表：至少有企业全称、统一社会信用代码、注册资本
- 业务信息表：至少有行业分类、主要产品/服务
- 项目说明表：至少有项目名称、项目类型、建设内容概述

如果关键字段缺失：
1. 优先通过MCP接口补全（如search_company_id获取企业ID，再调用其他接口）
2. MCP无法补全的，标记【待补充】，允许Writer在写作时通过联网检索尝试获取
```

#### 步骤5：创建Writer团队

根据信息表就绪情况，分批创建Writer：

```
第一批（可并行，依赖信息表已就绪）：
  Writer-1, Writer-2, Writer-3, Writer-4, Writer-5, Writer-6
  前提：info_table_finance.md, info_table_corporate.md, info_table_business.md 已就绪

第二批（需等Parser-D完成）：
  Writer-7, Writer-8
  前提：info_table_project_desc.md 已就绪

创建每个Writer时，在消息中传递：
- 该Writer需要读取的信息表文件路径
- 该Writer负责的章节编号和标题
- 字数要求
- 该章节特有的注意事项
```

#### 步骤6：TeamWait等待Writer-1~8完成

```
等待第一批和第二批Writer全部完成。
对于每个Writer的输出，Leader做简单检查：
- 文件是否存在
- 字数是否在目标范围±20%内
- 是否包含"truncated"字样（如有，标记需重试）
```

#### 步骤7：创建Writer-9

```
Writer-9是结论章，需要读取前8章的完整输出。
创建Writer-9时传递：
- chapters/chapter_1.txt ~ chapters/chapter_8.txt 的文件路径
- 明确指示：综合前8章核心结论，提炼项目可行性判断
```

#### 步骤8：TeamWait等待Writer-9完成

#### 步骤9：创建Integrator

```
Integrator负责：
1. 读取全部9章输出
2. 执行三层质检
3. 生成Word文档
创建Integrator时传递：
- chapters/chapter_1.txt ~ chapters/chapter_9.txt 的文件路径
- Word渲染样式要求
- 质检标准
```

#### 步骤10：TeamWait等待Integrator完成 → 交付

```
向用户报告完成状态，提供：
1. Word文档下载路径
2. 质检报告摘要
3. 标注了【待补充】的数据项清单（提醒用户手动补充）
```

### 3.4 Leader禁止事项

> 以下行为Leader**绝对禁止**，违反将导致报告质量失控：

1. **禁止跳过信息表检查**：必须在创建Writer前读取并验证信息表完整性
2. **禁止修改Writer的输出内容**：Leader只做状态检查，不修改文本
3. **禁止在Writer-9之前创建Integrator**：结论章必须在整合之前完成
4. **禁止让Writer跨章写作**：每个Writer只能写自己负责的那一章
5. **禁止省略任何Parser**：即使没有材料，也要创建Parser（空信息表 > 无信息表）
6. **禁止使用财务估算值**：如果财务数据缺失，标记【待补充】，不得自行编造
7. **禁止在SKILL定义之外创建Worker**：只能创建agent_templates中定义的14个角色
8. **禁止并行创建Writer-9和Integrator**：必须等Writer-9完成后才创建Integrator
9. **禁止忽略truncated输出**：检测到truncated时，必须要求该Writer重试
10. **禁止修改核心SKILL内容**：Leader运行时不得修改SKILL文件本身

## 四、数据准备阶段设计

### 4.1 Parser Worker职责分工

#### 4.1.1 Parser-A：财务模块

**职责**：解析所有与财务相关的材料，输出结构化财务信息表。

**输入文件识别规则**：

| 文件类型 | 示例文件名 | 处理方式 |
|----------|-----------|----------|
| 审计报告 | *审计报告*.pdf | 提取近3年审计意见、关键财务数据 |
| 财务报表 | *财务报表*.xlsx | 提取资产负债表、利润表、现金流量表 |
| 财务尽调 | *财务尽调*.docx | 提取财务分析结论、异常事项 |
| 5年预测 | *预测*.xlsx / *forecast*.xlsx | 提取收入/成本/利润预测数据 |

**输出文件**：`parsed/info_table_finance.md`

**输出格式规范**：

```markdown
# 财务信息表

## 数据来源标注
- 审计报告：[文件名] / [未提供]
- 财务报表：[文件名] / [未提供]
- 财务尽调：[文件名] / [未提供]
```

## 六、整合交付阶段设计

### 6.1 Integrator Worker职责

Integrator是团队的"终审官"，负责将9个Writer的输出整合为一份完整的Word文档。

**核心职责**：

1. **读取全部章节**：chapter_1.txt ~ chapter_9.txt
2. **执行三层质检**（详见6.2）
3. **发现问题则分级处理**（详见6.2）
4. **生成Word文档**（详见6.3）
5. **输出质检报告**

### 6.2 三层质检规范

#### 第一层：P0级 - 格式质检（强制通过）

```
检查项：
1. 二级标题完整性：43个二级标题是否全部存在（一字不差匹配）
2. 字数检查：每章字数是否在目标±20%范围内
3. 截断检测：是否包含"truncated"字样
4. 格式规范：是否使用了纯文本表格（使用竖线|分隔列）
5. 【待补充】统计：统计全文【待补充】标记数量

P0级不通过的处理：
- 二级标题缺失 → 标记为P0问题，要求对应Writer重写该章
- 字数偏差>20% → 标记为P0问题，要求对应Writer调整
- truncated检测 → 要求对应Writer重写（最多3轮）
- 表格格式不统一 → Integrator统一格式化
```

#### 第二层：P1级 - 单章质量检查

```
检查项（针对每一章）：
1. 逻辑连贯性：段落之间是否有逻辑跳跃
2. 数据一致性：同一数据在不同章节中是否矛盾
3. 论证充分性：结论是否有数据支撑
4. 语言规范性：是否使用专业、规范的工程咨询语言

P1级不通过的处理：
- 标记为P1问题，记录问题描述
- 要求对应Writer修正（最多2轮）
- 2轮后仍不通过，Integrator自行微调（措辞优化，不改数据）
```

#### 第三层：P2级 - 结构完整性检查

```
检查项：
1. 章节顺序：10章是否按标准顺序排列
2. 前后引用：各章之间的引用是否一致
3. 结论呼应：第9章结论是否与各章内容一致
4. 附表附图：第10章（附表附图附件）是否包含在第9章Writer输出中

P2级不通过的处理：
- Integrator自行调整结构
- 涉及内容修改的，标记为P2问题并记录
```

#### 问题分级与迭代上限

```
迭代规则：
- 最多执行3轮质检迭代
- 第1轮：P0 + P1 + P2 全检
- 第2轮：仅检查第1轮发现的问题
- 第3轮：仅检查第2轮仍未解决的问题

最终处理：
- 3轮后仍有P0问题 → 报告Leader，Leader向用户报告
- 3轮后仍有P1问题 → Integrator自行修正并记录
- 3轮后仍有P2问题 → 交付并在质检报告中说明
```

```markdown
### 4.2 字数校验

### 4.3 truncated检测重试
```

## 九、关键设计决策记录

### D-01：Writer拆分策略 → 选择方案B（细粒度）

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| Writer拆分粒度 | A. 按主题分3-4个Writer | B. 每章一个Writer，共9个 | **选定B** |

**选择理由**：

1. **上下文隔离**：每章一个Writer，避免不同章节的内容在同一个上下文中互相干扰。比如第6章的财务计算逻辑不会影响第2章的行业分析逻辑。
2. **并行加速**：细粒度拆分后，最多8个Writer可以并行执行（第1-6章 + 第7-8章两批），大幅缩短总执行时间。
3. **容错隔离**：如果某个Writer失败或输出质量差，只需重试该Writer，不影响其他章节。
4. **字数可控**：每个Writer只需关注自己章节的字数目标（2,200~4,000字），比一个Writer处理多章更容易控制总字数。
5. **质检定位**：质检时可以直接定位到具体Writer，问题归属清晰。

**代价**：Worker总数从7-8个增加到14个（4个Parser + 9个Writer + 1个Integrator），Leader需要管理更多的Worker。但Leader的行为由核心SKILL控制，管理复杂度可控。

### D-02：数据准备归属 → 选择方案C（融入团队流程）

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 数据准备归属 | A. 独立Phase 1 | B. 独立Agent（非Worker） | C. 融入团队流程，Leader统一编排 | **选定C** |

**选择理由**：

1. **材料不确定性高**：用户可能提供全套材料，也可能只提供一个项目说明文档，甚至什么都不提供。固定的Phase 1无法适应这种不确定性。
2. **按需创建**：Leader可以根据实际材料情况，只创建有意义的Parser（但按照规则，即使无材料也要创建，输出空信息表）。
3. **并行优化**：Parser之间无依赖关系，可以全部并行创建和执行，不需要串行等待。
4. **减少阶段间耦合**：不区分Phase 1/Phase 2，避免阶段切换时的数据传递开销和状态管理复杂度。
5. **Leader自主编排是平台核心能力**：既然平台特色就是Leader自主编排，就应该充分利用这个能力，而不是退回预定义工作流。

### D-03：第6章财务方案 → 独占Writer

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 第6章归属 | A. 与其他章合并给一个Writer | B. 独占一个Writer | **选定B** |

**选择理由**：

1. **字数最多**：第6章目标4,000字，是所有章节中最长的，需要专用的上下文空间。
2. **计算复杂**：需要执行IRR、NPV、投资回收期、盈亏平衡点、敏感性分析等财务计算，需要专门的Prompt引导。
3. **数据敏感**：财务数据零容忍估算，需要最严格的质量控制。独占Writer可以在Prompt中嵌入最严格的约束。
4. **数据依赖集中**：第6章几乎只依赖info_table_finance.md，与其他章节的信息表依赖不同，合并反而增加不必要的数据加载。

### D-04：第9章结论 → 专用Writer-9读前8章

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 第9章归属 | A. Integrator顺带写 | B. 专用Writer-9 | **选定B** |

**选择理由**：

1. **窗口压力评估**：前8章总计约26,000字，在当前LLM上下文窗口（通常128K tokens，约10万汉字）内完全可以一次性读取。26,000字约占用26%的窗口，剩余空间足够生成2,500字的结论。
2. **职责分离**：Integrator的核心职责是整合和质检，不应该同时承担写作任务。Writing和Integrating是两种不同能力。
3. **质量保障**：Writer-9专注写好结论，Integrator专注质检和渲染，各司其职。
4. **迭代便利**：如果结论质量不好，只需重试Writer-9，不需要重跑整个Integrator流程。

### D-05：Parser-D独立存在 → 专门解析项目说明文档

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 项目说明文档处理 | A. 并入Parser-C | B. 独立Parser-D | **选定B** |

**选择理由**：

1. **信息维度不同**：Parser-C处理的是"企业现状"（公司是什么、做什么、行业怎样），Parser-D处理的是"项目规划"（要建什么、怎么建、预期效果）。两者是不同维度的信息。
2. **输出定向不同**：Parser-D的输出明确指向第7章（影响效果分析）和第8章（风险管控方案），这两个章节需要的素材（项目的社会/经济/环境影响、项目风险识别）在"企业现状"材料中很难找到。
3. **文件类型不同**：项目说明文档通常是方案书、白皮书、产品手册等，与公司简介、财务报表等材料在格式和内容结构上差异很大，需要专门的解析逻辑。
4. **并行效率**：Parser-D可以与Parser-C并行执行，不增加总时间。

### D-06：材料缺失时的处理策略 → U>M>W + 【待补充】

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 材料缺失处理 | A. 大胆推断填充 | B. U>M>W + 标记【待补充】 | **选定B** |

**选择理由**：

1. **可研报告的法律严肃性**：可研报告是投资项目审批、融资的关键文件，数据造假可能导致严重的法律后果。
2. **财务数据零容忍**：从v5.0方案继承的核心资产，财务数据必须100%真实，任何估算都可能导致投资决策失误。
3. **专业透明**：明确标注【待补充】，让用户知道哪些数据需要人工补充，比"看起来完整但数据不可靠"要好得多。
4. **三级兜底**：U（用户材料）→ M（MCP接口）→ W（联网检索），三个层级都尝试过了仍然拿不到的数据，确实需要用户人工提供。

### D-07：质检策略 → 三层质检 + 问题分级 + 最多3轮迭代

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 质检策略 | A. Writer自检即可 | B. 三层质检+问题分级 | **选定B** |

**选择理由**：

1. **Writer自检不够**：Writer在生成内容时存在"自我合理化"倾向，很难发现自己遗漏的二级标题或格式问题。
2. **问题分级避免过度迭代**：P0（格式）必须修复，P1（单章质量）尽量修复，P2（结构）可容忍。分级处理避免无限迭代。
3. **3轮上限保障效率**：无限迭代会导致执行时间不可控。3轮足够解决绝大多数问题，剩余问题在质检报告中记录。
4. **从v5.0继承**：这是经过实战验证的质检策略，v5.0方案中已证明其有效性。

### D-08：第10章（附表附图附件）的归属 → 并入Writer-9输出

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 第10章归属 | A. 独立Writer-10 | B. 并入Writer-9 | **选定B** |

**选择理由**：

1. **内容量小**：第10章目标1,800字，且主要是附表清单、附图清单和附件索引，内容量不足以独立为一个Writer。
2. **与第9章关系紧密**：附表附图附件通常是前9章的补充材料，Writer-9在读完全部9章后，顺手整理附表附件清单是自然的。
3. **NDRC大纲中的第10章**：在国家发改委大纲中，第10章"附表、附图和附件"本身字数要求就较少（1,800字），且在Writer-9的二级标题"9.3 附表、附图和附件说明"中已涵盖。

### D-09：输出格式 → 纯文本 + 纯文本表格（|分隔列）

| 决策项 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 输出格式 | A. Markdown格式 | B. 纯文本+纯文本表格（\|分隔列） | **选定B** |

**选择理由**：

1. **避免Markdown残留**：Markdown格式（#、**、-等）在转换为Word时可能残留格式符号，影响文档专业性。
2. **纯文本表格格式简单、兼容性好、Word渲染友好**：纯文本表格以|分隔列，格式简单直观，Integrator解析后渲染为Word表格，兼容性好。
3. **从v5.0继承**：这是v5.0方案中已验证的格式策略。
