
# 多Agent系统实战指南

## 概述

多Agent系统（Multi-Agent System, MAS）是由多个自主的智能体组成的系统，这些Agent通过协作来解决超出单个Agent能力范围的复杂问题。

**核心思想**：一个Agent什么都会，但什么都不精；把复杂任务拆给多个专业Agent，让它们像团队一样协作。

**类比**：就像公司不是靠一个超级员工，而是靠多个专业角色（产品、设计、开发、测试、运营）协作来完成复杂项目。

---

## 为什么需要多Agent

### 单Agent的局限性

| 局限 | 说明 |
|------|------|
| **能力边界** | 单个模型的能力有上限，不可能精通所有领域 |
| **注意力分散** | Prompt越长、职责越多，行为越不可控 |
| **上下文限制** | 复杂任务信息太多，装不下 |
| **可靠性问题** | 单个Agent出错了就是全错 |
| **效率问题** | 什么都自己干，慢 |

### 多Agent的优势

| 优势 | 说明 |
|------|------|
| **专业分工** | 每个Agent只做一件事，做得更好 |
| **并行处理** | 多个Agent可以同时干活，快 |
| **容错性** | 一个错了还有别人兜底 |
| **可扩展性** | 加新能力就加新Agent |
| **可维护性** | 改一个Agent不影响别人 |

---

## 多Agent协作的核心挑战

| 挑战 | 说明 |
|------|------|
| **任务拆解** | 怎么把一个大任务拆成合适的子任务 |
| **角色定义** | 每个Agent干什么，边界在哪里 |
| **协作机制** | Agent之间怎么沟通、怎么配合 |
| **冲突解决** | 意见不一致时听谁的 |
| **状态共享** | 信息怎么在Agent之间传递 |
| **成本控制** | Agent越多，调用成本越高 |
| **死循环** | AgentA推给AgentB，AgentB又推回AgentA |

## 经典协作模式

### 模式一：流水线模式（Pipeline）

```
用户 → Agent1 → Agent2 → Agent3 → 输出
```

**特点**：
- 线性流程，一步接一步
- 每个Agent只负责一个环节
- 结构简单，容易实现

**适用场景**：
- 内容创作（调研→写作→编辑→排版）
- 数据处理（采集→清洗→分析→可视化）
- 流程明确、步骤固定的任务

**优点**：简单、可控、易调试
**缺点**：不灵活、不能回溯、无法并行

---

### 模式二：主管调度模式（Supervisor / Hierarchical）

```
        ┌──────────┐
        │ 主管Agent │
        └────┬─────┘
       ┌─────┼─────┐
       ▼     ▼     ▼
   ┌───┐  ┌───┐  ┌───┐
   │Agent│ │Agent│ │Agent│
   │ A  │ │ B  │ │ C  │
   └───┘  └───┘  └───┘
```

**特点**：
- 星型拓扑，一个主管管多个专业Agent
- 主管负责：拆解任务、分配工作、收集结果、决定下一步
- 主管不干活，只调度

**适用场景**：
- 90%的生产场景（LangGraph首推模式）
- 任务类型明确、需要集中控制
- 需要保证可靠性和可调试性

**优点**：可控性强、调试简单、路由决策集中
**缺点**：主管可能成为瓶颈、频繁切换时主管调用多

**关键设计要点**：
1. 主管每次只分配给一个Agent
2. 专业Agent的职责边界要清晰
3. 主管要有明确的"结束"判断
4. 设置递归限制防死循环

---

### 模式三：去中心化协商模式（Swarm / Peer-to-Peer）

```
Agent A ←→ Agent B
  ↑          ↑
  ↓          ↓
Agent C ←→ Agent D
```

**特点**：
- 没有主管，Agent之间直接移交控制权
- 每个Agent有handoff工具，觉得自己搞不定就转交给别人
- 像真人团队一样自发协作

**适用场景**：
- 任务模糊、需要灵活协作
- Agent之间需要频繁互动
- 追求自然流畅的协作体验

**优点**：灵活性高、无主管瓶颈、成本较低
**缺点**：调试困难、决策不透明、容易死循环

**关键设计要点**：
1. 每个Agent明确自己的"移交条件"
2. 一定要有递归/循环限制
3. 确保至少有一个Agent能处理终止条件

---

### 模式四：评审团模式（Critic / Ensemble）

```
     ┌─────┐
     │用户 │
     └──┬──┘
        ▼
┌───────────────┐
│  并行生成多个答案  │
│  Agent A B C  │
└───────┬───────┘
        ▼
┌───────────────┐
│   评审/融合    │
│  Judge Agent  │
└───────┬───────┘
        ▼
     最终答案
```

**特点**：
- 多个Agent同时生成答案
- 一个评审Agent（或投票机制）选出最好的
- 类似"专家会诊"

**适用场景**：
- 高质量内容生成
- 复杂推理任务
- 对准确性要求高的场景

**优点**：质量更高、容错性强、集思广益
**缺点**：成本高（N倍调用）、延迟高

---

### 模式五：辩论模式（Debate）

```
Agent A（正方） ←→ Agent B（反方）
        ↓
    Judge（裁判）
        ↓
     最终结论
```

**特点**：
- 两个Agent从不同角度辩论
- 第三方Agent当裁判
- 通过辩论逼近真相

**适用场景**：
- 决策支持
- 风险评估
- 需要多角度思考的问题

**优点**：考虑更全面、减少偏见、提高决策质量
**缺点**：耗时久、成本高

---

### 模式对比总结

| 模式 | 可控性 | 灵活性 | 成本 | 调试难度 | 适用场景 |
|------|--------|--------|------|---------|---------|
| 流水线 | 高 | 低 | 低 | 低 | 固定流程 |
| 主管调度 | 高 | 中 | 中 | 中 | 大多数生产场景 |
| 去中心化 | 低 | 高 | 低 | 高 | 复杂模糊任务 |
| 评审团 | 高 | 中 | 高 | 中 | 高质量要求 |
| 辩论 | 中 | 中 | 高 | 中 | 决策支持 |

**生产建议**：
1. 先用主管调度模式跑通
2. 稳定后，把高频协作路径改成去中心化handoff
3. 对质量要求极高的环节加评审

## 多Agent系统设计方法论

### 第一步：角色定义

**好的角色设计标准**：
1. **职责单一**：每个Agent只做一件事
2. **边界清晰**：什么归我管，什么不归我管，很明确
3. **可评估**：这个Agent干得好不好，有明确标准
4. **可替换**：换一个实现，不影响整体系统

**角色定义模板**：
```
角色名称：
核心职责：
能力范围：
工具权限：
输出标准：
移交条件：（什么时候交给别的Agent）
```

**反模式**：
- ❌ "全能型"Agent：什么都能干
- ❌ 职责重叠：两个Agent能干同一件事
- ❌ 边界模糊："大概归他管吧"

---

### 第二步：状态设计

多Agent协作的核心是信息传递——State就是团队的"公共白板"。

#### 状态设计的三个原则

1. **够用就好**：不要把所有东西都往State里塞
2. **明确归属**：每个字段该谁写、谁读，要清晰
3. **版本意识**：注意覆盖问题，谁先写、谁后写

#### 状态更新的三种模式

| 模式 | 语法 | 适用场景 |
|------|------|---------|
| **覆盖模式** | 普通字段 | 当前版本类数据（如当前草稿） |
| **追加模式** | Annotated[list, add] | 日志、历史、引用来源 |
| **合并模式** | Annotated[dict, or_] | 信息收集类场景 |

---

### 第三步：协作流程设计

#### 设计方法：从业务流程倒推

1. 先画人工完成这个任务的流程图
2. 每个步骤对应一个Agent角色
3. 定义步骤之间的交接标准
4. 确定异常处理路径

#### 常见反模式

1. **Agent太多太碎**：不是每一步都要一个Agent，适当聚合
2. **主管太能干**：主管忍不住自己干活，破坏分工
3. **没有终止条件**：Agent们来回踢皮球
4. **信息传递丢失**：上一个Agent的输出，下一个Agent接不住

## 实战案例：内容创作团队

### 角色设定

| 角色 | 职责 | 工具 | KPI |
|------|------|------|-----|
| **调研员** | 搜集资料、核实来源 | 搜索、文献库 | 资料全面且来源可靠 |
| **撰稿人** | 根据调研写初稿 | 无（只动嘴） | 逻辑连贯、表达清晰 |
| **编辑** | 审核质量、提修改意见 | 语法检查、批注工具 | 找出所有逻辑漏洞 |
| **排版员** | 格式化成最终输出 | Markdown排版 | 格式规范、美观 |

### 为什么这样设计

- **调研员有搜索权，撰稿人没有**：防止撰稿人自己瞎编
- **编辑只提意见不改稿**：保持客观性，避免自己审自己
- **排版员只动格式不动内容**：内容和格式分离，职责清晰

### 协作流程（主管模式）

```
用户需求
    ↓
主管：这是内容创作任务
    ↓
主管→调研员：搜集资料
    ↓
调研员→主管：调研笔记 + 引用来源
    ↓
主管→撰稿人：写初稿
    ↓
撰稿人→主管：初稿
    ↓
主管→编辑：审核
    ↓
编辑→主管：修改意见
    ↓
主管判断：需要大改吗？
    ├── 是 → 转撰稿人修改（循环）
    └── 否 → 转排版员
    ↓
排版员→主管：终稿
    ↓
主管→用户：最终答案
```

## 生产级优化技巧

### 1. 递归限制防死循环

```python
result = supervisor.invoke(
    {"messages": [...]},
    config={"recursion_limit": 25}  # 最多25轮，超限强制终止
)
```

**为什么重要**：多Agent系统最常见的bug就是"踢皮球"——AgentA推给AgentB，AgentB推回AgentA，无限循环。

---

### 2. 分层模型降成本

```python
supervisor_llm = ChatOpenAI(model="gpt-4o", temperature=0)     # 主管用大脑
worker_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.3)  # 工人用小模型
```

**原理**：主管需要推理能力，用强模型；专业Agent只需要执行能力，用小模型。

**效果**：成本降低60-70%，且不影响调度可靠性。

---

### 3. 评估体系

| 评估指标 | 说明 | 怎么测 |
|---------|------|--------|
| **路由准确率** | 主管每次分配对不对 | 人工标注+统计 |
| **工具调用效率** | 完成任务用了多少次工具调用 | 日志统计 |
| **端到端成功率** | 最终输出满足需求吗 | 人工评估+自动指标 |
| **平均交互轮数** | 完成任务需要多少轮 | 日志统计 |
| **单任务成本** | 花了多少钱（token） | 用量统计 |

---

### 4. 监控与调试

**必备能力**：
1. 完整的执行链路追踪（每个Agent的输入输出）
2. 调用次数和成本统计
3. 错误日志和异常告警
4. 重放功能（出了问题能回放）

**工具**：
- LangSmith（LangChain生态）
- LangGraph Studio
- 自建日志系统

---

### 5. 安全与权限

| 层级 | 措施 |
|------|------|
| **工具级** | 每个Agent的工具权限最小化，调研员不能写文件 |
| **状态级** | 敏感字段加密，按角色控制读写 |
| **操作级** | 高风险操作需要人工确认 |
| **审计级** | 所有操作留痕，可追溯 |

## 常见坑与避坑指南

### 坑1：Agent越多越好？

❌ 错误：把任务拆得越细越好，每个小动作一个Agent

✅ 正确：适度拆解，Agent数量以"职责清晰、协作顺畅"为准，不是越多越好

**判断标准**：如果两个Agent总是一前一后出现，而且它们之间的交接很简单，就可以合并。

---

### 坑2：主管什么都管？

❌ 错误：主管既调度又干活，忍不住自己上手

✅ 正确：主管只做调度和决策，专业的事交给专业Agent

**为什么**：主管一旦开始干活，就会分散注意力，调度质量下降，而且破坏了分工原则。

---

### 坑3：没有验收标准

❌ 错误：每个Agent做完就完了，没有检查

✅ 正确：每个Agent的输出都有明确的验收标准，不合格就返工

**方法**：在Agent Prompt里明确写清楚"什么算做好了"。

---

### 坑4：状态一团糟

❌ 错误：State字段随便加，谁都能改

✅ 正确：State设计要规划，每个字段的含义、谁写谁读、会不会覆盖，都要想清楚

---

### 坑5：不做异常处理

❌ 错误：只考虑正常流程，出了错就崩

✅ 正确：每个Agent都有失败处理逻辑，主管有兜底方案

## 选型建议

### 框架选择

| 框架 | 类型 | 特点 | 适用场景 |
|------|------|------|---------|
| **LangGraph** | 图工作流 | 最灵活、生产级、生态好 | 大多数场景 |
| **AutoGen** | 对话驱动 | 多Agent对话自然、微软出品 | 研究、对话类场景 |
| **CrewAI** | 角色化 | 开箱即用、简单易上手 | 快速原型、简单场景 |
| **A2A协议** | 互操作标准 | 跨厂商、跨框架 | 异构Agent协作 |

### 什么时候用多Agent

**该用的情况**：
- ✅ 任务可以拆成多个明确的步骤
- ✅ 不同步骤需要不同的能力/工具
- ✅ 对质量要求高，需要多轮验证
- ✅ 任务复杂，单个Agent搞不定

**不该用的情况**：
- ❌ 简单查询，单Agent秒答的事
- ❌ 任务边界模糊，拆不清的
- ❌ 对延迟要求极高的场景（多Agent慢）
- ❌ 成本敏感，舍不得花钱的

## 总结

多Agent系统是AI应用从"玩具"走向"工具"的关键一步。单个Agent再聪明，也比不过一个配合默契的团队。

**核心认知**：
1. **分工是第一生产力**：专业的Agent做专业的事
2. **可控比灵活重要**：生产环境先保证稳定可控，再追求灵活
3. **架构决定上限**：好的多Agent设计能让系统能力线性增长
4. **人是最终保障**：关键环节加Human-in-the-Loop

**进阶路径**：
1. 单Agent → 2. 主管调度多Agent → 3. 去中心化协作 → 4. Agent市场/生态
