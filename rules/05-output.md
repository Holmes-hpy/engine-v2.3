# 产出物管理规则

> **版本**: v2.3.0
> **优先级**: P5
> **说明**: 本文件定义产出物的版本管理、不可变原则、交付标准和交接契约。

---

## 1. 核心原则：不可变交付物（Immutable Artifacts）

### 1.1 绝对禁止事项

产出物一旦创建，**永不修改**。具体禁止：
- 修改已有产出物的任何内容
- 删除旧版本文件
- 用同名文件覆盖已有文件
- 在原文件上直接编辑

### 1.2 正确做法

需要修改或优化已有产出物时，**必须创建新版本文件**，旧版本完整保留。

```
错误做法：v1.0-设计稿.md → 直接修改 → v1.0-设计稿.md（内容变了，文件名不变）
正确做法：v1.0-设计稿.md → 新建v1.1-设计稿.md → v1.0保留，v1.1新增
```

这就像基础设施领域的"不可变服务器"模式——不修改运行中的服务器，而是创建新服务器替换旧的。

### 1.3 为什么不可变？

- **可追溯**：任何时候都能看到历史版本，知道改了什么
- **可回滚**：新版本有问题，随时可以回退到旧版本
- **无副作用**：不会因为修改文件导致引用该文件的其他内容断裂
- **审计友好**：完整的版本链就是审计轨迹

## 2. 产出物位置

### 2.1 唯一路径

所有产出物一律存放在 `任务文档/{任务}/产出物/`，没有例外。

> 删除了 v2.3.0 之前的"项目级产出物 → output/deliverables/"双路径设计。
> 双路径导致 LLM 困惑，造成产出物散落在三个不同位置（项目根产出物/、output/、任务文档/任务/产出物/）。
> v2.3.0 起统一为单一路径。

### 2.2 产出物类型

| 类型 | 说明 | 位置 |
|------|------|------|
| 草稿(draft) | 任务进行中的版本 | `任务文档/{任务}/产出物/` |
| 定稿(final) | 通过评审的版本 | `任务文档/{任务}/产出物/` |
| 归档(archived) | 已过时但保留备查 | `任务文档/_archive/` |

## 3. 版本命名规范

### 3.1 版本号格式

```
v{major}.{minor}-{YYYYMMDD}-{描述}.{ext}
```

| 字段 | 说明 | 示例 |
|------|------|------|
| major | 主版本号：结构/方向重大变更时+1 | v1, v2 |
| minor | 次版本号：内容补充/修正时+1 | v1.0, v1.1, v1.2 |
| YYYYMMDD | 创建日期 | 20260718 |
| 描述 | 简短描述（可选，建议添加） | api-design、最终方案、初稿 |
| ext | 文件扩展名 | md、py、json、yaml |

### 3.2 完整示例

```
任务文档/20260718-启动包优化/产出物/
├── v1.0-20260715-需求分析.md
├── v1.1-20260716-需求分析-补充边界条件.md
├── v1.2-20260717-需求分析-最终版.md
├── v2.0-20260718-架构设计-重构.md
└── v2.1-20260718-架构设计-补充专家意见.md
```

### 3.3 版本升级决策树

```
需要修改已有产出物？
├── 是 → 当前版本号minor+1（v1.0→v1.1）
│
└── 否（全新产出物）
    ├── 同类型已有产出？
    │   ├── 是 → 继承最高版本号minor+1
    │   └── 否 → v1.0
    └── 是否为结构性重大调整？
        ├── 是 → major+1（v1.5→v2.0）
        └── 否 → minor+1
```

## 4. 版本清单与版本链

### 4.1 .meta/versions.yaml

每个任务文件夹的 `.meta/versions.yaml` 记录该任务所有产出物的版本链：

```yaml
task_id: "TASK-0001"
task_name: "启动包优化"
created_at: "2026-07-18T10:00:00+08:00"

versions:
  - version: "v1.0"
    file: "产出物/v1.0-20260715-需求分析.md"
    created_at: "2026-07-15T10:30:00+08:00"
    type: "draft"
    description: "需求分析初稿"
    predecessor: null
    successor: "v1.1"

  - version: "v1.1"
    file: "产出物/v1.1-20260716-需求分析.md"
    created_at: "2026-07-16T14:20:00+08:00"
    type: "draft"
    description: "补充边界条件"
    predecessor: "v1.0"
    successor: "v2.0"

  - version: "v2.0"
    file: "产出物/v2.0-20260718-架构设计.md"
    created_at: "2026-07-18T09:00:00+08:00"
    type: "final"
    description: "架构设计定稿"
    predecessor: "v1.1"
    successor: null
    tags: ["deliverable", "architecture"]
```

### 4.2 版本链可视化

```
v1.0 ──> v1.1 ──> v2.0(final)
  │        │
  │        └─ type: draft（补充修正）
  └─ type: draft（初稿）
```

## 5. 产出物格式标准

### 5.1 Markdown交付物头部

所有Markdown格式的产出物必须包含以下头部：

```markdown
---
title: {文档标题}
version: v{major}.{minor}
created: {YYYY-MM-DD}
status: draft | final | archived
task_id: TASK-{NNNN}
predecessor: v{major}.{minor} | null
---

# {文档标题}

{正文内容}
```

### 5.2 JSON交付物格式

```json
{
  "_meta": {
    "version": "v1.0",
    "created": "YYYY-MM-DD",
    "status": "draft",
    "task_id": "TASK-NNNN"
  },
  "data": { }
}
```

## 6. 交接契约

### 6.1 交接触发条件

以下情况必须生成交接报告：
1. 任务状态变为 `completed` 或 `failed`
2. 任务执行过程中发生Agent切换
3. 任务涉及多个阶段或子任务
4. 任务产生需要后续使用的中间产物

### 6.2 交接报告位置

交接报告存储在 `任务文档/{任务}/交接报告.md`。

### 6.3 交接报告结构

```markdown
# 任务交接报告

## 基本信息
- 任务ID: TASK-{NNNN}
- 任务名称: {名称}
- 执行Agent: {agent名}
- 开始时间: {ISO8601}
- 结束时间: {ISO8601}
- 任务状态: completed/failed/blocked

## 执行摘要
{3-5句话概括任务执行情况和结果}

## 已完成工作
1. {具体完成项}
2. ...

## 产物清单
| 产物名称 | 路径 | 版本 | 状态 |
|----------|------|------|------|
| {名称} | {相对路径} | v{X.Y} | final/draft |

## 已知问题
- {逐项列出，无则写"无"}

## 待办事项
- [ ] {后续需要完成的事项}

## 关键决策
- {任务过程中做出的重要决策及理由}

## 上下文状态
{描述当前项目/系统状态}

## 建议的下一步
1. {建议操作}
```

### 6.4 交接模式

| 模式 | 适用场景 | 字段要求 |
|------|----------|----------|
| 完整(full) | 跨角色/跨阶段正式交接 | 全部字段 |
| 轻量(light) | 同角色内简单交接 | 基本信息+已完成+待办+已知问题 |

### 6.5 交接验证

生成交接报告后必须自检：
- [ ] 所有产物路径正确且可访问
- [ ] 已完成工作描述准确
- [ ] 待办事项明确可执行
- [ ] 关键决策有理由说明

交接不合格 → 任务状态变为 `handoff_incomplete`，要求补充。
