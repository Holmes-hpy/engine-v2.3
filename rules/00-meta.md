# 元规则（Meta Rules）

> **版本**: v2.3.0
> **优先级**: P0（最高）
> **说明**: 本文件定义规则体系本身的规则。所有其他规则文件必须遵守本文件的约束。

---

## 1. 规则文件清单与优先级

本项目的规则体系由以下文件构成，按编号顺序排列，**编号越小优先级越高**：

| 编号 | 文件 | 约束对象 | 优先级 |
|------|------|----------|--------|
| 00 | `00-meta.md`（本文件） | 规则体系本身 | P0 |
| 01 | `01-llm-behavior.md` | LLM 自身行为 | P1 |
| 02 | `02-project-structure.md` | 项目目录结构与命名 | P2 |
| 03 | `03-task-execution.md` | 任务执行流程 | P3 |
| 04 | `04-knowledge.md` | 知识管理与三层沉淀 | P4 |
| 05 | `05-output.md` | 产出物管理 | P5 |
| - | `_registry.yaml` | 规则注册表（索引） | - |
| - | `rules.md`（根目录） | 规则体系入口（跳板文件） | 最先加载 |

### 1.1 优先级链

```
00-meta > 01-llm-behavior > 02-project-structure > 03-task-execution > 04-knowledge > 05-output
```

当两条规则发生冲突时，**编号小的规则胜出**。例如：
- `01-llm-behavior.md` 规定"拿捏不准必须反问"，而 `03-task-execution.md` 规定"故障后自动重试"——如果故障原因是 LLM 不确定如何处理，L1 行为规则胜出，LLM 应先反问用户而非自动重试。

### 1.2 全局前提

`01-llm-behavior.md` 中的行为规则是**全局前提条件**，适用于所有场景、所有任务、所有阶段。无论执行什么操作，都必须先满足 L1 行为约束。

## 2. 冲突解决机制

### 2.1 冲突类型

| 冲突类型 | 定义 | 解决方式 |
|----------|------|----------|
| 直接矛盾 | 两条规则对同一行为给出相反指令 | 编号小的胜出 |
| 范围重叠 | 两条规则都涉及同一领域但侧重不同 | 同时遵守，取并集 |
| 场景限定 vs 通用 | 一条是通用规则，一条是特定场景规则 | 场景限定规则优先（在其适用场景内） |
| 新增规则 vs 旧规则 | 用户新增规则与现有规则冲突 | 新增规则优先（时间最近原则） |

### 2.2 场景限定规则标记

当一条规则仅在特定场景下生效时，必须在规则标题后标注适用场景：

```markdown
### 规则名称 [场景: xxx]
```

例如：
- `### 对话保存规则 [场景: 所有任务执行期间]`
- `### 命名前缀规则 [场景: 用户自定义Agent/Skill]`

### 2.3 无法解决的冲突

如果遇到本文件未覆盖的冲突情况：
1. **不得自行猜测解决方案**
2. 必须反问用户，列出冲突的规则和各自的后果
3. 等待用户裁决后再继续执行

## 3. 规则扩展协议

### 3.1 新增规则的判断流程

当用户提出新的约束要求时，按以下步骤判断放入哪个规则文件：

```
新约束约束的是什么？
├── LLM 自身的行为（怎么说话、怎么思考、怎么做决策）
│   └── 放入 01-llm-behavior.md
├── 目录/文件/命名/结构
│   └── 放入 02-project-structure.md
├── 任务的创建/执行/状态/流转/故障
│   └── 放入 03-task-execution.md
├── 知识沉淀/记忆/挖掘/本体化
│   └── 放入 04-knowledge.md
├── 产出物/版本/交付/交接
│   └── 放入 05-output.md
└── 以上都不属于
    └── 放入最相关的文件中，在规则标题后标注 [跨维度: 新维度名]
```

### 3.2 跨维度规则处理

- 跨维度规则放入语义最接近的现有文件
- 在规则标题后标注 `[跨维度: 维度名]`
- 当同一文件中积累超过 **3 条**同一维度的跨维度规则时，提取为新的编号规则文件（如 `06-cost.md`）
- 新文件插入时，后续文件编号顺延（不重新编号现有文件）

### 3.3 禁止事项

- **禁止**修改已有规则的含义（只能追加补充说明或新建版本）
- **禁止**删除规则条目（只能标记为 deprecated）
- **禁止**在规则文件中混入项目特定配置（配置应放在 `.meta/` 目录）
- **禁止**在规则文件中写代码（规则描述行为，不实现行为）

## 4. 规则加载策略

### 4.1 启动时必加载

项目初始化完成后，以下文件必须加载到 LLM 上下文：
- 全部 6 个规则文件（00-05）
- `项目使用指南.md`
- `_registry.yaml`

### 4.2 任务执行时按需加载

在任务执行过程中，LLM 已加载全部规则（通过项目使用指南和启动清单），无需额外判断加载哪些规则。规则文件按设计保持精简（每个文件控制在合理长度内），全部加载的 token 成本可控。

### 4.3 规则引用格式

在对话、交接报告、沉淀日志中引用规则时，使用以下格式：

```
[规则编号: 章节号]
```

例如：`[L1: 3.2]` 表示引用 `01-llm-behavior.md` 第 3.2 节。

---

## 5. 规则版本管理

- 规则文件本身属于启动包的一部分，随启动包版本管理
- 启动包版本号见 `.bootstrap-complete` 文件
- 规则的每次重大变更对应启动包的一个新版本
- 禁止在已部署项目中直接修改规则文件——规则变更通过部署新版本启动包实现

## 6. 术语定义

| 术语 | 定义 |
|------|------|
| **LLM** | 大语言模型，即执行本规则的人工智能 |
| **用户** | 项目的拥有者和使用者，即人类 |
| **任务** | 用户提出的一个独立工作单元，有明确的开始和结束 |
| **Agent** | 扮演特定专家角色的 LLM 实例 |
| **产出物** | 任务执行过程中产生的可交付文件 |
| **沉淀** | 从对话和产出物中提取有价值知识并存储的过程 |
| **捡破烂** | 无约束地从原始对话记录中挖掘潜在价值内容的过程 |
| **BOOTSTRAP_DIR** | 启动包所在目录（只读，不写入） |
| **TARGET_DIR** | 项目初始化的目标目录（所有操作在此执行） |
