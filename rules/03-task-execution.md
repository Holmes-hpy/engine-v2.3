# 任务执行流程规则

> **版本**: v2.3.0
> **优先级**: P3
> **说明**: 本文件定义任务从创建到归档的完整流程，包括状态机、生命周期、故障恢复、自动认知和会话持久化。

---

## 1. 任务状态机

### 1.1 状态定义

| 状态 | 代号 | 说明 |
|------|------|------|
| pending | 待处理 | 任务已创建，等待执行 |
| in_progress | 进行中 | 任务正在执行 |
| completed | 已完成 | 任务成功完成 |
| failed | 失败 | 任务执行失败 |
| blocked | 阻塞 | 任务因依赖未满足或不确定而暂停 |
| reviewing | 评审中 | 任务产物待评审 |
| handoff_incomplete | 交接不完整 | 任务完成但交接报告缺失 |
| archived | 已归档 | 任务已归档，不再活跃 |

### 1.2 合法状态流转

```
                        ┌─────────────┐
             ┌─────────►│   pending   │◄──────────┐
             │          └──────┬──────┘           │
             │                 │ start            │ retry
             │                 ▼                  │
             │          ┌─────────────┐           │
             │    block │  in_progress│           │
             │◄─────────┤             ├─────┐     │
             │          └──────┬──────┘     │     │
             │                 │            │     │
             │          submit │        fail │     │
             │                 ▼            │     │
             │          ┌───────────┐        │     │
             │          │ reviewing │◄───┐   │     │
             │          └─────┬─────┘    │   │     │
             │         pass  │ reject    │   │     │
             │               │       ┌───┘   │     │
             │               ▼       ▼       │     │
        ┌────┴────┐    ┌─────────┐  ┌───────┴──┐   │
        │ blocked │    │completed│  │  failed  │───┘
        └────┬────┘    └────┬────┘  └──────────┘
             │              │
             │        ┌─────┴──────────┐
             │        │                │
             │   archive│  handoff_fail │
             │        ▼                ▼
             │   ┌──────────┐  ┌──────────────────────┐
             │   │ archived │  │ handoff_incomplete    │
             │   └──────────┘  └──────────┬───────────┘
             │                            │ fix
             │                            ▼
             │                     ┌─────────┐
             └─────────────────────│completed│
                                   └─────────┘
```

| 从状态 | 到状态 | 触发条件 |
|--------|--------|----------|
| pending | in_progress | 任务开始执行 |
| pending | blocked | 依赖任务未完成/缺少关键信息需反问 |
| in_progress | reviewing | 任务完成，提交评审 |
| in_progress | failed | 任务执行出错（重试耗尽） |
| in_progress | blocked | 执行中发现新依赖/遇到不确定需反问 |
| reviewing | completed | 评审通过 |
| reviewing | in_progress | 评审不通过，返回修改 |
| reviewing | failed | 评审发现严重问题 |
| blocked | in_progress | 依赖已满足/用户已回答问题 |
| failed | pending | 重置任务，准备重试 |
| completed | archived | 任务归档 |
| completed | handoff_incomplete | 交接报告缺失 |
| handoff_incomplete | completed | 补充交接报告 |

### 1.3 禁止的流转

- `completed → failed`（已完成任务不应回退）
- `archived → 任何状态`（已归档任务不可变更）
- `failed → completed`（必须先经过pending重试）

## 2. 任务生命周期

### 2.1 阶段总览

```
创建 → 自动认知 → 执行 → 评审 → 完成 → 交接 → 归档
```

### 2.2 创建阶段 (Create)

**触发条件**: 用户提出新需求。

**执行步骤**:
1. 解析用户意图，提取任务主题（2-6个汉字/英文）
2. 生成任务ID：`TASK-{NNNN}`（按序列递增）
3. 检查 `任务文档/` 下是否已存在同名文件夹（同日重复处理见下方）
4. 创建任务文件夹：从 `_template/` 复制模板
5. 创建捡破烂文件夹：同步在 `捡破烂/` 下创建同名文件夹
6. 生成任务定义JSON，写入 `tasks/active/`
7. 状态设为 `pending`

**同名处理**:
- 同日同名文件夹存在 → 检查是否同一任务
  - 是 → 提示用户"该任务已存在"，确认是否继续
  - 否 → 自动追加序号 `-01`、`-02`

**任务JSON模板**:
```json
{
  "task_id": "TASK-0001",
  "title": "任务标题",
  "status": "pending",
  "priority": "normal",
  "version": 1,
  "retry_count": 0,
  "max_retry_count": 3,
  "created_at": "ISO8601",
  "started_at": null,
  "completed_at": null,
  "assigned_agent": null,
  "task_folder": "任务文档/20260718-xxx/",
  "junk_folder": "捡破烂/20260718-xxx/",
  "artifact_version_counter": 0,
  "conversation_rounds": 0,
  "knowledge_extracted": 0,
  "transitions": [],
  "subtasks": [],
  "dependencies": [],
  "context": {
    "project_guide_loaded": false,
    "startup_checklist_generated": false,
    "rules_loaded": [],
    "experts_recommended": []
  }
}
```

### 2.3 自动认知阶段 (Auto-Cognition)

**触发条件**: 任务文件夹创建成功后，开始执行前。

**执行步骤**:
1. 读取 `项目使用指南.md`（了解项目全貌）
2. 读取 `rules/` 下所有规则文件（00-05）
3. 读取 `rules/_registry.yaml`（规则索引）
4. 扫描 `expert-library/` 目录（了解可用专家）
5. 查询 `.memory/knowledge.db`（获取项目当前状态）
6. 生成《任务启动清单》（从模板复制并填充）
7. 更新任务JSON的 `context` 字段，标记认知完成

**任务启动清单内容**:
- 当前任务基本信息
- 已加载规则列表（全部6条）
- 推荐专家（基于任务关键词匹配Top5）
- 项目当前状态摘要
- 注意事项（版本管理、知识沉淀等）

### 2.4 执行阶段 (Execute)

**触发条件**: 状态变为 `in_progress`。

**执行规范**:
1. 遵循 `01-llm-behavior.md` 的方案优先原则——先出方案再执行
2. 每完成一个子步骤，更新任务状态
3. 每轮对话结束后（下一轮对话开始前，采用延迟执行模式，详见 `01-llm-behavior.md` 第2节）：
   - 保存对话到 `捡破烂/{任务}/round-{NN}.md`
   - 追加摘要到 `任务文档/{任务}/对话记录.md`
   - 更新任务JSON的 `conversation_rounds`
4. 产出物保存到 `任务文档/{任务}/产出物/`，遵循版本管理规则（见05-output）
5. 执行实时知识沉淀（见04-knowledge，采用延迟执行模式）

**异常处理**:
- 遇到不确定的问题 → 状态变为 `blocked`，反问用户（遵循L1反问不猜原则）
- 执行出错 → 进入故障恢复流程（见第4节）
- 发现新依赖 → 创建子任务，状态变为 `blocked`

### 2.5 评审阶段 (Review)

**触发条件**: 任务执行完成，产出物已提交。

**评审流程**:
1. 执行方完成任务后，状态变更为 `reviewing`
2. 用户检查任务产物
3. 评审结论：
   - 通过 → `reviewing → completed`
   - 不通过 → `reviewing → in_progress`（返回修改，附评审意见）
   - 严重问题 → `reviewing → failed`

### 2.6 完成阶段 (Complete)

**完成标准检查清单**:
- [ ] 评审已通过
- [ ] 所有预期产出物已生成
- [ ] 产出物符合格式规范和版本管理规则
- [ ] 对话记录已完整保存到捡破烂
- [ ] 知识沉淀已完成
- [ ] 交接报告已生成

### 2.7 交接阶段 (Handoff)

**触发条件**: 任务完成或Agent切换。

交接报告存储在 `任务文档/{任务}/交接报告.md`，包含：
- 任务基本信息
- 执行摘要（3-5句话）
- 已完成工作清单
- 产物清单（含路径、版本、状态）
- 已知问题
- 待办事项
- 关键决策记录
- 建议的下一步

**交接验证**:
- 交接报告必须通过完整性自检
- 不通过 → 状态变为 `handoff_incomplete`，要求补充
- 补充完成 → 状态回到 `completed`

### 2.8 归档阶段 (Archive)

**触发条件**: 任务完成后90天，或用户显式要求归档。

**归档动作**:
1. 任务文件夹从 `任务文档/` 移动到 `任务文档/_archive/`
2. 捡破烂文件夹中超过4周的对话移动到 `捡破烂/_archive/`
3. 任务JSON移动到 `tasks/completed/`
4. 更新任务索引

## 3. 并发控制

### 3.1 最大活跃任务数

`MAX_ACTIVE_TASKS = 10`

当活跃任务数达到上限时，新任务进入等待队列。

### 3.2 任务优先级

| 优先级 | 数值 | 说明 |
|--------|------|------|
| critical | 1 | 阻塞其他任务的关键路径 |
| high | 2 | 重要任务 |
| normal | 3 | 普通任务（默认） |
| low | 4 | 可延后处理 |

### 3.3 乐观锁

任务JSON中的 `version` 字段作为乐观锁：
1. 读取当前version
2. 执行变更
3. 写入时检查version是否一致
4. 一致 → 更新并version+1
5. 不一致 → 回滚，等待3秒重试，连续3次冲突则标记blocked

## 4. 故障恢复

### 4.1 故障分级

| 等级 | 名称 | 影响范围 | 响应时间 |
|------|------|----------|----------|
| L1 | 致命 | 整个系统不可用 | 立即 |
| L2 | 严重 | 当前任务完全失败 | 5分钟内 |
| L3 | 一般 | 当前任务部分失败 | 15分钟内 |
| L4 | 轻微 | 非核心功能受影响 | 下次执行时 |

### 4.2 故障判定

```
IF 磁盘空间耗尽 OR 数据库损坏 OR 核心规则丢失 THEN L1
IF 任务执行抛出未捕获异常 AND 无检查点 THEN L2
IF 任务执行抛出异常 BUT 有检查点 THEN L3
IF 输出格式不规范 OR 日志写入失败 THEN L4
```

**关键约束**: 如果故障原因是 LLM 不确定如何处理，**必须先反问用户（遵循L1反问不猜原则）**，而非自动重试。自动重试仅适用于确定性故障。

### 4.3 恢复策略

**L1（致命）**:
1. 停止所有任务，记录状态快照
2. 保存故障现场到 `logs/fault/scenes/`
3. 从最近检查点回滚
4. 运行健康检查验证
5. 回滚失败 → 请求人工介入

**L2（严重）**:
1. 标记任务为failed
2. 检查是否有检查点
   - 有 → 从检查点恢复，状态设为pending
   - 无 → 从头开始
3. 重试计数+1
4. 重试≥3次 → 标记永久失败，请求人工介入

**L3（一般）**:
1. 从最后检查点恢复
2. 跳过已完成步骤，继续执行
3. 记录恢复事件

**L4（轻微）**:
1. 记录WARNING日志
2. 跳过故障步骤，继续执行
3. 交接报告中标注问题

### 4.4 重试策略

- 最大重试次数：3次
- 退避策略：立即 → 30秒 → 2分钟
- 不重试的情况：语法错误、权限不足、磁盘空间不足、依赖文件缺失、需要用户决策的情况

### 4.5 检查点机制

- 任务状态变更时自动创建状态检查点
- 关键步骤完成后创建步骤检查点
- 检查点存储在 `tasks/checkpoints/{task_id}/`
- 默认保留最近3个检查点

### 4.6 必须请求人工介入的情况

1. 同一任务连续失败超过3次
2. L1故障无法自动恢复
3. 检查点文件损坏
4. 检测到数据不一致
5. 系统资源持续不足超过10分钟

## 5. 任务超时

按优先级设置执行时长上限（仅累计in_progress状态时间）：

| 优先级 | 执行时长上限 |
|--------|-------------|
| critical | 24小时 |
| high | 72小时 |
| normal | 168小时（7天） |
| low | 336小时（14天） |

- 达到75%时触发超时预警
- 达到100%时自动进入blocked状态

## 6. 会话持久化

### 6.1 对话记录保存

每轮对话结束后（下一轮对话开始前，采用延迟执行模式，详见 `01-llm-behavior.md` 第2节），需同时保存两处：
1. **原始对话** → `捡破烂/{任务}/round-{NN}.md`（完整原文，见L1第2节）
2. **对话摘要** → `任务文档/{任务}/对话记录.md`（结构化摘要）

### 6.2 对话记录.md格式

```markdown
# 对话记录 - {任务标题}

---
## 第{N}轮
- 时间: {ISO8601}
- 用户输入摘要: {1句话概括}
- 助手响应摘要: {1句话概括}
- 关键决策: {列出本轮做出的决策，无则写"无"}
- 重要发现: {列出本轮的新发现，无则写"无"}
- 待办事项: {列出新增待办，无则写"无"}
- 已沉淀知识: {列出本轮沉淀的知识点，无则写"无"}

**用户输入原文摘要:**
{截取前100字...}

**助手响应原文摘要:**
{截取前100字...}
---
```

### 6.3 沉淀日志

每次知识沉淀操作记录到 `任务文档/{任务}/沉淀日志.md`，包含：
- 沉淀时间
- 沉淀类型（实时/周度挖掘）
- 沉淀内容摘要
- 存储位置
- 置信度

---

## 7. 任务间关系

- **父子任务**: 父任务在所有子任务完成后才能completed
- **依赖任务**: 任务A依赖B → A在B完成后才能开始
- 关系记录在任务JSON的 `dependencies` 和 `subtasks` 字段
